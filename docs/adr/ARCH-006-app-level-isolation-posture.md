# ADR: ARCH-006 — Per-user isolation and data invariants are enforced at the application layer, with CI guards as the load-bearing compensating controls

**Status:** Accepted
**Date:** 2026-06-18
**Source:** `/improve-codebase-architecture` on the *schema + trigger + RLS layer*, then `/grill-with-docs` over the five resulting plans (`retired-docs:superpowers/plans/archive/2026-06-18-{per-user-isolation-seam-r4, reducer-complete-bump-push-seam, reducer-invariant-db-backstops, schema-truth-and-migration-order-guards, trigger-families-dsn-misplacement}.md`). Resolves the documented-vs-real R4 contradiction and records the cross-plan posture.

## Context

Three shipped documents described per-user isolation (R4) three different ways, and one was false:

- `docs/standards/DATABASE_SECURITY.md` R4 prescribes **native PostgreSQL RLS** (`ENABLE`/`FORCE ROW LEVEL SECURITY` + per-action `CREATE POLICY` keyed on `current_setting('app.current_user_id', true)`, with a per-request transaction-scoped `set_config` gateway injection).
- `mailserver/AGENTS.md:98` claimed "RLS enforced + FORCE'd on all user-data tables."
- `mailserver/sql/AGENTS.md:42` said the truth: isolation is enforced via **`p_mailbox_id` parameter propagation in reducers**, not native RLS.

Measured reality (2026-06-18): **zero** tables `ENABLE ROW LEVEL SECURITY`, **zero** `CREATE POLICY`, and **zero** Go calls inject per-user DB context (`set_config('app.current_user_id'|…)` — the only `set_config` is the session-scoped, same-for-every-user `app.encryption_key`). The native-RLS pattern in the standard is **aspirational, not implemented**.

The grill then found the same shape repeats across the layer — several correctness invariants live in application code (the reducer/the gateway), not in the database:

- **R4 scoping** is reducer-threaded `p_mailbox_id`, not RLS.
- **Storage and sending quotas** are enforced only in `deliver()`/`send()` (the ceiling is a *transition* invariant — an admin may legitimately lower a quota below current usage — so a DB `CHECK` would fire on valid rows; see CONTEXT.md → *State invariant vs transition invariant*).
- **`scheduled_actions.action_kind`** has no `CHECK`; the kind's validity is enforced by the dispatcher's switch.

Each choice is individually reasonable. Together they constitute a **posture**: correctness is concentrated in "did we remember to scope/validate in application code, and does CI catch it if we didn't." That posture is coherent and aligned with the project's "logic where the data is" architecture — but it makes the **guard layer load-bearing**, not optional hardening. The day a guard regresses silently is the day the posture stops being safe. This ADR records the posture and names the controls that make it safe.

## Decision

1. **R4 is enforced at the application layer, and the standard says so.** `DATABASE_SECURITY.md` R4 is rewritten to describe the real boundary — `p_mailbox_id` propagation (R1/R3 in reducers) + the `account_scope`/`provision_account` resolver seams + the `check-account-scope.sh` guard + divergent-id pgTAP fixtures — as **the** enforcement. The native-RLS pattern is retained only as a clearly-labelled *"Considered / deferred — NOT enforced"* pointer to this ADR and to the deferred plan. `mailserver/AGENTS.md:98`'s false claim is corrected to cite `sql/AGENTS.md:42`.

2. **Native PostgreSQL RLS is deferred, not rejected.** It is the only *fail-closed-at-runtime* control, but building it is a gateway-wide project (no per-request transaction exists today — `internal/jmap/` is 67 auto-commit calls, zero `.Begin(`; it needs `BYPASSRLS`/worker-role carve-outs that reopen the *Dispatch privilege boundary*; policies must key on `mailbox_id` with a NULL-owner case). It is captured, grounded, and grill-ready in `retired-docs:superpowers/plans/archive/2026-06-18-native-rls-backstop.md`. **Re-trigger:** after the go-translator IMAP/SMTP thinning shrinks the raw gateway query surface (234 raw user-data-table query literals today — the precise count from `check-gateway-ownership.sh` after the 2026-06-18 precision+coverage tightening; 175 carry a scoping token **in a predicate context**, 59 allowlisted — concentrated in IMAP/CardDAV/admin), **or** on a missing-filter cross-tenant incident, **or** on a compliance requirement for DB-enforced isolation.

3. **The compensating controls are load-bearing and each is self-tested.** Deferring RLS chooses **fail-open** as the steady state (a forgotten predicate leaks; RLS would deny). That is only acceptable if the guard layer is *positive*, not an allowlist of known-bad shapes the next engineer's new path quietly evades. The controls, and the property each protects:
   - **The account-scope guard becomes *positive*.** Today `check-account-scope.sh` is negative (it pattern-matches known-bad predicates — `user_id = p_mailbox_id`, etc. — with allowlists). It is extended to *fail closed*: a new user-data access (reducer, and via a new `check-gateway-ownership.sh`, a raw gateway query) that does not carry a scoping token fails CI. The residual is explicit: an allowlisted-then-changed query, or dynamic SQL, can still evade — RLS (decision 2) is what eventually closes that.
   - **State invariants take a DB `CHECK`; transition invariants stay in the reducer.** Floors (`used_bytes ≥ 0`, `sending_sent_today ≥ 0`) are added as `CHECK`s (free, un-bypassable, catch decrement underflow); ceilings/quotas stay reducer-guarded.
   - **The read-receipt `never` policy gets a guard trigger** that re-derives the policy via `messages → account_scope() → get_read_receipt_policy()` (mailbox-keyed, alias-proof by construction).
   - **The dispatcher fails safe** on an unknown `action_kind` (`BZ036` → retry → terminal `failed` + logged), backstopping the unconstrained column.
   - **The schema/migration split is guarded** by a determinism check (byte-identical replay), a column-parity convergence pgTAP, and a no-duplicate-version guard.
   Each ships with its own `-selftest.sh` (or pgTAP) so a silent regression of the control is itself caught.

4. **Address-keyed rules resolve through one seam; mailbox-keyed rules through another; neither hand-rolls the match.** Address-keyed rules (the only handle is an email/UPN — e.g. a bounce's `from_addr`) go through `resolve_identity`; mailbox/message-keyed rules (a `mailbox_id`, or a `message_id` that joins to one) go through `account_scope`. Raw `lower(addr)` matching in a rule is forbidden (it spawns a new twin of the single-sourced predicate, re-introducing the ADR-004 alias-miss class). See CONTEXT.md → *Directory scope / identity resolution*.

## Considered options

- **Fork B now — build native RLS as the R4 mechanism.** Rejected *for now* (not on principle): it is the only fail-closed-at-runtime control, but the cost is a gateway-wide transaction-discipline change plus reopening the Dispatch-privilege-boundary decision, and it would backstop a raw-query surface the go-translator program is about to shrink. Deferred with a concrete re-trigger (decision 2), not dropped.
- **Leave the docs as-is.** Rejected: a security standard that prescribes a mechanism with 0% deployment is worse than no standard — it reads as enforced and hides the real boundary from the next maintainer/AI.
- **Add a DB `CHECK` for every invariant (quotas included).** Rejected: a ceiling `CHECK` rejects the legitimate admin-oversubscribe / reconciliation-overwrite states. Only *state* invariants (floors, enums, NOT-NULL pairs) become `CHECK`s; *transition* invariants stay in the reducer that owns the transition.
- **Keep the account-scope guard negative (pattern-match only).** Rejected as the steady state under a deferred-RLS posture: a negative guard is fail-open against a brand-new unscoped path. The guard is made positive precisely because it is now a load-bearing control, not optional hardening.

## Consequences

- `DATABASE_SECURITY.md` R4 rewritten (real boundary as enforcement; native RLS demoted to a deferred pointer) + a one-line *state-vs-transition* rule for when an invariant is a `CHECK`. `mailserver/AGENTS.md:98` corrected.
- `check-account-scope.sh` extended from negative to positive; new `check-gateway-ownership.sh` (+ selftests) covering the raw gateway query surface; both wired into `scripts/test.sh`. **The positive guard is the control that makes the RLS deferral safe — its coverage is the residual risk's only bound until RLS lands.**
- New `CHECK`s for the usage floors (one migration, `users`/`mailboxes` byte counters); read-receipt `never` guard trigger; the schema-truth determinism + column-parity + no-duplicate-version guards.
- Native RLS becomes a tracked, grounded, deferred plan (`2026-06-18-native-rls-backstop.md`) with a recorded re-trigger — future architecture reviews must not re-suggest it as new; they update the plan or fire the trigger.
- **Residual risk, stated plainly:** until native RLS lands, a future unscoped path that evades the positive guard's coverage (allowlist drift, dynamic SQL, a token in a SET assignment, an ownership check the awk can't relate across statements) can leak cross-mailbox data at runtime. The sole compensating controls are the positive guard's coverage and code review. This is the accepted, eyes-open cost of deferring RLS.
- **2026-06-18 precision+coverage tightening (post-Wave-2 adversarial verify).** Two real gaps closed: (1) a pre-existing info-disclosure IDOR — `user/recall.go` read a message's `from_addr`/`received_at`/`Message-ID` by id with no ownership binding (the metadata leaked to any authenticated user before the sender check); fixed by binding the read to a mailbox the caller owns (`JOIN mailboxes … WHERE mb.user_id = $caller`). (2) the guard was both too loose and too narrow: it counted an ownership token **anywhere** in the literal (so recall.go's projection token passed) and its `UDT_RE` omitted real per-user tables. The token check now requires a **predicate context** (recall.go's exact shape now fails the guard), and `UDT_RE` gained tags, quarantined_messages, user_spam_model, user_sender_list, user_smime_certs, user_signatures, user_imap_settings, message_attachments, app_passwords, sessions. The newly-surfaced queries were each resolved (R2-INSERTs, admin consoles, prior-ownership-checked user reads, delivery path) — fixed or honestly allowlisted, never by loosening the guard. See `docs/standards/DATABASE_SECURITY.md` R4 for the full covered-table list.

## Addendum (2026-07-05) — honest record of the un-defer trigger + the topology decision

- **The un-defer was directive-driven, not a recorded trigger.** Decision 2 above names exactly two re-trigger conditions for building native RLS: the go-translator thinning shrinking the raw gateway query surface, or a missing-filter incident / compliance requirement forcing DB-enforced isolation. **Neither fired.** The native-RLS-backstop program was un-deferred and executed starting 2026-06-19 by direct user instruction (queued as the final wave of a full-queue execution), with the thinning prerequisite explicitly **not fully met** at that time (45 JMAP + 36 IMAP + 9 CardDAV auto-commit call sites, zero `.Begin`, zero RLS — accepted eyes-open; see the plan's own "eyes-open" note). This is recorded here so the ADR's re-trigger language isn't read as having been satisfied when it wasn't — the work is still sound (verified end-to-end by the 2026-07-03 flip rehearsal and the 2026-07-05 autoplan gauntlet review), it was simply authorized by direct instruction rather than by either recorded condition.
- **Supported topology, decided 2026-07-05: strict one-organization-per-install.** Each setjoin deployment is exactly one organization; there is no multi-org/MSP-hosting model. Under that topology, the real isolation boundary customers need is cross-**mailbox** *within* their one org — which the application-layer predicates + positive CI guards (decision 3) already enforce and already pass SOC2/ISO review. Native RLS is therefore **defense-in-depth, not the load-bearing control** — a second, independent backstop, not a gap-filler. The flip stays **opt-in and reversible per install** (never a forced-on default) precisely because it is polish, not a compliance requirement. Consequently, the `is_local` cross-organization recall question (`native-rls-backstop.md` fork 4) is **explicitly out of scope**: setjoin's recall/isolation model only ever needs to reason about same-tenant (same-install) boundaries. If a future deployment model ever supports multiple organizations on one install, this topology assumption — and therefore RLS's load-bearing-vs-defense-in-depth status — must be re-litigated, not silently assumed to still hold.
