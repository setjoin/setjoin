# ADR: ARCH-018 — The FORCE-RLS Scope-Helper Recipe

**Status:** Accepted
**Date:** 2026-07-16
**Source:** Collaboration Suite whole-pipeline review (2026-07-16), architecture lens finding #2 (Strong), converged with the security lens's independent finding on `meeting_member_role`; `TODOS.md` → "Collaboration Suite — whole-pipeline review: deferred findings" → arch #2.

## Context

Every FORCE-RLS table family shipped since Drive P1 (`drive_*`, V114) has hit the same wall: a membership predicate written **inline** in a `CREATE POLICY` — `EXISTS (SELECT 1 FROM drive_space_members WHERE space_id = id AND user_id = …)` on `drive_space_members` itself, or the chat/meet equivalents — makes the policy evaluate its own table while resolving its own table's policy. Under `FORCE ROW LEVEL SECURITY` that is `ERROR: infinite recursion detected in policy for relation "…"`, not a slow query — the table becomes unreadable to any non-bypass role.

The fix has been rediscovered five times (Drive V114, Chat V119, Meet V125, Meet-recording V129 twice) and each site's comment cites the prior one by name ("the V114/V119 recursion-dodge, Nth use") instead of a single canonical write-up. Two real drifts accumulated during that replication, caught only by a whole-pipeline review reading all seven side by side:

- **The `search_path` pin split in two.** The drive family (`drive_member_role`, `drive_space_owner`, `drive_has_admin_perm`, all V114; `chat_hold_active`, V126/V127) pins `SET search_path = pg_catalog, public`. `chat_member_role` (V119) and `meeting_member_role` (V125) shipped pinning `public` only — and V125's own comment *names* the SECURITY DEFINER search_path escalation foot-gun immediately above the weaker pin, then uses it anyway. `meeting_attendee_role` (V129) copied the V125 shape verbatim, propagating the weaker form a third time.
- **The liveness-filter matrix lives in nobody's head.** Three helpers read the same kind of "is this person still here" fact from three different tables/shapes, each individually justified in its own migration's comment, with no single place that shows all three side by side. The security lens flagged this independently: a kicked-but-not-yet-evicted meeting participant (`banned_at` set, `left_at` not yet stamped) still reads as a member through `meeting_member_role`, and nothing before this review said whether that was intended.

Neither drift caused an observed incident. `pg_catalog` is implicitly first in any search_path that doesn't explicitly exclude it, and every statement in all seven helper bodies already schema-qualifies its own tables (`public.<table>`), so the weaker pin is not currently exploitable — but it is one un-owned pin away from being copied into a helper whose body someday does NOT fully qualify its identifiers. Pillar C (federation) will mint a ninth scope helper next; this ADR exists so #9 starts from the recipe instead of grepping the newest-looking prior example. (#8, `drive_user_can_write_regular`, was added and normalized into this matrix 2026-07-16 — arch #A3 — after shipping as an undiagnosed inline workaround; see the postmortem below the matrix.)

## Decision

**A FORCE-RLS table whose policy needs to check membership/role/hold-state on a table that is itself FORCE-RLS'd (directly, or one join away) resolves that check through a `SECURITY DEFINER` scope helper — never an inline subquery on the policy-protected table.**

The recipe, as a checklist:

1. **Why a DEFINER helper, not an inline predicate.** A policy on table `T` may not contain a subquery against `T` (or a table whose own policy recurses back to `T`) evaluated as the *invoker* — RLS re-enters the invoker's policy on every row and PostgreSQL raises `infinite recursion detected in policy`. A `SECURITY DEFINER` function runs as its **owner** (`setjoin_worker`, a `BYPASSRLS` role — see root `AGENTS.md` → native-RLS DSNs), so the membership lookup inside it does not re-enter any policy at all. The helper is the ONE place the recursion is broken; every policy that needs the fact calls the helper, never the table.
2. **`SET search_path = pg_catalog, public` is MANDATORY on every such function**, no exceptions. This is the classic PostgreSQL `SECURITY DEFINER` privilege-escalation foot-gun: without an explicit pin, the function runs with the *caller's* `search_path`, and a caller who can create objects in a schema ahead of `public` on that path can shadow an unqualified identifier the function resolves. Every helper body in this family already schema-qualifies every table it touches (`public.<table>`), so today's exposure is zero — but the pin is the belt for the day a helper is copied without that discipline, and it costs nothing. `pg_catalog, public` (not `public` alone) additionally protects against a caller shadowing a *built-in* function or operator the body calls implicitly (casts, comparison operators) with one in `public`.
3. **`STABLE`, never `VOLATILE`**, unless the helper mutates (none of the eight do). A membership/role/hold-state read must be plan-cacheable within one statement and must not be assumed to see writes from the same statement.
4. **Owned by `setjoin_worker`** (`apply_worker_ownership()`, V118) — a `BYPASSRLS` pool identity — never by `setjoin_owner` (migration-loader identity, deliberately `NOBYPASSRLS`; an owner-owned DEFINER function does NOT bypass FORCE RLS post-flip, the exact trap the V114 §D AUTOPLAN comment records). `EXECUTE` is revoked from `PUBLIC` and re-granted only to `setjoin_app`/`setjoin_owner`/`setjoin_worker` — the helper's argument shape (`(id, user_id)` pairs the caller supplies) means an ungated `EXECUTE` grant would let any authenticated role probe membership on an arbitrary id, an enumeration oracle.
5. **Returns the role/fact, not a boolean gate decision.** Every helper below returns `text` (a role string) or a fact (`boolean`/`bigint`); the calling policy compares (`IS NOT NULL`, `= 'manager'`, `IN (...)`) — this keeps the RBAC ladder (`manager`/`editor`/`viewer`) expressible from ONE helper per table family instead of one boolean helper per permission level.

### The eight-row liveness-filter matrix

Every helper answers "is this fact live right now" differently, because "live" means something different to each consumer. This table is the canonical reference — a new helper (Pillar C) is reviewed against it, not against whichever prior helper happens to be open in an editor.

| # | Helper | Backing table | Liveness filter | Why that filter is correct for this consumer |
|---|--------|---------------|------------------|-----------------------------------------------|
| 1 | `drive_member_role` (V114 arm 1) | `drive_space_members` | none — row presence IS liveness | Membership rows are added/removed atomically by `drive_member_grant`/`drive_member_revoke`; there is no "left" state to filter, a row existing means currently a member. |
| 1b | `drive_member_role` (V120 arm 2 — chat-bound spaces) | `chat_channel_members` (via `drive_spaces.chat_channel_id`) | none — same reason as #4 | Derives Drive access live off chat membership (DES-009 D1); chat membership rows are likewise deleted on leave, so presence is the fact. |
| 1c | `drive_member_role` (V129 arm 3 — meeting-bound spaces) | `meeting_participants` (via `drive_spaces.meeting_id`) | `banned_at IS NULL`; **no** `left_at` filter | Deliberately different from arms 1/1b: DES-009's B2 extension makes recording access track **attendance**, not live meeting presence — a member who leaves mid-meeting (or after it ends, when `meeting_end` mass-stamps `left_at` for everyone) must keep recording access; only an explicit ban revokes it. |
| 2 | `drive_space_owner` | `drive_spaces.owner_user_id` | none — not a membership check | Returns a static column value; the RLS policies that call it separately guard its relevance with `chat_channel_id IS NULL AND meeting_id IS NULL` (DES-009 D3: the owner column grants nothing on a bound space). |
| 3 | `drive_has_admin_perm` | `admin_role_assignments`/`admin_role_groups` | `expires_at IS NULL OR expires_at > now()`, plus JIT eligibility (`eligible=false OR activated_until > now()`) | The admin-grant analog of `left_at`: a timed-out or not-yet-activated JIT assignment must not count as a live admin grant. |
| 4 | `chat_member_role` | `chat_channel_members` | none — row presence IS liveness | Same shape as #1: `chat_channel_members` has no `left_at`/`banned_at` column; leaving a channel `DELETE`s the row (there is no ban primitive at the channel-membership layer — A1 shipped no channel-level kick). |
| 5 | `meeting_member_role` | `meeting_participants` | `left_at IS NULL`; **no** `banned_at` filter | Serves LIVE in-meeting reads (`meetings`/`meeting_participants` RLS — "can this caller see the roster/meeting row right now"). See "the kicked-but-not-evicted edge" below for why the missing `banned_at` filter is accepted, not a gap. |
| 6 | `meeting_attendee_role` | `meeting_participants` (same table, historical read) | `banned_at IS NULL`; **no** `left_at` filter — the inverse of #5 | Serves POST-END recording/attendance reads. `meeting_end` mass-stamps `left_at` for every participant, so filtering on it would return zero rows for every meeting that has ended — the exact opposite of #5's need. Host/cohost count regardless of `joined_at` (their row is reducer-created at meeting creation); a plain participant counts only with a webhook-fed `joined_at` (D2's admission-vs-attendance line — being invited is not having attended). |
| 7 | `chat_hold_active` | `chat_channels.legal_hold` ∨ `chat_case_hold_channels`/`chat_case_holds` | `released_at IS NULL` (case-hold arm, V127) | Not a per-user membership helper — a per-channel boolean the destruction path (purge sweep, admin channel list, BZ194 trigger) and a member's own read must resolve identically (same DEFINER-under-FORCE-RLS reason as #1–#6: `chat_channels` has no UPDATE policy). Included in this family for sharing the identical recursion-dodge + pin rationale, not the membership shape. A released hold must not keep gating destruction, so `released_at IS NULL` is the liveness filter on the HOLD row rather than on a person. |
| 8 | `drive_user_can_write_regular` (V135, normalized 2026-07-16 — arch #A3) | `drive_spaces` (`classification='regular'`), delegating to `drive_member_role` per candidate space | none of its own — delegates entirely to row 1/1b/1c's liveness filters | Answers "is this user manager/editor of ANY regular (unbound) space" for the `drive_chunks_insert` 'g'-scope (global-dedup) policy arm. Originally shipped (V135) inlining all three `drive_member_role` arms verbatim, VOLATILE, EXECUTE-to-`setjoin_app`-only, because a nested STABLE-DEFINER call was believed to "silently return no rows" inside a WITH CHECK — see the postmortem below. Root-caused as a red herring and normalized to delegate + the standard recipe (STABLE, `apply_worker_ownership` trio). |

### Row 8's undiagnosed-workaround postmortem (arch #A3, 2026-07-16)

V135's inline comment claimed "a nested STABLE-DEFINER call, evaluated inside another DEFINER helper inside a plpgsql reducer's RLS WITH CHECK, silently returned no rows on the live gate even though the top-level call returned true." This was re-investigated with a throwaway probe (as `setjoin_app`, under FORCE RLS, exercising every claimed shape: a direct call, a WITH CHECK evaluated during a plain top-level INSERT, and the same INSERT wrapped in a separate invoker-rights PL/pgSQL function) — **the nested-DEFINER call works correctly in every one of those shapes.** It is a red herring, not a real PostgreSQL limitation.

The actual, reproducible failure is orthogonal to nesting entirely: **PostgreSQL's row-security implementation additionally requires the tentative new row of an `INSERT ... ON CONFLICT` (`DO NOTHING` or `DO UPDATE`) to satisfy the target table's SELECT policy**, regardless of whether an actual conflict occurs — an anti-oracle measure so `ON CONFLICT DO NOTHING` can't be used to probe the existence of a row the caller couldn't otherwise `SELECT`. `drive_chunks_read`'s SELECT policy requires a pre-existing `drive_upload_claims` row, which does not yet exist for a first-time chunk — exactly what `drive_chunk_register`'s real `INSERT ... ON CONFLICT (scope_key, sha256) DO NOTHING` statement does. Any chunk insert carrying that ON CONFLICT clause, run as a non-bypass role, fails this check independent of the INSERT policy's own logic. Proven live: temporarily making `drive_chunks_read`'s `USING` clause permissive (`true`), with **zero** change to the INSERT WITH CHECK policy or helper, makes the identical `ON CONFLICT` insert succeed.

Consequence: `drive_chunks_insert`'s WITH CHECK — and therefore this helper — is DEAD on both of `drive_chunks`' real writers today. `drive_chunk_register` is itself `SECURITY DEFINER` + worker-owned (runs as `setjoin_worker`, `BYPASSRLS` — bypasses RLS entirely, both the WITH CHECK and the ON-CONFLICT SELECT-policy check, regardless of caller role); `drive_preview_attach` is only ever invoked on the preview worker's own `BYPASSRLS` pool. The policy only matters as defense-in-depth for a future writer that runs as `setjoin_app` directly — and such a writer would still need to route around the ON-CONFLICT anti-oracle check above, independent of this function's shape. Delegating to `drive_member_role` (this ADR's row 8) is therefore a pure duplication removal with no behavior change on any live path, not a fix to an exploitable gap.

### The kicked-but-not-yet-evicted edge (meeting_member_role, row 5)

The security lens flagged that `meeting_member_role` does not filter `banned_at`, so a participant with `banned_at` set but `left_at` still `NULL` reads as a live member through every policy that calls it (`meetings_read`, `meeting_participants_scope`). This is a real, named, accepted window — not a silent gap:

- **DES-011** ("the SFU is a peripheral; reducers are the sole meeting authority") makes every kick/ban an **eviction call** (`RoomController.RemoveParticipant`), never a database-flag-only revocation. The moment `meeting_control` sets `banned_at`, it also fires the eviction — the participant's actual media session ends synchronously with that reducer call, not on the next webhook.
- `left_at` is stamped by the loss-tolerant `meeting_participant_event` ingest (the `participant_left` webhook, or the worker's periodic `ListRooms` reconcile if the webhook is dropped) — by design, asynchronously and best-effort (DES-011: "webhooks are facts, never authorization").
- So the window this predicate leaves open is: *Postgres still shows the banned user as a roster/meeting-metadata reader* for the sub-second-to-few-second gap between the ban and the webhook/reconcile closing `left_at` — **not** that they retain any media access, which DES-011's eviction call already closed synchronously. A banned-but-not-yet-`left_at` user re-reading `GET /meet/{id}` during that window sees the meeting still exists and the roster as it stood; they cannot rejoin the room (the mint path is gated separately) and cannot receive further media.
- **Decision: do not add a `banned_at` filter to `meeting_member_role`.** Doing so would make a banned user's client-side polling (which is how the client currently learns "you were removed" — see `mailserver/internal/meet/AGENTS.md`) 403 mid-transition instead of returning a coherent "you're still nominally in this stale roster read" that the eviction has already made harmless. If a future finding shows this read genuinely leaks something beyond stale metadata, fix it as a `banned_at` filter addition with its own migration and its own regression test — not folded into this hardening-only pass.

## Consequences

- One canonical reference for the recipe: a new scope helper (Pillar C, federation) is written by copying this ADR's five-point checklist and adding a row to the liveness-filter table, not by finding "the newest-looking" prior helper and imitating whatever it happened to do.
- The `search_path` pin is now uniform across all eight helpers (V133 for the original seven; row 8 shipped pinned from the start) — a hardening no-op today (see Context), removing the one place a future helper could copy the weaker form with a plausible-looking precedent to point at.
- The liveness-filter matrix makes the row-5/row-6 asymmetry (`meeting_member_role` vs `meeting_attendee_role` filtering opposite columns on the *same* table) a documented, intentional design fact instead of something a future reader has to reverse-engineer from two migrations three weeks apart.
- Cost: this ADR does not reduce the number of helpers (eight stays eight, soon nine) — it is a documentation and pin-normalization pass, not a consolidation. A shared-helper-factory or macro was considered and rejected below; the eight bodies are genuinely different queries over different tables and a generator would be one more layer to keep in sync with the table it's supposed to explain.

## Alternatives rejected

- **A single generic `scope_role(table_name, id_col, ...)` helper:** would need dynamic SQL (`EXECUTE format(...)`) inside a `SECURITY DEFINER STABLE` function, defeating plan caching and reopening a SQL-injection-shaped surface for a value that today is a fixed, reviewed literal per call site. The eight bodies are short (3–6 lines) and genuinely differ in their liveness filter — the matrix above is the shared abstraction; the SQL itself should not be.
- **Fixing the `meeting_member_role`/`banned_at` "gap" by adding the filter:** rejected for now (see "the kicked-but-not-yet-evicted edge" above) — the actual authority (SFU eviction) is already synchronous with the ban; the Postgres-side read lag is cosmetic, and closing it would require re-verifying every caller of `meeting_member_role` doesn't depend on a banned user still resolving a roster read during the eviction-to-webhook window. Left as a documented, deliberate known-edge.
- **Loosening the `search_path` pin requirement for read-only `STABLE` helpers on the theory that "the drive family is already fully schema-qualified so it doesn't matter":** rejected — the whole point of the pin is that it protects the NEXT helper someone writes without checking whether its body happens to be fully qualified, not the current eight.
