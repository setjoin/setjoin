# Storage HA, Backup & Disaster Recovery — Design Spec

> **Target:** Prism Mailserver, Phase 37 extension. Blob storage HA + multi-provider backup + restore wizards.

**Goal:** Replace the single-node SeaweedFS SPOF with a tiered storage architecture: on-prem HA replicating SeaweedFS volumes across 3 nodes (enterprise), independent S3/OSS/B2 backup at any scale (with manifest-based incrementals and GFS retention), and wizards for first-boot disaster recovery, partial restore, integrity verification, and scale-up/scale-down.

**Architecture:** Three independent layers — (1) Storage topology (single or 3-node Raft SeaweedFS), (2) Backup engine (manifest-based, S3/OSS/B2 drivers, incremental with merge), (3) Restore engine (first-boot wizard, admin partial restore, integrity check). All three share a common Driver interface (`PutObject/GetObject/DeleteObject/ListObjects`). Aliyun OSS uses `aliyun-oss-go-sdk-v2`; everything else uses `aws-sdk-go-v2` with endpoint configuration.

## 1. Storage Topology

### 1.1 Single Node (Current)

Unchanged from today: one SeaweedFS container running master + volume + filer + S3 gateway in one process. Volume path configurable via env var. S3 backup available at this tier.

### 1.2 3-Node HA (Enterprise)

Three servers, each running:

```
server<N>:
  weed master   -mdir=/data/master -peers=server1:9333,server2:9333,server3:9333
  weed volume   -dir=/data/vol -mserver=server1:9333 -rack=rack<N>
  weed filer    -master=server1:9333,server2:9333,server3:9333 -s3
```

- **Masters** form Raft quorum (tolerates 1 failure, requires 2/3 healthy)
- **Volumes** use replication mode `001` (async replica to one peer). Configurable to `002` (sync to two peers) for zero-data-loss deployments.
- **Filer** embeds its LevelDB/RocksDB metadata in the Raft log — filer state is HA.
- **S3 API** served by any filer node. Gateway connects via comma-separated endpoint list.
- **Write latency:** ~2-5ms (same-rack async). Reads load-balanced across replicas.
- **Data loss window on failover:** in-flight writes (< 1 second for async, 0 for sync).
- **Cost:** 3 servers, 2-3x raw storage depending on replication factor.

### 1.3 Scale Up/Down

**1 → 3 (Scale Up):** Wizard SSHes into new nodes, installs SeaweedFS, configures Raft peers, replicates existing volumes, updates gateway endpoint, runs failover test.

**3 → 1 (Scale Down):** Gateway enters write-drain mode (rejects new blob uploads with `503 Retry-After`), final backup runs, volumes consolidated to node 1 via `weed shell volume.move`, nodes 2/3 removed from Raft, replication set to 000, gateway S3 endpoint reverted to single node, drain mode released. Reads unaffected throughout.

### 1.4 Configurable Volume Path

Admin sets `SEAWEEDFS_VOLUME_PATH` (default `/data`) during deploy or in the wizard. The path is the filesystem directory where SeaweedFS stores its master and volume data.

### 1.5 Deploy Philosophy

One deploy path, not two. SeaweedFS is a single Go binary with no runtime dependencies — no need for container isolation.

- **Production:** systemd units generated by the auto-deploy wizard. `seaweedfs.service` runs the `weed` binary directly. Same as the gateway (`mailserver.service`) and PostgreSQL (`postgresql.service`). Systemd handles restarts, logging (journald), and resource limits.
- **Development:** `dev.sh` starts PostgreSQL + SeaweedFS + gateway as background processes on the developer's machine. No Dockerfile, no compose.yml, no bridge networking. Uses the same binaries and config format as production.
- **Upgrades:** Stop service → replace binary → start service. Identical for dev and prod.
- **Docs:** CLAUDE.md and architecture.md use systemd-only deployment language.

The wizard generates systemd units for all three nodes:

```ini
[Unit]
Description=SeaweedFS Storage Node
After=network.target

[Service]
Type=simple
User=mail
ExecStart=/usr/local/bin/weed server \
  -dir=/data/seaweedfs \
  -master.peers=node1:9333,node2:9333,node3:9333 \
  -filer -s3 -s3.port=9000 \
  -volume.max=100
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

## 2. Backup Engine

### 2.1 Driver Interface

```go
type Driver interface {
    PutObject(ctx context.Context, key string, data io.Reader, size int64) error
    GetObject(ctx context.Context, key string) (io.ReadCloser, error)
    DeleteObject(ctx context.Context, key string) error
    ListObjects(ctx context.Context, prefix string) ([]ObjectInfo, error)
    HeadObject(ctx context.Context, key string) (*ObjectInfo, error)
    EnsureBucket(ctx context.Context) error
    BucketExists(ctx context.Context) (bool, error)
    ProviderName() string
    Endpoint() string
}
```

Two implementations:
- **S3 driver** (`aws-sdk-go-v2`): AWS S3, Backblaze B2, Cloudflare R2, Wasabi, MinIO, SeaweedFS, any S3-compatible
- **OSS driver** (`aliyun-oss-go-sdk-v2`): Aliyun OSS with its native auth signature

Provider selection is UX-only presets — UI shows "Amazon S3", "Backblaze B2", "Aliyun OSS", "Other S3-compatible", all mapping to the same two drivers with different endpoints.

### 2.2 Backup Artifacts

Each backup run produces (timestamped together):

| Artifact | Content | Format |
|---|---|---|
| `config.json` | `system_config` + features + domains + connectors | JSON |
| `pg_dump.sql.gz` | Full PostgreSQL dump (uses `--snapshot` for consistency with config + blob snapshot) | gzipped SQL |
| `blob-manifest.json` | `[{"hash":"abc123","size":2456789}, ...]` for all blobs with `ref_count > 0` | JSON array |
| `backup-manifest.json` | Index of above three + timestamp + item counts + total sizes | JSON |

Config, pg_dump, and blob snapshot share a PostgreSQL transaction for point-in-time consistency.

### 2.3 Incremental Blob Backup

Only the blob manifest is incremental. Config and pg_dump are full each run (config is tiny; pg_dump uses native WAL streaming via Phase 37).

```
backup bucket:
  blobs/
    abc123def456...          ← actual blob content, SHA-256 keyed
    ...
  manifests/
    full-001.json            ← initial full manifest (N hashes)
    incr-001.json            ← new hashes since full-001
    incr-002.json            ← new hashes since incr-001
    ...
    backup-manifest-001.json ← index of above
```

**Blob upload is idempotent:** `HEAD` check on backup S3 before `PUT`. Same SHA-256 = same content = skip.

**Manifest merge** is a pure in-memory operation (merge SHA-256 sets, dedup is free). When merge condition triggers, a new synthetic full manifest is written and the old chain deleted. No data movement.

### 2.4 Retention Policies

All configurable, all using the same manifest-merge engine:

| Policy | Config | Behavior |
|---|---|---|
| Merge after N | `merge_after_n: 10` | After 10 incrementals, merge into synthetic full. Keep last `keep_fulls` fulls. |
| Time-based merge | `merge_at: "0 3 * * SUN"` | Merge incrementals into full every Sunday 03:00 |
| Keep N days | `keep_days: 30` | Incrementals older than 30 days are merged into the current full |
| GFS | `gfs: "7d4w12m"` | 7 daily incrementals + 4 synthetic weekly fulls + 12 monthly fulls |

No downside to offering all four — manifest merge costs ~15ms for 100K hashes and no data transfer.

### 2.5 Scheduling

pg_cron job inserts into `backup_runs` table with `status='pending'`. LISTEN/NOTIFY wakes the Go backup worker. Admin can trigger ad-hoc from the System page. Schedules: hourly, daily, weekly, or custom cron.

### 2.6 Consistency

Config export + blob snapshot share a PostgreSQL transaction. pg_dump uses `--snapshot` to share the same snapshot. If the backup process dies, the incomplete `backup-manifest.json` is never committed — next run picks up from last committed manifest.

## 3. Restore Engine

### 3.1 Mode Detection

Gateway startup determines mode from database state:

```go
func detectMode(pool) string {
    userCount := pool.QueryRow("SELECT COUNT(*) FROM users")
    if userCount == 0 { return "setup" }
    pending := pool.QueryRow("SELECT COUNT(*) FROM restore_jobs WHERE status IN ('pending','running')")
    if pending > 0 { return "restore_resume" }
    return "normal"
}
```

Setup mode → serves setup wizard on same LISTEN_ADDR as normal operation (typically `:443` with TLS). After restore completes, gateway transitions to normal mode — same address, login page replaces wizard.

### 3.2 First-Boot Restore Wizard

Setup page has two paths: **Fresh Install** (create domain + admin user) and **Restore from Backup**.

The restore wizard:

```
Step 1: Backup Provider
  - Provider: [Amazon S3 | Backblaze B2 | Aliyun OSS | Other S3-compatible ▼]
  - Endpoint, Region, Bucket, Access Key, Secret Key

Step 2: Storage Path
  - SeaweedFS volume path: [________________] (default: /data)
  - If restoring to a server that has the old SeaweedFS volume mounted
    at a custom path (e.g., /mnt/old-seaweedfs-data), point to it here
  - Blob restore will HEAD-check each hash before download — existing
    blobs at this path are automatically used, saving transfer time

Step 3: Pre-flight check
  - Downloads backup-manifest.json (small, few KB)
  - Shows preview: DB size, blob count, blob total, user count, domain count
  - Checks available space on PostgreSQL, SeaweedFS volume path, /tmp
  - Shows warnings if insufficient space (admin can override)

Step 4: Execute
  - Progress bar with per-phase status
  - Order: config → pg_dump → pg_restore → blob restore → re-index → verify → ready
  - Each blob checks existence before download (SHA-256 dedup — handles existing volumes)

Step 5: Complete
  - Redirect to login page
```

Restore types from the wizard:
- **Full Restore:** config + pg_dump + blobs — complete platform recovery
- **Config Only:** just `config.json` → upsert into `system_config` → restart → login

### 3.3 Admin Portal Restore

Available from `/admin/system` → "Restore" tab:

| Restore Type | Scope | Conflict |
|---|---|---|
| Mail + Attachments | All mailboxes or specific mailbox | Skip / Overwrite / Merge |
| Mail only | All mailboxes or specific | Skip / Overwrite / Merge |
| Attachments only | All blobs or specific hashes | — |
| Config only | system_config rows | Skip / Overwrite |

### 3.4 Partial Restore (Integrity Check)

Admin runs "Verify Integrity" from `/admin/system` → "Restore":

```
1. SELECT sha256 FROM blobs WHERE ref_count > 0
2. HEAD request to primary SeaweedFS for each hash
3. Collect missing hashes
4. Show gap report: total blobs, present, missing, sizes
5. [Restore Missing Blobs] → fetches only missing hashes from backup
```

Handles: deleted blobs, disk corruption, incomplete migration, partial restore resumption.

### 3.5 Pre-flight Space Check

Runs before any data is written. Checks:

| Resource | How checked | Threshold |
|---|---|---|
| PostgreSQL free | `pg_database_size` vs `df` on data directory | 2x uncompressed dump size |
| SeaweedFS free | `weed shell volume.fsck` or `df` on volume path | 2x blob manifest total |
| /tmp free | `df /tmp` | 1x uncompressed dump size |

Warnings shown if any threshold not met. **Admin can override** and proceed with partial restore — missing items appear in the integrity report and can be backfilled later after expanding storage.

### 3.6 Existing Volume Detection

Blob restore uses `HEAD` on primary SeaweedFS before each download. If the blob already exists (same SHA-256 = same content), skip. This automatically handles:
- Old SeaweedFS volume from same physical disk reused on new server
- Partial restore resumption (crashed mid-restore, gateway restarts in `restore_resume` mode)
- Deduplication across restore sources

## 4. Auto-Deploy Wizards

### 4.1 Deploy Storage HA (1 → 3 Nodes)

Extension of the PostgreSQL HA wizard (Phase 37). Adds SeaweedFS configuration:

1. Enter node 2 and 3 IPs + SSH credentials
2. Configure volume paths per node:
   - Node 1: [/data        ▼] (current, detected from running instance)
   - Node 2: [/data        ] (default, or mount a dedicated disk)
   - Node 3: [/data        ] (default, or mount a dedicated disk)
3. SSH into both, download SeaweedFS binary, create data directories at configured paths
4. Configure Raft masters on all three with peer list
5. Start volume servers with replication `001`
6. Move existing volumes from node 1 to replicated layout
7. Update gateway `S3_ENDPOINT` to multi-node
8. Run failover test
9. Show status: `Storage HA Active — 3 nodes, replication 001`

### 4.2 Scale Down (3 → 1 Nodes)

1. Admin confirms: all volumes consolidated to node 1
2. Gateway write-drain mode (503 on new blob uploads, reads normal)
3. Final incremental backup runs
4. Volumes verified replicated, then consolidated to node 1
5. Nodes 2/3 removed from Raft peers
6. Replication set to 000
7. Gateway S3 endpoint → single node
8. Drain mode released
9. Status: `Single Node — No Storage HA`

### 4.3 Deploy on Fresh 3-Node Cluster

Same as 4.1, but starting from clean install. No volume migration needed. Uses the same first-boot flow as Section 3.2 — admin chooses "Fresh Install" then runs the HA wizard from the admin portal.
