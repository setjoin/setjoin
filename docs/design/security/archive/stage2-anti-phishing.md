# Advanced Anti-Phishing / Impersonation Protection — Design Spec

> **Roadmap:** Stage 2.4 — Enterprise Deal-Qualifier | **Effort:** ~4 weeks | **Status:** Draft

## Goal

Detect impersonation attacks in inbound email by combining three signals: display-name
spoofing (fuzzy match against internal user names), lookalike domain detection (homoglyph
analysis of the sender domain), and mailbox intelligence (contact graph to flag novel
senders using names that match known contacts). Gmail includes this in all editions; EXO
gates it behind Defender P1. We match Gmail's "included in base" model.

## Architecture

Three independent detectors, evaluated during SMTP inbound delivery after SPF/DKIM/DMARC
and before JMAP commit. Each detector returns a verdict (none / warn / reject) and a set
of evidence symbols. The most severe verdict wins. Verdicts are recorded as a header
(`X-AntiPhish`) and optionally appended to the message body as a safety banner.

1. **Display-name spoofing.** Parse the `From` header. Extract the display name (the
   human-readable part before the angle-addr). Compare against the organization's user
   display-name list via `pg_trgm` similarity with a configurable threshold (default
   0.85). A display name of "Jane Doe (CEO)" matching an internal user "Jane Doe" at
   0.95 similarity triggers a warn. An exact match from an external domain triggers
   reject. Internal users are cached in memory with a 5-minute TTL.

2. **Lookalike domain detection.** Extract the sender domain from `Return-Path` (or
   `From` as fallback). Apply homoglyph normalization — map Unicode confusables to
   ASCII (e.g., Cyrillic 'о' → Latin 'o', Greek 'ν' → Latin 'v'). Compare the
   normalized domain against a list of protected domains (own domains + configurable
   list of common targets like microsoft.com, google.com, paypal.com). A normalized
   match against a protected domain where the original differs indicates a homoglyph
   attack — reject immediately. Also flag high-similarity domains (Levenshtein distance
   ≤ 2 against a protected domain) as warn. Use the Unicode `confusables` data set
   (UTR #39) via a compiled-in table generated by `scripts/gen-confusables.go`.

3. **Mailbox-intelligence contact graph.** Build a per-mailbox contact graph from the
   `message_recipients` and `messages` tables: for each recipient, track every sender
   (email + display name) that has previously delivered mail to them. On inbound
   delivery, for each recipient: if the sender address is novel (never seen by this
   recipient) but the display name matches a known contact at a *different* email
   address, flag as impersonation (warn). Contact graph is queried from PG with a
   single indexed query per recipient; a negative cache (`seen_senders` bloom filter
   in memory) avoids re-querying repeat senders.

## Key Design Decisions

- **Verdict precedence: reject > warn > none.** Lookalike domain matches are always
  reject (homoglyph attacks have no legitimate use). Display-name spoofing uses warn
  for fuzzy matches and reject for exact matches from external domains. Contact graph
  impersonation uses warn only — never reject, to avoid false positives from shared
  names at different companies.
- **pg_trgm for fuzzy display-name matching.** PostgreSQL's built-in trigram module
  gives us similarity scores without an external dependency. The threshold is
  configurable per domain.
- **Unicode confusables table, not an NLP model.** UTR #39 confusables are
  well-maintained by the Unicode Consortium, cover all known homoglyph attacks, and
  require no ML inference. The table is compiled into Go at build time via `go:generate`
  — no runtime dependency.
- **Contact graph as materialized view, not real-time join.** The contact graph query
  against `messages` + `message_recipients` would be expensive per inbound delivery.
  A materialized view refreshed every 5 minutes by pg_cron keeps lookups fast (index
  scan on `mailbox_id + sender_email`). The 5-minute staleness window is acceptable:
  a contact established 5 minutes ago is unlikely to be impersonated immediately.
- **Feature toggles per detector.** `feature.antiphish_display_name`,
  `feature.antiphish_lookalike`, `feature.antiphish_contact_graph`. All default true.
  Per-domain overrides for verdict action (warn/reject/none).

## Dependencies

- **PostgreSQL `pg_trgm` extension** — already available (used for search in Phase 9 calendar)
- **pg_cron** — already deployed (used for orphan blob cleanup)
- **Unicode confusables.txt** — downloaded at build time, no runtime dependency
- **SMTP inbound pipeline** — DMARC already evaluated before our hook point; we run after DMARC but before ClamAV (phishing detection is cheaper than AV)
- **Competitive context:** Gmail includes user/domain impersonation detection in all
  editions. EXO gates it behind Microsoft Defender for Office 365 Plan 1 (P1). Zimbra,
  NetEase, Tencent, and Axigen have no documented impersonation protection. We are the
  only on-premise platform offering it built-in at no per-seat cost.

## Non-goals

- Phishing detection based on body content (URL/link analysis is Stage 1.3 Link
  Protection; attachment analysis is Stage 1.4 Sandbox)
- DMARC aggregate reporting (already implemented in Phase 7; BIMI is separate)
- Sender authentication via VMC/BIMI (BIMI is a future item)
- User-specific safe-sender override (V1 uses admin-configured domain allowlists only;
  per-user allowlists deferred)
