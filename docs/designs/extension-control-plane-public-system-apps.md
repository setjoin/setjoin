## Decision

Setjoin will design a complete layered extension platform around an independent
**Extension Control Plane**. Contribution type, execution runtime, and placement
are separate axes. Trusted Core is a separate internal mechanism that may share
registry metadata; it is not a public profile.

Mail, Drive, Calendar, Contacts, and Tasks become **protected first-party system
apps** with public contracts. They are logically modular and expose stable APIs,
commands, events, and contribution points, but their authoritative data and
reducers are not ordinary uninstallable third-party components. Chat, Meet,
Office, and similar surfaces may be optional first-party apps with replaceable
providers and explicitly governed data removal.

This design builds on
`retired-docs:superpowers/specs/2026-08-24-app-marketplace-plugin-platform-design.md`.
Its restricted WebApp profile remains the simplest developer path.

## Problem

Setjoin already has provider-neutral Office boundaries, a restricted container
application design, reducer-authoritative lifecycle state, webhook outboxes,
administrator permissions, source profiles, and signed-artifact plans. These do
not yet form one durable public platform for extending Mail, Drive, Calendar,
Chat, Meet, Office, AI, or administrative workflows.

Exposing PostgreSQL extensions, internal tables, arbitrary hooks, or in-process
Go/JavaScript modules would break tenant isolation, reducer authority, upgrade
compatibility, and the on-premise support boundary. Setjoin needs PostgreSQL-like
stability and discoverability with Kubernetes-like isolation and reconciliation.

## Lessons from successful ecosystems

- **PostgreSQL 18:** catalog-driven typed extension points, packaged versions and
  dependencies are worth adopting. Dynamic libraries, WAL, shared memory,
  `shared_preload_libraries`, extension SQL and database credentials are not
  community interfaces; PostgreSQL's own documentation warns of superuser and
  search-path escalation hazards.
- **VS Code:** contribution points, manifests, scaffolding, lazy activation,
  multiple extension hosts and workspace trust reduce developer friction.
  Setjoin uses stronger isolation because a local VS Code extension host retains
  broad operating-system authority.
- **Kubernetes:** desired-state resources plus external reconcilers extend the
  platform without modifying its control plane. Central authentication,
  authorization and admission remain authoritative. This is Setjoin's lifecycle model.
- **Grafana:** typed plugin classes, scaffolding, signatures, compatibility
  metadata and load-time validation are the right marketplace supply-chain model.
- **Backstage:** frontend/backend separation, network-only plugin communication
  and centralized permission decisions fit Setjoin's capability broker.
- **Home Assistant:** a small manifest, generated configuration UI, dependencies,
  code ownership and visible quality tiers enable broad participation.
- **Microsoft Teams and Feishu:** marketplace review, publisher identity,
  tenant availability and resource/data consent are separate gates. Teams uses
  app-centric assignment plus resource-specific consent; Feishu separates
  custom and store apps and applies platform plus tenant review to store-app
  permissions, with additional scrutiny for advanced scopes. Setjoin adopts
  these layered gates without treating a signature or listing as authorization.
- **WordPress/Jenkins:** easy hooks, public directories and core use of extension
  points grow ecosystems, but privileged in-process execution and very wide
  compatibility surfaces create lasting security and maintenance costs.

## PostgreSQL-to-Setjoin mapping

| PostgreSQL | Setjoin | Boundary |

| Trusted extension | Trusted Core internal mechanism | Setjoin/vendor controlled and separately reviewed |

## Architecture

```text
official / curated / verified / community / private catalogs
                         |
               signed snapshot resolver
                         v
                Extension Control Plane
       +-----------------+------------------+
       |                 |                  |
 registry/compat   lifecycle reconciler   trust/supply chain
       +-----------------+------------------+
                         v
                  Capability Broker
                         |
             Command + Query + Event Gateway
                         |
 Contributions: WebApp | Provider | UI | Action | Event | Job | Client Surface
                         |
 Runtimes: Remote HTTPS | managed OCI | WASI | desktop helper | mobile bundled
                         |
        protected public system-app contracts
                         |
       Mail | Drive | Calendar | Contacts | Tasks
                         |
              reducer/RLS/audit authority

Trusted Core is a separate closed internal lane beside the public architecture.
```

The control plane owns extension identity, namespace, manifest schema, artifact
digests, signatures, dependencies, compatibility, desired state, installation
generation, grants, lifecycle, health projections, catalog trust, and audit.
Reducers own mutations and grants. Go adapters perform bounded effects and report
observations tied to an expected operation, digest, generation, and revision.

## Terminology and state invariants

- **Extension:** immutable publisher-qualified identity.
- **Release:** immutable manifest and artifact-digest set for one version.
- **Installation:** one extension attached to one deployment, tenant, group, or user scope.
- **Desired state:** reducer-owned presence, release, availability, settings and grants.
- **Revision:** monotonically increasing optimistic-concurrency value.
- **Operation:** durable attempt to reconcile one revision; one mutating owner at a time.
- **Generation:** monotonically fences runtime authority on activation or revocation.
- **Grant:** reducer-owned authorization for one typed capability and bounded scope.
- **Health:** executor observation only; it never grants authority.

Stale operation observations cannot activate, restore grants, or remove a newer generation.

## Installation scopes and Capability Broker

Here `tenant` names the existing organization/account-isolation scope within the
single-organization deployment model; email domains are not tenants. This design
does not introduce multi-organization hosting or a new tenant schema. CP0 must map
wire scope fields to the existing authenticated scope before implementation.

Deployment scope requires a platform administrator; tenant scope requires a
tenant app administrator; group scope additionally requires a group owner or
delegate; user scope may be self-installed only from administrator-allowed
catalogs within a pre-approved capability envelope. User consent cannot grant
tenant data, administrative actions, new egress, or a stronger runtime. Narrower
scopes inherit parent denials and never broaden parent grants.

Every request crosses one broker. A capability is a typed tuple:

```text
(installation, generation, actor, tenant, capability, action,
 resource scope, data class, audience, expiry, request id)
```

The broker revalidates current grants and resource authority. Short-lived tokens
cannot survive generation fencing. Permission expansion, runtime-class change,
new egress, publisher change, or signature downgrade requires renewed approval.
There is no public `Invoke(plugin, action, JSON)` escape hatch.

The broker is one logical authority, not one network process. Reducers own grants
and generations. Authorization decisions are not positively cached across
requests: every request compares its token generation with the strongly current
reducer-owned fence before data access. Read-only performance may use cached
domain projections only after this fence check. Loss of authoritative fence
connectivity fails closed.

### Capability eligibility and approval tiers

Publisher verification, artifact signing, catalog review, tenant approval and a
runtime grant prove different facts. None implies another. Admission therefore
passes three independent gates: the catalog decides whether a release may request
a capability; the tenant administrator decides whether and at what resource/data
scope to grant it; the broker enforces that grant on every operation. A release
that expands permissions, data scope, egress or runtime authority requires fresh
approval. While approval is pending, the proposed release receives no new authority;
the previously approved, non-revoked generation may retain only its previously
approved grants. Revocation fences that generation immediately. This is the same
rule as the lifecycle section, not permission to keep an unapproved broader route.

Capabilities are classified by consequence rather than by whether the app is
free, commercial, community or first-party:

1. **Basic:** isolated UI contributions, app-owned settings/data and bounded
   health/support surfaces that cannot read Setjoin business data or reach an
   undeclared network destination. Automated catalog checks plus an existing
   administrator-approved envelope may admit these.
2. **Sensitive:** scoped Mail/Drive/Calendar/Contacts/Tasks reads or writes,
   event subscriptions, background jobs, message sending, external egress and
   similar access to tenant data. These require declared purpose and data class,
   catalog review, explicit tenant-admin approval and a least-privilege resource
   scope. User consent alone cannot grant them.
3. **Authority-affecting:** mail hold/release, identity or authentication policy,
   storage-provider authority, tenant-wide export, retention/legal hold, security
   policy or global administration. Before GA these are limited to first-party
   code or a specifically certified Provider profile.

Authority-affecting capabilities are not permanently private or Enterprise-only.
They may become available to qualified community apps after the public contract,
isolation, generation fencing, revocation, audit, conformance suite and named
certification profile are executable. Promotion is per capability and contract
major, not a blanket trusted-publisher bypass. A verified or certified badge is
displayed separately from the exact capabilities a tenant granted.

## Contributions, runtimes and placement

Contribution types are WebApp, Provider, UI, Action, Event Consumer, Job,
Import/Export, and Client Surface. Execution runtimes are Remote HTTPS, managed
OCI, WASI, desktop helper, and declarative/bundled mobile integration. Provider
and Job are contribution types, not runtimes. Mobile never downloads arbitrary
executable code: it uses declarative contributions, code bundled with a signed
app release, or a separately installed companion app.

### Runtime classes

| Profile | Purpose | Isolation and availability |
|---|---|---|
| Remote | Vendor/customer-hosted integrations | HTTPS, audience tokens, origin/SSRF/egress policy |
| Managed OCI | Substantial self-hosted services and WebApps | Rootless, read-only root, mediated volumes/secrets and bounded network/resources |
| WASI | Small transforms and policies | No ambient authority; bounded host calls/time/memory/fuel |
| Desktop helper | Device-local capability unavailable to web | Signed subprocess/WASI, admin/MDM and device-local grants |
| Mobile declarative/bundled | Mobile actions and surfaces | No downloaded code; app-store-signed bundle or companion app |

Runtime placement is independent of contribution type. An Office Provider may be
Remote or managed OCI; a transform may use WASI; an app may combine WebApp and UI
without automatically receiving Setjoin data authority.

## App classification

| Class | Members | Replacement policy |
|---|---|---|
| Kernel | Identity, tenant, broker, audit, keys, extension control | Not replaceable |
| Protected system apps | Mail, Drive, Calendar, Contacts, Tasks | Public API and replaceable UI/providers; authority not ordinarily removable |
| Optional first-party apps | Chat, Meet, Office, Whiteboard, Forms | Disableable; provider replaceable; governed export/removal |
| Providers | Office, AI, search, ASR, antivirus, reputation, migration, eligible storage | Qualified and replaceable |
| Community apps | CRM, approval, automation, reporting and workflows | Installable/removable under grants |

Logical boundary, API boundary, and process boundary are separate decisions.
Every domain should reach the first two. Physical service separation occurs only
for scaling, fault isolation, licensing, or runtime needs. This prevents a
distributed monolith.

Each substantial module also declares startup-only, drain/restart or qualified
live-switch behavior under CP0. These are lifecycle classifications, not new
permissions or existing manifest fields. A protected module can use the same
interface discipline without being publicly replaceable. Existing atomic reducers
spanning domains remain atomic; module separation must not replace them with
event choreography merely to satisfy the plugin metaphor.

### Mail

Mail becomes a protected system app with JMAP plus a Setjoin Mail Extension API.
SMTP, IMAP, JMAP, delivery transactions, mailbox ownership, retention, legal
hold, journaling and authoritative reducers remain protected. Third parties may
provide alternative clients, UI contributions, spam/malware/DLP/classification
providers, AI summaries, routing, workflow actions, archive exports, migration,
reporting and normalized event consumers.

A mail contribution receives no raw mailbox/database access. Each command is
reauthorized against the actor and exact message, thread, mailbox or admin scope.

### Drive and Calendar

Drive exposes file/version/branch/preview/action contributions while preserving
immutable versions, ACLs and content authority. Calendar exposes scheduling,
availability, conferencing and resource-booking contributions while preserving
attendee privacy and reducer-owned conflict decisions. Cross-app workflows use
versioned commands and events, never shared tables.

Contacts preserves ownership, visibility and anti-enumeration boundaries; Tasks
preserves ownership, ACL, audit, assignment and notification decisions. E3 covers
all five protected system apps. Mail, Drive and Calendar are the first reference
contracts; Contacts and Tasks remain experimental until their contract suites pass.

## Public contracts

Each domain publishes four surfaces:

1. **Queries:** authorized projections and opaque cursors.
2. **Commands:** intent with idempotency keys and durable receipts.
3. **Events:** committed domain facts after the reducer transaction.
4. **Contributions:** UI, action, provider, automation, import/export or job hooks.

Events such as `mail.message.committed.v1` and
`drive.version.accepted.v1` come from transactional outboxes. Plugins never
consume WAL, internal table names, raw `LISTEN/NOTIFY`, or request-owned tenant IDs.
Cross-app atomic changes remain inside owning or orchestration reducers; events
do not simulate distributed transactions.

### Event delivery

The outbox records committed events with stable IDs, schema version, tenant,
subject and aggregate/partition key. Delivery is at-least-once. Consumers
acknowledge offsets and deduplicate event IDs. Ordering is guaranteed only within
the documented aggregate key, never globally. Bounded retries end in a
tenant-visible dead-letter state with reasoned replay. Retention and replay age
are policy-controlled. Slow consumers cannot retain WAL or block reducer commits;
backpressure pauses only their subscription.

## UI model

The platform defines slots such as navigation item, app page, entity card,
inspector tab, compose action, file action, message action, meeting panel and
admin settings. Simple actions are declarative. Rich surfaces run on isolated
origins or sandboxed iframes with a versioned message protocol. Community code
cannot inject JavaScript, CSS, Svelte modules, or commands into the Setjoin shell.

## Manifest, catalogs and packaging

The closed, versioned manifest contains identity, publisher, release,
compatibility, artifacts, execution runtimes, contributions, requested capabilities,
data classes, egress, lifecycle profile, resources, support, license and
migration/export declarations.

It cannot contain shell commands, SQL, host paths, Docker socket access, raw
proxy configuration, arbitrary environment interpolation, unbounded egress, or
executable install hooks. Artifacts are digest-pinned. Catalog inclusion,
publisher verification, signature, scan, human review and runtime health remain
separate displayed facts. Future offline `.sjapp` packages use the same manifest,
signatures and digests; offline packaging does not itself require a license.

Typed configuration distinguishes public values, generated values, secret
references, credentials and storage claims. Secrets live in Setjoin's secret
authority, are delivered only to the expected runtime/generation, never appear
in projections, and rotate through typed lifecycle operations. Managed volumes
use named storage classes, tenant quotas, backup policy and container-internal
mount targets; host paths remain forbidden.

Catalog classes state origin, not safety: official is shipped by Setjoin;
curated has a named review scope/date; verified proves publisher namespace;
community is unreviewed; private is signed by a customer root. Admission
separately evaluates signature, digest, provenance, scan, review, capabilities,
runtime, egress and compatibility.

Before public community submission, first-party releases dogfood a Git-provider-
neutral pull-request and release workflow, with GitHub as the initial hosted
adapter. CI validates the closed manifest and artifacts; approval produces an
immutable, platform-signed catalog record. Developer and contributor accounts do
not receive long-lived signing keys. The Registry authorizes the Publisher and
release actor and performs platform-managed signing; advanced publishers may add
their own signature as a second attestation. Local development may remain
unsigned only in an explicit constrained developer mode.

At initial ecosystem launch, community submission, automated validation and the
basic platform signature are free. There is no paid listing, paid verification,
manual-review product, certification tier, priority queue, official recommendation
or trademark program in the initial scope. A basic signature proves artifact and
catalog-record integrity only; it is not a security review, quality endorsement or
support promise. Community listings remain visibly unreviewed. Pricing and human
review return as a new product decision only after concrete developer, customer or
partner demand exists; this design does not pre-allocate implementation seams that
make the free path more complex.

The free unreviewed catalog still has a platform security-response duty. For a
validated vulnerable or malicious release, Setjoin publishes a signed advisory with
affected identities, versions and digests, blocks new installation and upgrade to
revoked digests, and shows existing administrators a persistent warning with a fixed
release or explicit disable/removal guidance. Catalog revocation does not silently
stop, uninstall or delete an already running customer application. Automatic runtime
fencing requires a separately approved Emergency Security Mitigation policy and its
stronger signing, scope, expiry, rollback, audit and operator-control gates. A missing
paid review relationship never suppresses a known security notice.

Harbor is a future controlled OCI/artifact mirror when package volume,
replication or private-registry needs justify it. Artifact Hub is a later
catalog/organization/search reference or reuse candidate only after the ecosystem
has material scale. Neither is a current dependency or authorized deployment.
The submission contract must remain portable to GitLab, Gitee, GitCode or a
self-hosted forge, and customer installs resolve approved digests from Setjoin-
controlled or customer-private sources rather than execute arbitrary Git URLs.

### Distribution and licensing posture

The intended community core is AGPL-3.0 and public SDKs, protocols, validators,
examples and client libraries are Apache-2.0, subject to a dependency and legal
review before publication. Extensions may choose compatible open-source or
commercial terms and must display them in the catalog.

Official Enterprise artifacts use a separate permanent commercial subscription
license with an explicit non-production evaluation grant. They do not use BSL or
any automatic future license conversion. Community users are not technically
prevented from building or testing their own HA topology; official qualified HA,
multi-instance centralized governance, Enterprise validated-channel evidence,
certification, SLA and
support responsibility are the paid product. Subscription expiry must not stop an
installed server or lock customer data. Dual licensing requires Setjoin-owned
copyright or contributor grants that expressly permit commercial relicensing.
External code contributions therefore require a lightweight individual or
corporate contributor license agreement modeled on the Qt/Canonical approach:
contributors retain copyright and independent reuse rights while granting
Setjoin perpetual, worldwide, non-exclusive copyright and necessary patent
rights, including sublicensing for both AGPL community and commercial Enterprise
distributions. The agreement must state the dual-licensing purpose plainly;
copyright assignment is not required, and DCO alone is insufficient for code
that will enter both release trains.

## Extension-owned data

The user-confirmed app data/backup/lifecycle amendment
owns default app-managed Drive spaces, three backup presets, dependency-aware scope,
inactive-copy restore, destructive previews and backup-preserving uninstall. It adds
planning requirements, not implementation evidence; the classes below remain distinct.

| Data class | Authority | Disable/remove | Backup/restore |
|---|---|---|---|
| Setjoin domain data | Owning system-app reducers | Preserved; never removed with app | Normal retention/backup |
| App metadata | Namespaced mediated store | Read-only when disabled; retain/tombstone by policy | Scoped backup/export |
| Managed volume | Encrypted, quota-bound storage class | Retain by default; purge is separate | Declared backup/schema compatibility |
| Remote-provider data | External and disclosed | Revoke credentials; cleanup is not proof | Export/deletion receipt where supported |

App schema versions are recorded. Mediated metadata uses a bounded declarative
migration DSL. App-owned volumes may use a separately signed, capability-limited
WASI or managed-OCI migration job with no Setjoin domain-data authority. Remote
providers own their migrations and return version/export/deletion receipts.
Expand remains compatible with the active generation; contract waits until
rollback expiry. Rollback is promised only when code and data formats remain
backward compatible or a tested reverse migration exists. Irreversible migration
requires approval plus backup/export evidence and removes the rollback claim.
Legal hold overrides removal; orphaned data remains tenant-scoped and quota-visible.

### Storage Provider boundary and performance contract

The selected public Storage Provider boundary extends only the byte plane. Drive
remains authoritative for ACLs, version and branch DAGs, ordered manifests,
content hashes and reference counts, quotas, retention and legal-hold decisions,
encryption metadata and key custody, audit, garbage-collection decisions, and
backup/restore roots. A Provider receives opaque, generation-fenced object
handles and bounded operations; it never receives database credentials,
tenant-wide enumeration authority, permission to invent object references, or
authority to decide retention or deletion.

The baseline Provider profile exposes streaming `PUT`, `GET`, `HEAD`, `COPY`,
range reads, and reducer-authorized deletion. Inventory is cursor-paginated and
bounded; an unbounded recursive list is not a public contract. Optional typed
claims cover conditional create/copy, verified checksums, multipart or large
objects, object lock/legal hold, locality and tiering. Every successful mutation
returns a receipt containing the logical digest, size, provider checksum or ETag,
provider generation, and operation identifier for Setjoin to verify and audit.
The qualification profile declares read-after-write and list consistency,
failure and retry semantics, range behavior, checksum behavior, object and
request limits, rate/concurrency hints, and supported durability/WORM controls.

S3 compatibility is an interoperability contract, not a performance guarantee.
AWS documents horizontal request scaling across prefixes and connections, while
SeaweedFS is designed for horizontal small-object access; a particular compatible
service can still be limited by disks, metadata placement, replication, network
topology, or implementation quality. Setjoin's current 4 MiB content-addressed
chunks also amplify requests: a 1 GiB file has 256 chunks, whole-file reads are
currently sequential, and a newly admitted chunk currently uses temporary upload,
server-side copy to its canonical key, then cleanup. These are recorded as
qualification debts, not assumed to be harmless because the API is S3-shaped.

Before any high-performance claim, the Drive data path must provide:

- bounded adaptive upload concurrency and ordered read-ahead, with memory limits,
  cancellation and backpressure rather than unbounded fan-out;
- per-Provider connection pools, jittered retry and explicit handling for
  throttling such as `503 Slow Down`, without retrying authorization failures;
- a locality-aware hot path and optional cache/tiering whose cached delivery is
  still fenced by current authorization and object generation;
- no direct or presigned delivery URL that can outlive revocation; any future
  direct-delivery profile must be short-lived or actively revocable,
  generation-bound, and fully audited;
- cursor-based reconciliation instead of whole-bucket materialization; and
- metrics for p50/p95/p99 latency, throughput, request amplification, retries and
  throttles, queue depth, cache hits, and gateway/backend CPU, disk and network.

Provider conformance tests cover small-object concurrency, large sequential
transfer, random ranges, deduplication-heavy upload, WORM behavior, partial
failure, retry safety, cancellation and overload. They run against each claimed
deployment topology; passing with local SeaweedFS does not certify a remote cloud
endpoint, and vice versa. Tier movement changes physical placement, not the Drive
file version or its logical content identity.

Primary performance references: [Amazon S3 performance
overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html),
[Amazon S3 performance design
patterns](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html),
and [SeaweedFS architecture and S3 API](https://github.com/seaweedfs/seaweedfs).

#### Default installation topology

The normal installer asks no storage-topology question. It provisions the bundled
local S3-compatible service (currently SeaweedFS), creates the required buckets,
generates and stores service credentials through the normal secret path, probes
read/write/range/delete behavior, and registers exactly one local hot Provider.
The installation fails closed if that probe does not pass; it must not silently
fall back to node-local files or an external network service.

Storage-target selection prefers an eligible independently mounted data volume
when one is available. If only the operating-system volume is eligible, installation
may continue after capacity and durable-I/O preflight, but the resulting topology is
recorded and displayed as a single-volume/shared-failure-domain deployment. The same
disk then contains operating-system, PostgreSQL and object-storage risks; free space
alone must not make the UI claim storage redundancy, an independent failure domain,
or production recovery readiness. Capacity thresholds, reserved emergency headroom
and low-space admission behavior belong to the future implementation plan rather
than being invented by the installer UI.

Custom installation may instead configure one administrator-supplied S3-compatible
endpoint. The setup flow collects endpoint and region, bucket names, credentials or
credential reference, TLS trust, addressing mode, optional object-lock support and
network locality, then runs the same conformance probe before activation. Secrets
are never exposed to apps. An explicit advanced choice may later add a remote
capacity, warm or replica Provider, but multi-tier placement is not required for
the initial default installation and is never enabled implicitly.

For the bundled local Provider, the normal installer chooses the platform-standard
data root automatically. Custom installation may select one absolute host directory
or mounted filesystem as the SeaweedFS data root. The default Setjoin deployment is
native: the installer renders that path into the dedicated SeaweedFS systemd unit,
and SeaweedFS owns the layout below it. A separately selected container deployment
maps the same host-side contract through an explicit bind mount, but Docker is not
a prerequisite or the default storage architecture. This is not a bucket browser
and administrators must not edit objects in that directory directly. External S3
configuration has no local-directory field.

Before accepting a custom data root, the installer resolves symlinks and mount
identity, rejects filesystem roots, system/application directories, non-empty
Setjoin-incompatible paths and paths nested inside another Setjoin-managed root,
then verifies ownership, permissions, free space, inode capacity, filesystem
features and a durable write/fsync/read/delete probe. It records the stable mount
identity as well as the displayed path so a missing disk cannot silently redirect
writes into an empty mountpoint on the operating-system disk. Installation creates
only the narrowly scoped subdirectories it owns and never recursively changes
permissions on a pre-existing parent tree.

The interactive SSH installer lists only discovered eligible disks and mountpoints,
showing capacity, filesystem, stable device identity and detected failure domain,
and adds an advanced absolute-path input. It does not expose a general server
filesystem browser. Path discovery and validation execute in the local privileged
installer boundary. After installation, the authenticated admin application receives
only a typed storage-health and topology projection and never gains arbitrary
directory-enumeration authority.

#### Bootstrap operator experience

Setjoin does not install a temporary privileged web server before the product is
ready. The native package/script is run over SSH as root and provides a resumable
interactive terminal flow: preflight, deployment profile, eligible storage target,
network and database settings, secret generation, native service installation,
schema activation, local first-administrator creation, service start and health
verification. Numbered choices and an advanced path field are sufficient; the
bootstrap contract does not require a full-screen TUI dependency. Unattended installs
consume an explicit root-readable configuration and secret files rather than command
line secrets.

The installer creates the first administrator locally through `mailctl
bootstrap-admin`, with hidden and confirmed terminal input, before the public listener
is considered ready. It then prints the authenticated admin URL and next actions.
The browser `/setup` surface may report read-only readiness and local recovery
instructions, but it cannot create the first administrator, accept storage paths or
credentials, browse the host filesystem, or perform restore. The existing authenticated
HA deployment wizard remains a post-bootstrap control plane for additional nodes; it
is not the authority that installs the first node.

The release carries one explicitly pinned SeaweedFS native binary per supported
OS/architecture together with its version, size and cryptographic digest in the
signed Setjoin artifact manifest. The installer selects only an exact supported
artifact, verifies it before execution and never downloads an unpinned `latest`
binary. Offline installation uses the same manifest and verification path. A missing,
wrong-architecture or digest-mismatched binary fails installation rather than falling
back to an operating-system package or container image.

The installer creates a dedicated non-login SeaweedFS service account whose write
access is limited to its selected data root and narrowly scoped runtime state. The
configuration and credentials use separate least-privilege ownership; the service
does not run as root or as the Setjoin gateway user. Its systemd unit applies the
strongest verified sandbox compatible with the pinned release, including no-new-
privileges, a bounded writable-path set, private temporary state and an empty or
minimal capability set. The S3 listener is private to the Setjoin host/cluster by
default and is not exposed as a customer-facing general object-store endpoint.

SeaweedFS has no independent `latest` channel in a managed Setjoin installation.
Each Setjoin release manifest names the exact SeaweedFS source version and artifact
digest plus its supported previous version, configuration schema, on-disk compatibility
and rollback classification. The Setjoin updater stages and verifies both product and
storage artifacts, checks capacity and topology health, drains storage-dependent work,
applies the declared service transition, and admits the release only after S3 and
Drive conformance probes pass. A failed admission restores the previous binary and
configuration only when the manifest declares the data path backward compatible;
otherwise the release must require a separately verified snapshot/restore or refuse
the update before mutation.

Administrators may schedule or defer this coordinated update according to policy,
but cannot make the managed service fetch arbitrary upstream builds. Urgent SeaweedFS
security fixes still ship as signed Setjoin release artifacts with an explicit affected
version range; urgency shortens release cadence, not the verification or provenance
boundary. A customer who replaces the managed binary manually leaves the qualified
managed profile until the exact supported artifact is restored and re-probed.

A single-node storage update uses a declared, bounded maintenance window: blob-
producing work drains, SMTP receives retryable temporary responses, the old service
stops, the verified binary/configuration switch occurs, and readiness returns only
after storage and application probes pass. The administrator sees the expected and
actual interruption, and timeout or failed health invokes the manifest-approved
rollback path rather than leaving an ambiguous partially admitted version.

An HA Provider uses a rolling update only when the exact source/target pair has a
retained mixed-version compatibility result covering Raft/master quorum, filer and S3
behavior, volume reads/writes, replica repair and rollback. The reconciler preserves
quorum and declared failure-domain redundancy, upgrades one bounded unit at a time,
waits for convergence and probes after each step, and pauses on degradation. Mixed
versions have a bounded transition lifetime, not a steady-state support promise. If
that evidence or safe redundancy is absent, the updater selects the same explicit
maintenance contract as a single node; it never treats `HA` as proof that arbitrary
rolling upgrades are safe.

#### Encryption posture and conversion

The default installer does not format, re-partition, unlock or enable encryption on
an administrator's disk, and it does not claim that the bundled local Provider is
encrypted merely because Setjoin generated application secrets. The SSH installer
reports three independent facts where applicable: host-volume encryption, Provider
server-side encryption, and Setjoin object-envelope encryption. Each is `enabled`,
`disabled`, `unsupported` or `unknown` with evidence and next action; `unknown` is not
rendered as secure.

For a bundled local SeaweedFS Provider, the relevant baseline is the selected host
filesystem or block device. If the operator requests disk encryption but the target
is not already an unlocked encrypted volume, the installer stops before writing data
and gives distribution-appropriate LUKS/dm-crypt preparation instructions, then asks
the operator to rerun installation. It never silently reformats a disk, generates an
unrecoverable key, modifies boot unlock policy or assumes custody of a recovery key.
For an external S3 Provider, the setup instead displays and qualifies supported
SSE-S3, SSE-KMS or vendor-equivalent settings. Disk encryption and S3 server-side
encryption are deployment-context controls, not a universal mutually exclusive radio
choice, and neither is enabled by default by Setjoin.

Proceeding with an unencrypted target is an explicit, auditable choice rather than
an implicit default. The interactive installer requires the operator to acknowledge
the detected unencrypted posture before continuing and records that decision and
the supporting probe result in the installation receipt. An unattended installation
must declare the equivalent policy in its root-readable configuration; if the field
is absent, installation fails closed. The acknowledgement does not turn an
unencrypted deployment into a compliant or recommended security posture, and it
does not suppress the continuing administrator warning.

Setjoin object-envelope encryption is a later, optional orthogonal profile for an
untrusted external Provider or high-security tenant. It may be layered over either
disk or server-side encryption. Enabling it after installation is a data-format
migration, not a boolean flip: create a new encoding generation, copy plaintext
through bounded authenticated encryption, verify plaintext identity and ciphertext
receipts, enter the declared write-freeze/fence cutover, retain the old generation for
rollback, then retire it according to retention policy. Moving an existing local
deployment onto LUKS similarly means provisioning a new encrypted target and using
the Provider migration workflow; Setjoin does not attempt unsafe in-place conversion
of the mounted data filesystem.

The future object profile requires streaming chunked AEAD, scope-bound keys and AAD,
versioned envelopes, range mapping, rotation and independently recoverable key
escrow. It must define how previews, malware scanning, Office/WOPI and legal retention
receive bounded plaintext. The existing whole-buffer deterministic `EncryptBlob`
helper is a prototype primitive: it has unit tests but no production caller, uses one
derived master-key domain and does not provide this migration, streaming, tenancy or
key-lifecycle contract. It must not be wired into Drive merely because it exists.

Current implementation audit (2026-09-01):

| Capability | Status | Evidence |
|---|---|---|
| Detect LUKS/dm-crypt and stable encrypted mount in installer | Not implemented | Installer has no `lsblk`/`findmnt`/`cryptsetup` probe or encryption status model |
| Configure or verify S3 SSE/KMS | Not implemented | `storage.DriverConfig` has no encryption fields; hot-path `PutObjectOptions` is empty |
| Encrypt/decrypt live S3 objects in Setjoin | Primitive only | `shared/cryptokey/storage.go` has tested whole-buffer helpers; repository has no non-test caller |
| Convert plaintext objects to an encrypted generation | Not implemented | No `mailctl storage-migrate --encrypt`, rekey command or encoding-generation reducer exists |
| Provider-to-Provider byte copy | Partial/maintenance-only | Admin endpoint and copy loop exist, but no real dual-write/delta fence and no encryption transform |
| Display encryption state or conversion in Storage admin | Not implemented | Current page shows cluster health and DR scans only |

The archived MAM/encryption design that describes S3 encryption as always-on and a
working `storage-migrate --encrypt` command is aspirational and conflicts with this
source audit. It is not implementation evidence or the authority for release claims.

Consequently the first implementation and operational promise remain simple:
one active storage Provider is sufficient, local is the safe default, and Drive
logical identities do not depend on whether an administrator later migrates or
tiers the physical bytes. Provider replacement or tier movement requires a
reconciled copy-and-verify workflow with retained source data until verification;
changing configuration alone never rebinds existing object handles.

#### Durability and replication ownership

Setjoin writes to one active logical Storage Provider. Replication, erasure
coding, node and rack placement, repair, and any backend-native cross-site copy
belong to that Provider; Drive does not synchronously dual-write independent
Providers or attempt to arbitrate their partial success. Backup remains a
separate, independently restorable protection boundary and is not inferred from
replication.

The bundled SeaweedFS profile derives a valid replication policy from the
declared physical topology. It must not claim host, rack or data-center
redundancy when the installation lacks those independent failure domains. A
single-node installation may run for evaluation or small deployments, but the
admin surface states its actual copy/failure-domain posture rather than showing
a generic healthy badge. Custom S3 activation records provider-reported and
tested capabilities—such as versioning, durability class, object lock and
replication visibility—without treating a marketing durability number as a
verified backup.

Health and readiness report logical availability separately from durability and
recoverability. Losing redundancy raises an actionable degraded state without
silently changing Drive semantics; repair is delegated to the Provider and its
progress is observed. Setjoin changes Provider placement only through a
copy-verify-fence-retire workflow, and retains the source until the destination
receipt and content verification are durable.

The default installation does not provision a second backup Provider. The backup
workflow recommends and validates an independent disk, host or remote S3 failure
domain. A snapshot or backup object stored in the same Provider may be exposed as
a convenience recovery point, but it is labeled co-located and cannot satisfy an
independent-backup, disaster-recovery or recoverability claim. Restore readiness
is based on a verified restore drill, not merely on replica count or backup-job
success.

The operational ownership is therefore explicit:

| Operation | Owner |
|---|---|
| Copy placement, failed-disk repair and node/rack rebalance inside one SeaweedFS/S3 service | Storage Provider |
| Backend-native replication between sites managed as one Provider | Storage Provider, observed by Setjoin |
| Migration between different endpoints, vendors, buckets or credential domains | Setjoin copy-verify-fence-retire reconciler |
| File versions, branches, conflicts and user-visible history | Drive reducers |
| Independent backup and restore | Backup subsystem using verified Provider reads/writes |

Cross-Provider migration must work even when neither backend can directly copy
from the other. Setjoin enumerates only reducer-authorized live objects, streams
or stages them through bounded workers, verifies size and content digest at the
destination, repeats a final delta/fence phase, changes the authoritative
placement generation transactionally, and retains the source for a declared
rollback window. The existing `internal/storage` migration skeleton has no real
dual-write phase and can miss concurrent writes around its cursor; it remains a
maintenance-window implementation and must not be represented as this future
zero-downtime contract until replaced and tested.

Object Lock is an optional typed Provider capability for ordinary Drive use and
a mandatory capability for any WORM, compliance-retention or legal-hold claim.
When it is absent, ordinary files remain available but those dependent features
are disabled with an explicit admin explanation. Database retention flags may
coordinate policy but never simulate backend immutability or satisfy a WORM
claim on their own.

The first cross-Provider replacement release promises only a declared
maintenance-window workflow. It performs the bulk copy while the source remains
authoritative, then enters a bounded storage-write freeze for the final inventory,
digest verification and placement-generation cutover. Existing bytes remain
readable from the source during the freeze. Drive uploads and Office saves return
a typed planned-maintenance response; SMTP delivery returns an appropriate
transient `4xx` so conforming senders retry rather than accepting mail whose bytes
cannot be committed. Blob-producing background work drains or pauses before the
fence. Failure or deadline expiry leaves the source generation authoritative and
unmodified.

This maintenance mode applies only when Setjoin replaces one logical Provider
with another. Node addition, disk replacement, replica repair and rebalance
inside a single SeaweedFS/S3 Provider remain backend operations and do not imply
a Setjoin storage-write freeze. Online cross-Provider migration is a later
capability gated on a proven delta journal, generation-fenced reads and writes,
crash-resumable verification, rollback, and concurrent-write fault injection;
the UI must not relabel the maintenance implementation as zero downtime.

## Lifecycle

```text
listed -> resolving -> awaiting approval -> staging -> probing -> active
                                                   \-> failed
active -> update staging -> authority unchanged -> update probing -> active / previous healthy
                         -> authority changed -> awaiting reapproval
                              -> approved -> update probing
                              -> denied -> current generation remains active
                              -> current release revoked -> fenced/unavailable
active -> planned admission closure -> permitted accepted-work drain
       -> retire residual authority -> stopped -> removed/tombstoned
active/draining -> security revocation -> immediately fenced
                -> separately authorized maintenance / explicit failure
```

Lifecycle is desired-state reconciliation. Operations are revisioned,
idempotent, crash-resumable and generation-bound. Revocation fences capabilities
before draining. Health never grants authority. Removal treats executable
artifacts, configuration, credentials, plugin-owned data, Setjoin-owned data and
audit tombstones separately.

The previous generation remains active while reapproval is pending unless that
release is revoked; revocation fences it and leaves the app unavailable rather
than silently accepting broader grants.

### Normative flow

```text
Admin -> reducer: desired release + grants + revision + reason
reducer transaction: authorize, persist goal/grants/audit, enqueue operation
reconciler: verify catalog/signature/digest/compatibility; stage and probe runtime
adapter -> reducer: observation(expected operation/revision/generation)
reducer transaction: activate new generation or record stable failure
runtime -> broker -> owning system-app API -> reducer: reauthorize and commit
reducer transaction: state + audit + semantic outbox event
candidate update -> reducer: record candidate; retain prior approved authority
planned retirement -> reducer: stop new admission; drain permitted accepted work
security revoke -> reducer: fence immediately; never revive revoked authority
activate/retire -> reducer: commit reviewed route/generation transition
```

Failure before activation changes no active route. Stateful rollback is claimed
only while schema/data remain compatible; otherwise the runtime is fenced and a
reasoned recovery operation is required.

Candidate staging and awaiting reapproval do not themselves revoke the existing
approved generation. Planned admission closure preserves only already authorized
work under the owning domain's drain contract; it does not admit new launches.
Explicit security revocation immediately invalidates affected authority even during
drain. Any continuation then requires a separately reducer-authorized maintenance
obligation, never an old token made valid again. The exact operation revision,
runtime generation, route revision and security-fence changes are frozen together
under CP0.3.
For E2 WebApp launch and serving membership, that freeze also includes
D6.3a's
launch-code schema, audience/callback registry, single-use redemption and generation
binding, serving-lease timing/renewal and non-success pending-outcome mapping.
E1 retains reducer authority; E2's adapter does not create another SSO registry.

## Compatibility and maintainability

Versioning is layered rather than coupled to the Setjoin release or assigned to
every HTTP route independently:

1. The Setjoin product release has its own version and does not imply an
   extension-contract break.
2. The extension platform publishes a monotonic integer `apiLevel`. A release
   increments it when the platform adds a contract or capability that an app may
   detect; supported older levels remain valid within their support window.
3. Each domain contract has an explicit major identity, such as
   `mail.commands.v1`, `mail.events.v1` or `drive.queries.v2`. Compatible additive
   changes remain within that major. A change to meaning, authorization,
   idempotency, ordering or required fields creates a side-by-side new major.
4. The manifest grammar has an independent `schemaVersion`; an app release has
   its own SemVer. A manifest declares its minimum `apiLevel`, the highest level
   it was tested against, and every required domain-contract major.
5. Individual HTTP routes do not receive unrelated SemVer numbers. They are
   transports for the owning versioned domain contract.

Surfaces are `experimental`, `beta`, `stable` or `deprecated`. A contract advances
to `beta` only after one executable first-party consumer, and to `stable` only
after at least two external developers independently complete reproducible
integrations in two structurally different application categories, plus a threat
model, conformance tests, compatibility range and deprecation/migration plan.
External validation tests whether the contract, SDK and documentation work without
private Setjoin knowledge; the validators' applications need not be publicly listed,
manually reviewed or commercial. First-party dogfood is necessary for `beta` but
cannot satisfy the external `stable` gate by itself. A stable contract is supported
until an explicitly scheduled retirement. **Accepted 2026-09-06:** ordinary removal
cannot occur before both 12 calendar months after a stable successor releases and
12 calendar months after explicit deprecation notice, using the later deadline.
Migration guidance and conformance fixtures accompany the successor. These clocks
run concurrently, not as a mandatory 24-month sequence. No successor or notice means
no ordinary retirement deadline; minimum windows do not cause automatic expiry.
This supersedes the prior three-year promise. The [policy comparison and decision](../research/2026-09-06-extension-api-longevity.md)
preserve its history. Rolling delivery and old-product maintenance remain distinct.
An urgent security response may fence unsafe behavior sooner, but must publish the
reason, affected range and supported remediation path.

Additional invariants:

1. Every extension-visible first-party path uses public DTOs, events and Provider
   contracts. Internal-only operations are enumerated as sealed capabilities and
   cannot be reached by public contributions or runtimes.
2. Plugins never import one another's implementation. Shared types live in small
   versioned SDKs; runtime communication uses broker or network contracts.
3. Contract tests cover supported SDK/runtime combinations against current and
   retained prior Setjoin builds.
4. Unknown capability or contribution kinds fail closed.
5. A compatibility resolver explains conflicts before installation and prevents
   partial activation.
6. New stable extension points require a real consumer, owner, tests, deprecation
   plan and security boundary.

### Contract registry and generated SDKs

The single source of truth is a versioned contract registry, not one universal
IDL. Mature ecosystems use the same pattern at different scales: Microsoft
generates REST clients from OpenAPI while versioning its app manifest as JSON
Schema; Kubernetes publishes discovery plus OpenAPI and reserves Protobuf mainly
for internal transport; Grafana separates `plugin.json`, frontend APIs and its
stable backend protocol; VS Code combines JSON declarations with a TypeScript
runtime API; Feishu separates server APIs, events, callbacks and language SDKs.

Setjoin therefore assigns one normative representation to each boundary:

1. Shared domain DTOs, capability envelopes, manifest and typed configuration use
   versioned JSON Schema.
2. Synchronous HTTP commands and queries use OpenAPI 3.1 referencing those domain
   schemas rather than copying their definitions.
3. Each semantic event has a canonical versioned JSON Schema inside the Setjoin
   CloudEvents envelope. AsyncAPI 3 is a generated discovery/documentation
   projection over those schemas, not a second event authority.
4. WASI host and guest interfaces use WIT because their ABI and resource model are
   not HTTP contracts.
5. Protobuf may optimize a sealed internal or explicitly profiled transport, but
   it is not the public extension contract source and cannot alter public meaning.

The registry binds every capability ID, domain-contract major and schema digest.
CI reproducibly generates and diffs low-level types, validators and clients. Go,
TypeScript and Rust are the initial supported SDK targets; Swift and Kotlin join
only when an approved client contribution needs them. Small hand-written
language-idiomatic wrappers are allowed, but cannot add wire semantics and must
pass the same conformance corpus. Generated artifacts record the source digest,
generator version and supported `apiLevel`; SDK package SemVer remains distinct
from the wire-contract version.

### Dependency invariants

Resolution produces an immutable lock graph of publisher-qualified release IDs
and signed artifact digests. It is deterministic for a catalog snapshot and
source policy. Cycles and ambiguous providers are rejected. Multiple major
versions may coexist only when their runtime/data namespaces are isolated and
the dependent manifest explicitly permits it. Dependency capabilities are never
inherited: each installation requests and receives its own grants. A graph update
stages and probes all changed nodes before an atomic routing switch. Before any
declared point of no return, failure leaves the prior graph active. After an
approved irreversible migration begins, failure fences affected routes and enters
reasoned recovery; it never claims automatic restoration of an incompatible prior
graph. Removal is blocked while active dependents exist unless one approved
operation removes, disables, or re-resolves the full graph.

The primary long-term cost is the permanent contract surface, not the runtime.
Keeping the stable surface small is the main maintainability control.

## Alternatives considered

- **Container marketplace expansion:** lowest initial cost, but Provider, UI,
  WASI and client features would overload a container-centric contract.
- **Layered capability platform — selected:** independent control plane with
  separate contribution, runtime and placement axes while retaining simple WebApp authoring.
- **Public Kubernetes-like API:** excellent internal lifecycle pattern, but too
  infrastructure-heavy for normal application developers.
