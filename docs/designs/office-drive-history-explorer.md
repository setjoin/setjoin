## Problem Statement

Setjoin already owns a capable on-premise Drive with immutable file versions,
branches, locks, comparisons, restore, audit activity, and a point-in-time space
view. It lacks a browser Office editor and presents historical state through
separate surfaces rather than one understandable, visual history experience.

The product needs to add Office editing without making an editor vendor the
authority for files, permissions, versions, retention, or audit. It should also
turn existing file, Office-save, permission, sync, and device-state facts into a
Time Machine-style History Explorer. Physical storage optimization is related,
but must not dictate the logical history or user interface.

## Demand Evidence

- Setjoin is intended for 300–10,000-user on-premise organizations.
- The founder has approximately 20–30 Exchange on-premise or hybrid customers;
  several are considering replacement and some are subject to domestic-technology
  or regulatory replacement requirements.
- Customers need an Office-capable collaboration suite rather than a mail-only
  replacement. File compatibility, private deployment, commercial redistribution,
  domestic-platform evidence, auditability, and continuity matter together.
- The founder explicitly chose a unified History Explorer design with Office,
  history UI, and storage optimization kept as independently executable tracks.

## Status Quo

Setjoin currently provides:

- `drive_file_versions` plus version-to-content manifests and immutable original
  bytes in SeaweedFS/S3/POSIX;
- version branches, labels, locks, conflict saves, compare, view, download, and
  restore-as-new-version;
- a Drive activity feed and reducer-owned audit facts;
- a user-visible "space as of time" view with per-file restore;
- Office type recognition and an isolated LibreOffice-based PDF preview worker;
- Electron, iOS, Android, and HarmonyOS shells that reuse the Svelte web surface;
- optional local file mirroring for desktop Drive access.

Setjoin does not currently implement WOPI, an embedded Office editor, a shared
history projection contract, or a supported offline embedded Office engine.

## Target User and Narrowest Wedge

The first wedge is an employee in a regulated or sovereignty-sensitive
organization who opens a DOCX/XLSX/PPTX from Setjoin Drive, edits it with other
authorized users, sees every accepted save become a normal Drive version, and can
visually inspect, compare, and restore earlier states.

The first administrator wedge is the operator who can answer: what changed, who
changed it, which editor generated it, what permissions applied, whether the
document and editor were healthy, and how to recover without database or object
store access.

## Product Principle

**Preserve authoritative facts; make state and history visually understandable.**

Setjoin should retain the most useful facts permitted by policy, then expose them
through progressive, graphical views: timelines, state snapshots, comparisons,
relationships, health signals, and clear recovery actions. More facts must not
mean a denser default screen. The default view explains the current state and
material changes; progressive disclosure exposes forensic detail.

The visual projection is never authority. Reducers and immutable versions remain
authoritative even if a projection is stale, unavailable, or rebuilt.

After this design is approved, the principle belongs in
`docs/design/PRODUCT_PRINCIPLES.md`. The separation between logical history,
projection, and physical representation belongs in a new architecture ADR.

## Locked Premises

1. Setjoin remains the Office integration host and file authority. The Office
   Broker hides WOPI, proprietary web-editor, desktop-launch, and offline-sync
   differences behind one Setjoin interface. Editors are replaceable, untrusted
   adapters or sidecars with no database or object-store credentials.
2. A successful editor save creates a normal Drive version and audit event; the
   editor never mutates authoritative bytes invisibly.
3. Collabora is the primary implementation PoC, not an irreversible dependency.
4. The Office Broker interface remains vendor-neutral; WOPI is one protocol
   adapter, not the universal interface. V1 web editing ships only Collabora and
   requires a non-distributed lab conformance run against ONLYOFFICE under a
   written evaluation/development entitlement. V1 desktop choice supports
   customer-installed Microsoft Office, WPS Office, LibreOffice, and Collabora
   Office through FolderMirror/open-with. Microsoft 365 Web, WPS WebOffice, and
   domestic web editors require their own adapter plus written commercial and
   deployment rights before customer use.
5. The History Explorer unifies presentation and query semantics, not physical
   storage. File versions, audit events, device facts, and derived renditions keep
   separate lifecycle and authorization rules.
6. Original Office/WPS/iWork bytes are never discarded. Text-history compression
   is tested only for eligible text or future canonical native representations.
7. The web product is online-only and does not advertise offline editing. Offline
   modes belong to installed Setjoin apps and must state exactly which local
   engine edits the file and where authoritative Drive save acceptance occurs.
8. A content-changing WOPI save callback creates an immutable Drive version.
   Byte-identical retries do not create duplicate versions, but retain an
   idempotent operation receipt and security-relevant audit facts. The UI may
   group autosaves visually; it never coalesces authoritative versions silently.

## Chosen Approach

Use one umbrella design with three independently promoted execution plans:

1. **Office foundation and provider adapters:** a deep Office Broker module,
   WOPI host adapter, Collabora primary web PoC, desktop open-with adapters,
   alternate backend contract tests, licensing, upstream, and deployment gates.
2. **Drive History:** a Time Machine-style timeline inside Drive, backed by a
   shared projection/query contract over Drive versions, Office saves, file
   lifecycle, permissions, sync, and device state. It is not a separate app.
3. **Physical history optimization:** a revalidated experiment for bounded text
   history packs and client-local SQLite recovery, with no effect on logical IDs,
   UI semantics, or Office originals.

The plans may share contracts and fixtures, but failure or deferral in one does
not block the others unless an explicit dependency gate says so.

### First-release boundary

The first release is deliberately narrower than the umbrella design:

- an Office Broker with administrator allowlists and user/device/file-type
  preferences;
- Collabora PoC and qualified browser/Electron online editing;
- Electron/FolderMirror open-with for customer-installed Microsoft Office, WPS
  Office, LibreOffice, and Collabora Office, including offline reconnect;
- file-level accepted saves, versions, compare, restore, locks, and history;
- a mandatory vendor-neutral WOPI authority/isolation profile;
- a lab-only ONLYOFFICE run of that profile and an editor-removal drill, without
  shipping or representing ONLYOFFICE as a production backend;
- licensing, reproducible-build, upstream, and backend-removal evidence.

Mobile editing, native embedded offline Office,
Microsoft 365 Web/WPS WebOffice, space/device/system History Explorer expansion,
a second production web backend, and physical history packs are separate
promotions. They remain represented here so the first release does not make them
impossible, but they are not first-release acceptance gates.

### Go-owned control plane

Setjoin Go owns editor discovery caching, launch, proof-key validation, scoped
tokens, WOPI callbacks, request limits, health/capacity control, and translation
between HTTP and reducer calls. Reducers own authorization, locks, version
creation, branches, audit, retention, state bump, and notification.

### Office Broker deep module

The seam lives above vendor protocols and below Drive/web/Electron callers. Its
small external interface is:

```text
Choices(actor, file, device, connectivity) -> allowed OfficeChoice[]
Open(actor, file, baseVersion, choice)       -> OfficeLaunch
Finish(session, providerOutcome)             -> accepted Drive result
```

`OfficeChoice` describes user-facing mode, provider, supported file types,
online/offline/co-edit behavior, installation and entitlement state, and the
reason an unavailable choice is disabled. `OfficeLaunch` is either a scoped web
session, a desktop open-with instruction over a mirrored local path, or a
view/download result. Callers never construct WOPI URLs, WPS requests, Office URI
schemes, locks, or upload callbacks themselves.

The implementation owns internal adapters for WOPI web editors, proprietary web
editors, and local open-with/sync. Provider manifests declare capabilities and
license/deployment cells; adapters translate them but cannot grant a Drive
capability. The same interface is exercised by an in-memory conformance adapter,
Collabora, FolderMirror/local-open, and later WPS/Microsoft adapters. This is a
real seam because multiple adapters vary today, not speculative indirection.

Administrator policy first restricts providers by tenant, classification,
platform, file type, data-egress rule, and verified entitlement. Within those
choices, a user may set a default per device and file family and override it for
one open. The fallback order is explicit: preferred compatible choice, tenant
default web editor, installed local editor, preview, then authorized download.
Unavailable or unlicensed providers are visible with an explanation only when
the viewer is authorized to know they exist.

Switching providers never hands an active session to another engine. Setjoin
first accepts or rejects the current save, closes/fences its cohort, records the
new base version, then launches the next provider. Different providers cannot
participate in one realtime co-edit cohort.

### Editor-session and save state machine

Each user/device open creates a reducer-owned `editor_launch` with its own random
ID, actor, device, scoped token, capabilities, expiry, and revocation generation.
Many authorized launches join one reducer-owned `document_editor_session` co-edit
cohort identified by tenant/file/node, backend, branch, base version, opaque lock
epoch, save generation, fencing generation, and terminal status. Cross-tenant
joins fail before disclosing cohort existence. Revoking one launch removes that
participant and token; it closes the cohort only when policy requires or the last
launch leaves. Backend disable, file revocation, or tenant shutdown fences the
whole cohort. The callback principal is the backend acting for the cohort; human
attribution is separately qualified from authenticated launches and editor
evidence.

The cohort state machine is `launching -> active -> saving -> active -> closing
-> closed`, with `revoked`, `expired`, and `failed` terminal paths. Launches have
`joining -> active -> leaving -> closed`, plus individual `revoked` and `expired`
paths. Every callback rechecks current authorization, cohort generation, node
lifecycle, lock epoch, and limits.
Rename/move preserves the stable WOPI file identity; trash, purge, permission
loss, backend switch, or explicit revocation fences future callbacks. A late or
fenced V1 save fails without changing the head; its content is discarded after
bounded in-memory processing and only a redacted security receipt is retained. A
future recovery store requires a separate reducer-owned, tenant-scoped,
encrypted, TTL-bound, admin-only design.

`PutFile` is serialized per cohort. When a backend supplies a documented stable
operation ID, the durable receipt key is `(tenant, cohort, lock_epoch,
backend_operation_id)` and stores expected base, digest, result version, and
response. Without one, the conservative key is `(tenant, cohort, lock_epoch,
expected_base, digest)`. A new digest accepted against the current base creates
one Drive version and advances the base atomically with its receipt. A retry of
the receipt returns the stored result; content identical to current head records
a no-op receipt. A digest already accepted earlier in the same lock epoch but no
longer current is rejected as an ambiguous delayed retry instead of reverting
newer work. An intentional byte-identical return to older content must use an
explicit Drive restore or a new lock epoch. Concurrent callbacks and stale bases
branch or fail according to the matrix below. `PutRelativeFile` always creates a
separately authorized Drive node/version.

WOPI locks are not overloaded onto the existing user checkout row. A reducer-
owned editor-session lock bridge stores the opaque WOPI lock value, application
instance/co-edit cohort, fencing generation, expiry, and related advisory Drive
checkout. It implements LOCK, REFRESH_LOCK, UNLOCK, and UNLOCK_AND_RELOCK while
preserving Setjoin's branch-on-conflict recovery.

Every content mutator consults the same reducer-owned fence in one transaction:

| Existing state / incoming write | WOPI save with matching opaque lock | Direct upload or FolderMirror | Restore | Offline reconnect |
|---|---|---|---|---|
| Active WOPI cohort | accept/serialize | reject or explicit conflict branch; never replace head | create explicit branch, then request cohort close before promotion | conflict branch |
| Hard user checkout, no WOPI cohort | reject unless same authorized owner converts it to a cohort | existing hard-lock rule | existing hard-lock rule | existing hard-lock rule |
| Soft checkout, no WOPI cohort | acquire cohort fence, preserve advisory attribution | existing soft-lock/conflict rule | existing restore rule | base-version conflict rule |
| No lock | acquire/accept | accept against current base | restore as new version | accept only if base unchanged; otherwise branch |

Race tests cover lock acquisition, direct upload, restore, reconnect, session
fencing, and callback commit at transaction boundaries.

### Editor-owned data plane

Collabora owns Office parsing, layout, browser editing, formulas, presentations,
and realtime co-editing. Setjoin does not port the LibreOffice/Collabora engine to
Go. Vendor PostMessage APIs are optional UX enhancements and cannot become save,
authorization, or history authority.

### Git-aligned Drive branches and user-visible conflict resolution

Office writes directly use the shipped Drive model whose authority is
`retired-docs:superpowers/specs/2026-07-09-drive-git-versioning-model.md`; Office does
not invent a second conflict system. Drive already has immutable versions,
per-file named branches, `parent_version_id`, `merged_from_version_id`,
`branch_id`, `conflict_of`, main and branch heads, branch lanes, and audited
resolution. It deliberately borrows Git's DAG and ref concepts without turning a
Drive space into a Git repository.

Every edit opens from `(file, branch-or-main, base_version)` and every save lands
on that same ref. If the target head changed, or a soft lock forces separation,
the reducer creates an auto-named branch and leaves main unchanged. An offline
FolderMirror save and a web-editor callback therefore converge on the same
branch-on-stale-base rule regardless of whether WPS, Microsoft Office,
Collabora, or another provider produced the bytes.

The user sees plain-language document concepts rather than object IDs or Git
jargon:

1. File rows and the editor header show the current line of work plus a visible
   conflict/branch badge.
2. Version History shows a main lane and named branch lanes, including author,
   provider, device, note, base, save time, and resolution state.
3. Conflict Review offers original download and authorized side-by-side rendition
   comparison, branch rename/note, continue editing either line, and request
   review.
4. Resolution exposes the four existing audited actions:
   - **Bring into main (fast-forward):** main did not move after the fork, so the
     main pointer advances without creating a version.
   - **Use this version as main (adopt):** create a new main version containing
     the selected branch bytes and record both parents.
   - **Keep both files:** create a separately named sibling containing the branch
     bytes and leave the original main unchanged.
   - **Close without using:** retain branch history and audit but mark it
     discarded.
5. A **Combine manually** workflow opens/downloads both versions, lets the user
   produce a combined document in an allowed provider, and saves that result to
   a branch before an explicit resolution action.

Office OOXML/WPS/iWork files do not receive automatic Git-style three-way text
merges or conflict markers. Realtime co-edit merging belongs to one active editor
cohort. Divergent offline or cross-provider snapshots remain full immutable
versions; comparison informs a human choice, and reducers record the chosen
lineage. A future provider-specific merge assistant may generate a candidate on a
new branch, but it can never update main without explicit authorization and
resolution.

| Browser online, default | Collabora service | Office Broker selects WOPI iframe; accepted saves create Drive versions | Yes |
| Browser online, optional | WPS WebOffice, Microsoft 365 Web, domestic editor | Provider adapter after entitlement, private-deployment, egress, and conformance gates | Later promotion |

| Mobile online | Collabora service | Reuse the same route in WebView after mobile compatibility gates | Later promotion |
| Desktop online/offline with external editor | User device | FolderMirror/open-with customer-installed WPS, Microsoft Office, LibreOffice, or Collabora Office; reconnect upload uses the same base-version branch rule | Yes |
| Cached offline view | User device | Open policy-eligible encrypted rendition and history metadata; no false edit affordance | Later promotion |
| Setjoin-branded embedded offline Office | Local native/Collabora engine | OEM or self-built client, local key custody, update and app-store lifecycle | Deferred PoC |
| Browser/PWA offline Office | Browser only | Not marketed or planned; the web product is online-only | No |

A Setjoin-App-embedded Collabora engine is technically feasible, but it is a
native-app capability rather than an offline website. Collabora Office 26.04 uses
the same engine/front end locally through WebView2 with an in-process engine on
Windows, WKWebView on macOS, and Qt6 WebEngine on Linux. Setjoin will evaluate
that architecture as a separate PoC. It adds package-size, sandbox, local IPC,
resource, signing, update, CVE, branding, redistribution, and support boundaries;
Collabora currently describes this desktop line as not yet enterprise-supported.
Until those gates pass, V1 uses FolderMirror/open-with and customer-installed apps.

An offline client cannot preserve exclusive server locking while disconnected.
It retains only a base-version claim; any lease is advisory after its TTL. On
reconnect, unchanged-base saves use the normal path and changed-base saves create
a deterministic conflict branch. Promotion requires encrypted cache/key custody,
revocation and offboarding wipe, rename/delete races, retry/idempotency, quota,
storage-pressure, and conflict-UX evidence.

## License, Upstream, and Replacement Strategy

### Deployment profiles

1. **Lab/PoC:** unmodified Collabora CODE, free, pinned to an exact source and
   image digest, never represented as vendor-supported production.
2. **Self-supported production (V1 shipping baseline):** a reproducible, source-derived and Setjoin-
   qualified Collabora Online build with no claim of vendor production support.
   Setjoin owns whole-artifact license scanning, security triage, backports,
   compatibility QA, notices, corresponding-source delivery, and support wording.
3. **Vendor-supported production:** customer BYOL or a written Setjoin OEM/ISV
   agreement covering customer-operated on-premise instances, redistribution,
   branding, support pass-through, desktop/mobile rights, updates, HA, and domestic
   platform builds.

V1 therefore does not depend on an OEM contract, but it may not use Collabora
trademarks to imply support or ship until whole-artifact counsel review and the
compliance ledger pass. The vendor-supported profile is a mutually exclusive
upgrade path. V1 provenance binds source commit and submodules, patch digests,
toolchain/container digests, SBOM, build attestation, and output digest. Two clean
builds must reproduce the same unsigned payload; signatures and timestamps are
recorded separately. The patch queue may lag at most 90 days or one upstream
security release, whichever is shorter; a critical exploitable issue overrides
that window.

### Compliance ledger

Every shipped editor build records source commit, patch queue, build recipe,
container/package digest, SBOM, license/notice set, corresponding-source location,
trademark/branding decision, security-support owner, and supported platform cells.
The ledger distinguishes a free connector from the editor engine license.

### Upstream policy

- Prefer configuration, WOPI, and PostMessage extension over source patches.
- Send general compatibility fixes upstream first. Handle vulnerabilities through
  coordinated private disclosure and embargo rules; apply immediate downstream
  mitigations when customer safety cannot wait for upstream publication.
- Keep a small, replayable patch queue with owner, reason, customer dependency,
  upstream issue/change, rebase result, tests, and removal condition.
- Never fork without an automated upstream-rebase rehearsal and a defined maximum
  supported divergence window.
- Treat CODE rolling releases as incoming source, not an automatic production
  update. Promote only source-bound, reproducibly built, compatibility-tested
  releases.

### Backend replacement

- No provider-specific identifier appears in reducer signatures or Drive schema;
  provider/session provenance is typed metadata, never an authority discriminator.
- A provider capability manifest reports launch modes, supported actions and
  formats, offline/co-edit behavior, platform/install requirements, entitlement,
  presentation features, conversion inputs, data egress, and vendor extensions.
- One mandatory Office Broker authority/isolation suite runs against every
  adapter. The WOPI profile runs only against WOPI adapters; WPS, Microsoft, and
  domestic proprietary protocols have discovery-derived adapter suites. Local
  adapters must additionally prove path containment, token handoff, application
  detection, offline base retention, and reconnect conflict behavior.
- Existing originals, metadata, byte identity, download, restore, and audit
  history remain usable when the editor is removed. Vendor-rendered visual
  comparisons may be temporarily unavailable until regenerated. Switching a
  tenant or space changes future launches, not historical identity.
- Vendor-specific derived renditions are disposable and rebuildable.

## Office Selection and Domestic-Technology Gates

Collabora remains the primary PoC because its MPL posture, open source, WOPI
support, multi-user editing, and ARM64/PPC64 availability fit Setjoin. It is not
declared the final exclusive backend until it passes the corpus, operational,
license, and procurement gates.

The scorecard includes:

- Microsoft Office, WPS, and macOS Office visual and round-trip fidelity;
- legacy WPS and iWork conversion, with conversion distinguished from lossless
  editing;
- comments, tracked changes, co-edit, reconnect, crash, restart, and conflicts;
- PPT notes, presenter mode, animation, fonts, audio/video, and export;
- browser, Electron, iOS, Android, HarmonyOS, and domestic browser behavior;
- named-user/concurrent-user/server licensing, free-development rights,
  proprietary embedding, white-label, redistribution, and customer self-hosting;
- signed evidence for Kylin/UOS and relevant CPU platforms. Merely running on
  Linux or ARM does not count as domestic certification;
- vulnerability response, LTS, reproducible updates, domestic support, HA, and
  10/50/200/500 concurrent editor measurements.

The 50-file minimum corpus is stratified by producer/version and feature risk:
Word layout/tracked changes/comments/fields/macros; Excel formulas/pivots/charts/
external data/macros; PowerPoint masters/notes/transitions/animations/fonts/media;
legacy binary Office; modern and legacy WPS; macOS Office; and iWork conversion.
Every case records original/render/round-trip digests, page or cell visual deltas,
semantic losses, warnings, and producer re-open results. Any unauthorized data
access, corrupt original, lost tracked change/comment, incorrect critical formula,
unopenable round trip, or silent active-content execution is a hard failure.
Visual tolerances and acceptable non-critical losses are fixed before the run,
not after results are known.

## Provider Core, WOPI Profile, and Security Policy

The mandatory profile covers discovery and proof keys, `CheckFileInfo`, `GetFile`,
`PutFile`, `PutRelativeFile`, LOCK/REFRESH_LOCK/UNLOCK/UNLOCK_AND_RELOCK, version
headers, idempotency, standard errors, request/body/time ceilings, token expiry,
revocation, and backend health. Optional operations are advertised and tested by
capability; absence cannot weaken authorization or save integrity.

The provider-core profile independently covers choice filtering, stable file and
base identity, launch/fence/finish lifecycle, capability downgrades, provider
switching, unavailable/unlicensed states, callback-to-reducer translation,
offline reconnect, and removal of any provider. WOPI success never substitutes
for provider-core conformance.

Active content is deny-by-default for the first release: no macro execution,
external data refresh, automatic external links, embedded executable objects, or
editor runtime egress. Production updates are fetched, verified, and promoted
out-of-band. Any future non-content support telemetry requires a separate opt-in
policy, schema allowlist, and exfiltration review. Password-
protected or encrypted files remain original-download-only until a separate
client-side secret-flow design passes. Upload and rendition paths retain malware,
archive-bomb, decompression, temporary-file, font, and resource limits.

The editor iframe uses an exact origin allowlist, restrictive CSP/frame ancestry,
typed PostMessage allowlists, non-referrer token delivery, redacted logs, and
short-lived file/session/action-scoped tokens. Guest edit, clipboard, download,
print, export, copy, and external-link behavior follow current effective Drive
capabilities and classification policy; unsupported enforcement fails closed to
preview or download denial.

## Drive History Contract

Drive presents a Time Machine-style History timeline. Its normalized event
envelope does not rewrite
source facts:

- stable event ID, schema version, source authority, and source event key;
- stable subject: tenant, space, node/file, version, device, or editor session;
- occurred-at and accepted-at timestamps;
- a source-assigned monotonic sequence within its tenant/authority stream; source
  adapters must persist or deterministically derive it from an immutable reducer
  audit/event key so rebuilds preserve order;
- actor and authenticated device/source;
- event class and source authority;
- before/after references or state digest;
- related version, branch, lock, permission, rendition, and editor session;
- visibility capability, retention class, integrity status, and source cursor.
- correlation/causation IDs, projector generation, projected-at time, and
  completeness/freshness bounds.

Ordering uses `(accepted_at, source_authority, source_sequence, event_id)` and is
stable under pagination. Projectors deduplicate by `(source_authority,
source_event_key)` and expose a cursor plus retained interval and missing event
classes. Every projection row carries tenant scope and is protected by the
repository's required RLS/isolation posture; every read also scopes tenant plus
authenticated user/capability. Event IDs and cursors are opaque, tenant-bound,
non-enumerable, and rejected cross-tenant without an existence oracle. The
current viewer's effective capability is rechecked at query time; historical
access is not inherited from past membership. A field-level matrix separately
governs actor, device, filename/path, permission principal/change, health,
digest, and evidence links. A redacted boundary appears only when the viewer may
know that the event exists; otherwise the row is omitted indistinguishably.

Attribution distinguishes callback principal, editor session, authenticated
participants, and claimed contributor. A consolidated save is never attributed
to one human at byte level unless the editor provides independently trustworthy
evidence; the UI displays provenance confidence.

The first source-coverage audit maps versions/saves/restores to Drive reducers,
moves/renames/trash to node lifecycle facts, permissions to ACL audit, locks to
checkout/editor-session facts, and sync/device/editor health to their own retained
event sources. Unsupported or purged intervals are explicit. Existing
`drive_space_as_of` ceilings are not described as complete reconstruction.

The initial Drive UI has three zoom levels:

1. **Current state:** owner, current version, editor/lock/sync health, and material
   warnings.
2. **Timeline:** grouped human-readable saves, moves, shares, permission changes,
   conflicts, restores, and device sync results.
3. **Forensic detail:** immutable IDs, exact timestamps, source authority, digests,
   audit facts, and downloadable evidence where authorized.

The file view starts with Drive's existing VersionDrawer and compare/restore actions.
The space view evolves the existing point-in-time view from a date form into an
interactive timeline. Device and system timelines reuse visual grammar and event
envelopes, not a shared authorization table.

Every visual view has a keyboard-operable and screen-reader table alternative,
logical focus order, non-color status labels, high-contrast and reduced-motion
behavior, localized copy, explicit time zone, and accessible text/metadata
comparison when a visual rendition cannot be interpreted.

## Storage Representation

Office saves remain immutable original bytes. OOXML is already a ZIP container;
small logical changes may rewrite many compressed bytes, so the Simon Willison
compressed-snapshot technique does not apply directly to authoritative Office
files.

After observed editor save cadence and semantic representation behavior are
known, a separate experiment may extract a disposable canonical semantic
representation for diff, search, change summaries, or compression. It cannot
replace the original, serve as a hidden alternate save authority, or cross
tenant/document/branch boundaries.

The archived compressed text-history plan remains evidence, not active work:
`retired-docs:superpowers/plans/archive/2026-08-16-compressed-text-history-storage-spike.md`.

## Approaches Considered

### Chosen: Unified design, independent execution tracks

This preserves one product experience while keeping Office procurement, history
UX, and storage experiments independently testable, deployable, and reversible.

### Rejected: One Office/Drive/Time-Machine mega-plan

It couples procurement, editor compatibility, UI, and storage promotion so a
license quote or compression failure blocks unrelated user value.

### Rejected: Office-only now, history later

It risks accepting editor save and identity semantics that later conflict with
the already-shipped Drive version DAG and point-in-time recovery model.

### Rejected: Port Collabora to Go

Go is appropriate for the WOPI/control plane. Rewriting the LibreOffice-derived
engine, browser editor, formula system, presentation engine, and interoperability
stack would discard the primary value of using Collabora.

## Success Criteria by Track

### V1 acceptance manifest

Before implementation starts, a version-controlled V1 manifest freezes exact

## Distribution Plan

The Office service is a separately deployed, pinned sidecar. Setjoin installation
and upgrade tooling publishes a compatibility manifest identifying supported
editor builds and deployment profiles. Self-supported builds include notices,
SBOM, reproducible build instructions, and corresponding source. Vendor-supported
builds require customer BYOL or a Setjoin OEM entitlement validated without giving
the editor direct access to Setjoin authority stores.

Web and online app WebViews reuse the Setjoin-hosted Office launch surface.
The local-open adapter invokes an administrator-allowed application already
installed and licensed on the user's device; Setjoin neither redistributes that
application nor represents its license as included. Native desktop/mobile
Collabora applications are not silently bundled; each has its own distribution,
signing, store, update, branding, and license gate.
