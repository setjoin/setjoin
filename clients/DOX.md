# clients/ — AGENTS.md

## Purpose

Native and shared client layer for the SetJoin platform. Covers: the cross-platform desktop shell (Win/Mac/Linux/信创 — **Electron**, see "engine map" below); the **iOS + Android mobile shells** (Tauri 2 Mobile WebView hosts — `clients/desktop/src-tauri` mobile cfg + `gen/apple`/`gen/android`); the **HarmonyOS NEXT native ArkTS + ArkWeb shell**; and the shared Rust crates (`guard-core`, `offline-core`, `capability-session`, `desktop-native`, `ohos-native`) that compile to native libraries and bridge to each platform (N-API/sidecar on Electron + HarmonyOS, UniFFI 0.32 on the mobile shells).

**Client-unification cutover DONE (2026-07-04):** the pre-unification Phase-12 native UIs — `clients/apple/` (SwiftUI), `clients/android/` (Jetpack Compose), and `clients/previews/` (static HTML mockups) — were **deleted**. They are superseded by the WebView shells that host the responsive webmail. The three live client families now are: **Electron desktop** (the only desktop shell — Tauri retired on desktop per ARCH-013), **Tauri 2 Mobile** iOS/Android (device-gated-verified), and the **HarmonyOS ArkWeb** shell. The desktop shell is **packaged with Electron** (electron-builder: macOS dmg, Windows msi, Linux AppImage/deb/rpm), not `cargo tauri build`; no workflow publishes releases yet (release builds and owner-side signing are planned separately); Tauri is packaged nowhere on desktop — it only builds the mobile targets (`tauri ios/android build`).

**Engine map (LOCKED 2026-06-23 — [ARCH-013](../docs/adr/ARCH-013-chromium-desktop-runtime-electron.md)):** the SvelteKit SPA runs on exactly **two** web engines, so the CSP + QA matrix is two-engine, not per-shell:

| Platform | Web engine | Shell |
|----------|-----------|-------|
| Windows / macOS / Linux / 信创 | Chromium (Electron) | **Electron** |
| Android | Chromium (System WebView) | WebView wrapper (Tauri 2 acceptable) + `window.setjoinNative` |
| HarmonyOS NEXT | Chromium M114+ (ArkWeb) | native ArkTS + ArkWeb shell |
| **iOS** | **WebKit (WKWebView) — forced** | WKWebView wrapper (Tauri 2 acceptable) + `window.setjoinNative` |

iOS is **WebKit-only**: Apple's alt-engine entitlement is EU-only and forbidden in China, so WKWebView is forced. Everywhere else is Chromium.

**Desktop shell = Electron, NOT Tauri (LOCKED 2026-06-23 — [ARCH-013](../docs/adr/ARCH-013-chromium-desktop-runtime-electron.md)):** Tauri 2 was retired on desktop because its WebKitGTK-4.1 dependency does not run on the reference 信创 OSes (Kylin V10 SP1 / UOS 1070 ship only WebKitGTK 4.0). Electron bundles its own Chromium (no host-engine dependency) and is the de-facto 信创 norm with LoongArch (龙芯) 适配 precedent (企业微信/钉钉); LoongArch Electron needs glibc ≥ 2.38 (New-World 龙芯). **guard-core + offline-core stay engine-agnostic native modules consumed via a dedicated Electron `UtilityProcess` sidecar by default (length-prefixed IPC; N-API in-process is the documented fallback)** — the sidecar process-isolates the C SQLCipher/SM4 cipher and decouples the cores from Electron's Node ABI — so a later **Qt + QtWebEngine** pivot (the documented fallback IF 等保三级 rejects Node's attack surface OR native 保密/电子签章/OFD/USBKey integration is needed) is a shell swap, not a core rewrite. The Electron shell ships **four build-gated security invariants** (each a CI gate, not a convention): Electron **Fuses**, **IPC sender-origin validation**, **session lockdown**, and an **N-2-major Electron patch-cadence gate** (the fifth ARCH-013 control, the **Ed25519-signed updater**, was **removed** from the shell on 2026-09-16 — see the In-app updater bullet below) — see "Electron security hardening" under Desktop features below.

**Client unification:** the responsive webmail is the single UI; native shells host it in a WebView and do JMAP/sync directly from the web app over HTTP. The native JMAP client crate `mail-core` was therefore deprecated and **removed** (C2). `guard-core` is the shared crate that backs **security** native capabilities (vault/TOTP/push/secure-store via the `window.setjoinNative` bridge); `offline-core` is the **app-agnostic offline substrate** (the encrypted SQLCipher store + generic sync primitives behind `window.setjoinNative.db`) that future offline-capable apps reuse by adding **only TypeScript** (a schema + a sync engine), no new Rust. The old SwiftUI/Compose `MailCore` call sites are gone with the deleted native UIs; every shell now hosts the webmail and calls native capability through the `window.setjoinNative` bridge.

**Platform crypto + custody (LOCKED 2026-06-23):** the offline store's at-rest cipher is AES-256 by default; the **国密 variant** uses **SM4 (SM4-GCM/SM4-XTS, never raw CBC)** wired into SQLCipher via `SQLCIPHER_CRYPTO_CUSTOM` from a **C/Rust** provider (RustCrypto `sm4`, or GmSSL/Tongsuo C) — **NOT** Go `emmansun/gmsm`, which is server-side only and cannot link into the Rust+C offline-core. The SQLCipher key is **hardware-wrapped** (Secure Enclave / StrongBox-or-TEE Keystore / HUKS / freedesktop Secret Service, Argon2id passphrase fallback on desktop) and biometric-gated. Pure-software modules cap at **GM/T 0028 安全二级**; a certified SKF/SDF (GM/T 0018) build variant is offered for 等保三级 contracts. See [ARCH-015](../docs/adr/ARCH-015-platform-crypto-sm4-key-custody.md). 国密 **TLS** is edge-proxy-terminated (TLCP/GB-T-38636) with the gateway/WebView speaking ordinary TLS 1.3 behind it — see [ARCH-014](../docs/adr/ARCH-014-guomi-tls-edge-proxy-posture.md).

**Guomi decisions status (re-checked 2026-07-04, Queue A5 slice 2): both ADRs are Accepted, not draft — there is nothing new to decide, only implementation gaps to track.** ARCH-014 (transport: edge-proxy primary, GmSSL native TLCP demand-gated on remote-党政 or iOS-国密) and ARCH-015 (client crypto: C/Rust SM4 via `SQLCIPHER_CRYPTO_CUSTOM`, hardware-wrapped biometric-gated key custody, GM/T 0028 Level-2 ceiling, SKF/SDF variant on demand) are the locked posture; re-litigating either was explicitly out of scope for this slice. Two implementation gaps exist under that already-decided shape, both already tracked elsewhere — this slice did not close either:
- **`SQLCIPHER_CRYPTO_CUSTOM` SM4 provider wiring** — `offline-core`'s `sm4-page-cipher` Cargo feature gate exists and the SM4-GCM cipher core (`cipher.rs`) is validated against the gmsm oracle, but the actual SQLCipher custom-provider registration is unwired (needs a forked/patched SQLCipher build — `bundled-sqlcipher-vendored-openssl` only supports `SQLCIPHER_CRYPTO_OPENSSL` at compile time). **Explicitly skipped this queue cycle** (`retired-docs:superpowers/plans/archive/2026-07-04-queue-program.md`'s skip-list: "SM4 page cipher (forked-SQLCipher dependency, niche)") — not a silent gap.
- **Hardware-backed key custody (Secure Enclave / StrongBox / HUKS wrap)** — not built on any shell yet. Every vault today unlocks by Argon2id-derived passphrase only (`guard-core`'s existing KDF); `vault.unlockBiometric()` is honest `false` everywhere (see the vault-subshape bullet above) precisely because there is no hardware-wrap-then-biometric-release path implemented. This is the concrete follow-up that would make mobile biometric unlock real, per ARCH-015 decision 2 — sized as its own crate-level feature (per-platform Keychain/Keystore/HUKS bindings + guard-core wrap/unwrap API), not a bug fix.

**Offline substrate (offline-core, 2026-06-23, LOCKED):** offline lives only in the native shells (the plain browser is online-only). Three layers, deliberately split: **guard-core stays SECURITY-ONLY** — it mints the per-store SQLCipher key (biometric-gated) and hands it to offline-core; it does **not** hold the mail cache. **offline-core** is a NEW app-agnostic crate (`clients/rust/offline-core`) that owns the encrypted SQLCipher store engine + **generic** sync primitives (outbound write-queue, sync state-token tracking, sync-issues/conflict store, retention/eviction, wipe) — it knows "named encrypted stores", **not** mail; it depends on guard-core for the key and applies it as `PRAGMA key` inside the native process (the key never crosses into JS). **App logic stays in TS**: each app brings its own schema + its own sync engine (mail = `mail-sync` over JMAP), driven over the **generic** `window.setjoinNative.db` bridge (`open(appKey)`/`exec(sql,params)`/`query(sql,params)`/`wipe(appKey)` — parameterized + allowlisted, **one encrypted DB file per app** so apps cannot read each other's store). This is explicitly **not** the deleted `mail-core` (which had a Rust sync engine + JMAP client): offline-core has zero protocol/mail logic. See `docs/adr/ARCH-012-offline-core-app-agnostic-store.md` and `retired-docs:superpowers/specs/2026-06-23-offline-mail-program-index.md`.

## Ownership

### Office local-open boundary (default OFF)

Electron `driveMirror` sub-shape v3 adds installed-editor choices and controlled
open for Microsoft Office, WPS Office, LibreOffice and Collabora Office. The
renderer supplies only `(spaceId,nodeId,appId)`. `MirrorService` resolves the
path from its encrypted mirror index, rejects root escapes/symlinks/non-Office
files, rechecks the live server `/office/choices?platform=electron` policy with
its scoped Drive bearer, then launches an allowlisted executable with
`shell:false`. No WOPI/Drive token or renderer-controlled filesystem path is
passed to the editor. Plain web and mobile do not advertise offline editing.

This doc owns everything under `clients/`. Protocol details, auth-server contract, JMAP method semantics, and gateway APIs are owned by `authserver/AGENTS.md`, `mailserver/AGENTS.md`, and `shared/AGENTS.md`. Rust crates (`guard-core`, `offline-core`, `capability-session`, `desktop-native`, `ohos-native`) are workspace-members of `clients/Cargo.toml` and are consumed by the shells as engine-agnostic native modules (N-API/sidecar on Electron + HarmonyOS, UniFFI on mobile); the desktop shell has its own build at `clients/desktop/`.

### FFI contract (the shared crate ABI)
- The shared crates are **engine-agnostic native modules** reached by each shell over its own binding: on Electron desktop a **`UtilityProcess` sidecar over length-prefixed request/response by default** (N-API in-process is the documented fallback — also decouples the cores from Electron's Node ABI so a major bump needs no N-API rebuild); **NAPI/ohos-rs** on HarmonyOS NEXT; **UniFFI 0.32** on iOS/macOS + Android. Keeping the modules engine-agnostic is what makes a future Qt+QtWebEngine desktop pivot a shell swap (ARCH-013), not a core rewrite.
- For HarmonyOS NEXT the crates compile to `ohos` targets (Rust tier-2 `aarch64`/`x86_64-unknown-linux-ohos`, `.so`) and load via **NAPI / ohos-rs (NOT UniFFI)**; SQLCipher via `rusqlite` bundled-sqlcipher + an `ohos` crypto link (`ohos-openssl`); biometric via `@ohos.userIAM.userAuth`. TypeScript type stubs in `clients/harmonyos/entry/src/main/cpp/types/`.
- `guard-core` uses UniFFI 0.32 for the **mobile** bindings. `build.rs` calls `uniffi::generate_scaffolding("src/<crate>.udl")`. On mobile the crate is linked into the Tauri shell (`clients/desktop/src-tauri` mobile cfg, `gen/apple`/`gen/android`), which reaches guard-core through the shell's own Rust — the standalone SwiftUI/Compose binding dirs (`clients/apple`, `clients/android`) were deleted with the pre-unification UIs.
- **The crate export interface is the stability boundary.** Changing a `guard-core` exported method signature requires regenerating bindings for every shell that consumes it (UniFFI for mobile; N-API stubs for Electron/HarmonyOS).
- **Pending regen (offline #1a):** `guard-core` gained UniFFI export `provision_store_key` (the per-store key provision, in addition to `meta_get`/`meta_set`/`meta_delete`). Desktop links Rust directly (no regen needed); Swift/Kotlin/HarmonyOS bindings must be regenerated before mobile uses them.

#### Electron security hardening (decided 2026-06-23 — [ARCH-013](../docs/adr/ARCH-013-chromium-desktop-runtime-electron.md) decision 4)

Electron's main/renderer split is **not** a security boundary by default. The shell ships four controls, **each a CI gate that fails the build on drift, not a convention** — the fifth ARCH-013 control, the signed updater, was removed 2026-09-16 (see the In-app updater bullet above); the bullets below are the live set plus the removed control's marker. `contextIsolation:true` is **table stakes, not the boundary** (a V8 patch-gap defeats it alone) — the boundary is `sandbox:true` + sender-origin validation + a minimal contextBridge + rapid Electron patching.

- **Sidecar by default** — guard-core (key-mint/unwrap) + offline-core (SQLCipher) run in a dedicated Electron **`UtilityProcess` sidecar** over a **length-prefixed request/response** channel; the main process never `dlopen`s the C cipher. N-API in-process is the documented fallback. Process-isolates the SM4/SQLCipher native code and decouples the cores from Electron's Node ABI. *Tests:* sidecar `exec`/`query` round-trip; a sidecar-crash fault-injection surfaces as a recoverable bridge error, not a main-process abort.
- **Electron Fuses (build-gated)** — at package time, **disable** `runAsNode`, nodeOptions (`enableNodeOptionsEnvironmentVariable`), nodeCliInspect (`enableNodeCliInspectArguments`), `grantFileProtocolExtraPrivileges`; **enable** `enableEmbeddedAsarIntegrityValidation` **+** `onlyLoadAppFromAsar` **together** (integrity validation is moot unless the app can only load from the validated asar), `enableCookieEncryption`, `loadBrowserProcessSpecificV8Snapshot`. *Test:* a CI `@electron/fuses` read-back fails the build on any drift from this locked set.
- **IPC sender-origin validation** — every `ipcMain` bridge handler validates `event.senderFrame.url` against an **exact allowlist of the bundled app origin** and **rejects unknown channels**, encoded **once** in a single `handle(channel, fn)` registration wrapper (not per-handler). The `db.exec(sql,params)`/`db.query(sql,params)` bridge stays a footgun unless the **statement allowlist is enforced in the sidecar/main** (never trust the renderer's SQL) — the offline-core contract. *Test:* a handler invoked from a spoofed/off-origin frame is rejected; an unregistered channel throws.
- **Signed updater — removed (not a live control).** The Electron Ed25519 updater module was deleted 2026-09-16 (DESKTOP-005, orphaned — see the In-app updater bullet above). ARCH-013's design (Ed25519 manifest binding SHA-256(artifact)+version, embedded pubkey, verify-before-install, owner-only temp dir, no unsigned downgrade, air-gap offline-signed sideload) is the spec for any reintroduction, not shipped behavior.
- **Session lockdown** — on the Electron `session`: a **session-level CSP** (`onHeadersReceived`) layered on the SvelteKit `<meta>` CSP; `webContents.setWindowOpenHandler` **denies** `window.open` (external links route through the `openExternal` bridge); `will-navigate` **denies** any off-origin navigation; `session.setPermissionRequestHandler` is **deny-by-default**. The `contextBridge` surface is the **minimal** `SetjoinNativeBridge` only. *Tests:* a Playwright e2e asserting `window.open` + an off-origin navigation are blocked and the app still hydrates (mirrors `e2e/csp.spec.ts`); a unit test that the permission handler denies an un-allowlisted permission.
- **Patch-cadence gate** — a CI gate **fails if the pinned Electron major is > N-2 behind the latest stable** (Electron backports Chromium security fixes only to current + last two majors).

- `native/BridgeProxy.ets` — the flat class registered via `registerJavaScriptProxy` (ArkWeb only supports a flat method list, not the nested `SetjoinNativeBridge` shape). Every registered method is **synchronous** (`methodList`, not `asyncMethodList` — its calling convention is undocumented even in official samples, all of which pass an empty array; every native call here is in-process blocking Rust with no real async I/O to gain from it). Two operations are genuinely async-native and can't return synchronously: `openExternal`/`share` are fire-and-forget (the SPA's `Promise<void>` contract doesn't need to wait); `pickFile` returns a request id immediately and delivers the picked file back via a correlation-id + `WebviewController.runJavaScript()` callback — unverified end-to-end without a device.
- `native/BridgeShim.ets` — the JS injected at document-start reshaping the flat `window.ohosNative` proxy into the nested `window.setjoinNative` contract (mirrors Electron's `bridge.ts`), wrapping every synchronous call in `Promise.resolve(...)`.
- `common/PushService.ets` — kept (HMS Push Kit; `push` is a **real** advertised capability here, unlike desktop's absence). `common/Theme.ets` — kept (backs `ServerConfigPage`'s styling).

**Device-gated (flagged, not silently dropped):** no HarmonyOS device/emulator boot exists in this sandbox — `hvigorw` compiles and packages the HAP but nothing here executes it. The MAM device-HMAC wire contract has no ArkTS-runtime test path; `cryptoFramework.createSymKeyGenerator('HMAC')` remains unverified on hardware. The v1 corpus plus `check-mam-lifecycle-conformance.sh` statically pins the three pure modules and each production composition caller. Harmony now receives the owning `MainPage` WebviewController clear callback and runs it only after guard-core's durable wipe latch; HAP compilation proves type/build integration, including `EntryAbility` foreground/background/destroy wiring, but not timer/check-in behavior, real ArkWeb deletion/relaunch, or restart persistence on hardware. Exactly-one composition is implemented in all three shells and remains default OFF; physical iOS/Android/Harmony HMAC, start/resume cadence, persistence, and wipe evidence remain OPEN. The `registerJavaScriptProxy` permission behavior is likewise unverified without a device.

### Shared Rust Crates

#### `capability-session` (`clients/rust/capability-session/`)

The **single process-local native capability authority** shared by Tauri Mobile and the Electron/Harmony N-API implementation. One `CapabilitySession` owns the optional unlocked `GuardCore` and the optional lazy `OfflineCore`; successful re-unlock replaces the full capability generation, while failed unlock is fail-closed and leaves the session locked. It owns locked/null/error semantics, secure KV delegation, crypto-profile normalization (`None`/empty → `standard`, `SMx` → `smx`), encrypted-store open/is-open/exec/query/wipe, and the generic recovery begin/chunk/commit/abort/read/ref/unref plane. It never returns a vault/store key.

Tauri and N-API remain adapters for app-data paths, runtime state/locking, serde/N-API error marshalling, and existing SQL/app-key gates. They must not add a second vault/offline slot or recreate `unlocked_core`/lazy-engine/profile rules. MAM lifecycle/rollout/scheduling, UI, OS notification/file/open helpers, and generated bridge IDL remain outside this crate; MAM may only borrow the session's already-unlocked `GuardCore`. `tests/session_matrix.rs` is the tempdir behavior corpus; `tests/adapter_source_contract.rs` prevents parallel state/helper regressions. The focused gate is `bash scripts/verify-architecture-r4.sh native`.

#### `guard-core` (`clients/rust/guard-core/`)

The **secure-value core**: vault · TOTP · ECDH-push · secure-store · wipe. It owns secure *values*, not the device-auth *lifecycle* — device checkin / token refresh / registration is HTTP owned by the platform bridge (desktop `bridge.rs`; the C2 `mam.rs`), not this crate. (There is **no passkey code** in guard-core; passkeys are browser WebAuthn served by authserver.)

UniFFI 0.32 library. Crate types: `cdylib` (mobile/HarmonyOS), `staticlib` (desktop link), `rlib` (workspace dep). Key deps: `totp-rs 5`, `p256 0.14 (ecdh+pkcs8)`, `aes-gcm 0.11`, `argon2 0.5`, `rusqlite 0.40 (bundled)`, `uniffi 0.32`, `zeroize`.

- **Vault open/create** (`GuardCore::new`) — opens or creates a plaintext SQLite file at `db_path` with **column-level** AES-256-GCM encryption (secrets and the label/issuer/kind metadata are ciphertext; the file is not whole-DB SQLCipher); derives a 32-byte AES key from `passphrase` via Argon2id (64 MiB, 3 iterations, 4-way parallelism, random 16-byte salt stored in `meta` table); `secure_delete=ON` so deletes leave no recoverable ciphertext; upgrades legacy cleartext metadata rows once (`metadata_enc` flag). `lib.rs`, `vault/kdf.rs`, `db/store.rs`.
- **TOTP add** (`add_totp_account`) — parses `otpauth://` URI, generates UUID, stores label/issuer/URI/seed AES-256-GCM-encrypted in SQLite. `lib.rs`, `totp/parser.rs`, `db/store.rs`.
- **TOTP generate** (`generate_totp`) — retrieves and decrypts the URI for an account, runs RFC 6238 TOTP. `lib.rs`, `totp/engine.rs`.
- **TOTP list** (`list_accounts`) — returns `Vec<TotpAccount>` (id, label, issuer) without decrypting seeds. `db/store.rs`.
- **TOTP remove** (`remove_account`) — deletes by account UUID. `db/store.rs`.
- **ECDH keypair** (`get_or_create_ecdh_public_key`) — generates P-256 keypair if absent; stores encrypted private key in `meta`; returns DER-encoded public key for server registration. `lib.rs`, `ecdh/mod.rs`.
- **Push challenge decrypt** (`decrypt_push_challenge`) — ECIES decrypt: parse 65-byte ephemeral public key + 12-byte nonce + ciphertext; ECDH shared secret → HKDF-SHA256 → AES-256-GCM decrypt. Wire format: `[65 eph_pub | 12 nonce | ct+tag]`. `lib.rs`, `ecdh/mod.rs`. **The exact cross-end contract (curve, point encoding, HKDF salt/info, AEAD params, key encodings) is `docs/standards/PUSH_ECIES_CONTRACT.md`** — the single source of truth both this end and the server's `authserver/internal/authn/push_native.go EncryptECIES` cite. A committed cross-end golden vector pins both ends byte-for-byte: Rust `tests/ecdh_golden.rs` decrypts a server-produced ciphertext; the Go `push_ecies_golden_test.go` reproduces the identical bytes via a fixed ephemeral key + nonce. Any KDF/format/encoding drift fails a test, not a push login.
- **Push approval signature** (`sign_push_approval`) — accepts one generated-binding-safe `PushApprovalAssertion` record, constructs the closed `setjoin.push-approval.v1` string/integer envelope from those decrypted notification fields, canonicalizes it with lexicographically ordered keys and signs it using ECDSA P-256/SHA-256 with the same persisted device key. It returns fixed 64-byte `r||s` as unpadded base64url; arbitrary-byte signing is not exposed. The server approval endpoint accepts no code/nonce-only fallback and returns no session token.
- **Secure key/value store** (`meta_get`, `meta_set`, `meta_delete`) — small per-key values AES-256-GCM-encrypted with the vault key and persisted in the `meta` table under an `ss:` namespace (base64-encoded ciphertext, kept separate from `kdf_params`/`ecdh_sk_enc`). Readable only while unlocked. Backs the desktop/mobile `secureStore` bridge. `lib.rs`, `db/store.rs`.
- **Per-store key provision** (`provision_store_key(app_key)`) — derives a 32-byte HKDF-SHA256 subkey from the vault root key, scoped by `app_key` (`'mail'`, `'drive'`, …) so distinct apps get independently-keyed stores. Consumed IN-PROCESS by offline-core's `apply_pragma_key`; the 32 bytes NEVER return to JS or cross the bridge. `lib.rs`, `vault/kdf.rs` (`derive_subkey`).
- **Device / MAM state + vault wipe** (`store_device_id`, `store_mam_policy`, `get_mam_policy`, `mark_wiped`, `is_wiped`) — device id and policy snapshots are in-memory; the non-secret wipe latch is durable as `meta.wiped` in the vault database, reloads on vault reopen, and survives restart until successful re-enrolment calls `clear_wiped`. Guard-core remains the value store; shell adapters consume pure transitions and own HTTP/effects. `lib.rs`. *(The removed device-auth stubs stay removed: guard-core does not own device auth.)*
- **`MamPolicy`** — the MAM-policy snapshot struct cached by `store_mam_policy`/`get_mam_policy`. `provider.rs`.
- **Database schema** — `meta(key TEXT PK, value TEXT)` for KDF params + ECDH key + `ss:`-namespaced secure-store values; `totp_accounts(id, label, issuer, uri_enc, seed_enc)`. `db/schema.rs`.
- **AES-256-GCM helpers** (`db/store.rs`) — `encrypt(key, plaintext) → Vec<u8>` and `decrypt(key, ciphertext) → Vec<u8>`; random 12-byte nonce prepended.

#### `offline-core` (`clients/rust/offline-core/`) — app-agnostic offline substrate (offline #1a, created)

The **app-agnostic offline store engine**: the one native substrate the whole suite reuses for offline. It owns the **encrypted SQLCipher store** + **generic sync primitives** (outbound write-queue, sync state-token tracking, sync-issues/conflict store, retention/eviction, wipe). It knows only **"named encrypted stores"**, not "mail" — **no JMAP, no protocol, no email logic**.

- **Depends on guard-core for the key** — guard-core mints the per-store SQLCipher key, **hardware-wraps** it (Secure Enclave / StrongBox-or-TEE Keystore / HUKS / freedesktop Secret Service; Argon2id passphrase fallback on desktop), biometric-gated; offline-core receives the unwrapped key in-process and applies it as the SQLCipher `PRAGMA key`. The key never crosses the bridge into JS, never lands on disk in usable form. (guard-core stays security-only; the mail cache is **not** in guard-core.) See [ARCH-015](../docs/adr/ARCH-015-platform-crypto-sm4-key-custody.md).
- **One encrypted DB file per app** — keyed by an `appKey` namespace (`'mail'` now; `'drive'`/`'calendar'`/`'contacts'` later). Apps cannot read each other's store.
- **Generic store bridge** — exposed over `window.setjoinNative.db`: `open(appKey)` / `exec(sql, params)` / `query(sql, params)` / `wipe(appKey)`. Statements are **parameterized and allowlisted in the native side (the Electron `UtilityProcess` sidecar / main process, never the renderer)** — no arbitrary cross-app SQL; trusting the renderer to send only safe SQL is a footgun (ARCH-013 decision 4). Real SQL + **FTS5 body search**.
- **App logic stays in TS** — each app brings its own schema (migrations applied through the bridge) and its own sync engine (mail = `mail-sync` over JMAP). **No per-app native crate.** Drive later = a new TS sync engine + schema against this same crate — **zero new Rust**.
- **Generic encrypted blob plane (U6, reused by connectivity E3)** — `offline-core::blob` provides content-addressed, refcounted, bounded begin/chunk/commit/abort and open/read/close primitives under the app store directory. The shell bridges expose handles and chunks only; no method accepts or returns a whole message. TS owns mail receipt/artifact/upload metadata. Its non-empty write path is capped at exactly 8 GiB; zero-byte attachment completion stays in the TS controller. Rust gates cover interrupted reopen/resume, independent interleaved transfers, exact size/hash promotion, and a planted marker absent from the SQLCipher database plus WAL/SHM bytes. Electron/Tauri unit tests and both real mobile simulators gate the existing continuity use; physical iOS/Android persistence/resume remains release evidence, so client-recovery/background flags stay OFF.
- **Encryption** — SQLCipher whole-DB page-level: AES-256 default; **国密 SM4 (SM4-GCM/SM4-XTS, never raw CBC)** via a **C/Rust** custom-cipher provider wired with `SQLCIPHER_CRYPTO_CUSTOM` — RustCrypto `sm4` or GmSSL/Tongsuo C, **NOT** Go `emmansun/gmsm` (server-side only; cannot link into the Rust+C crate) — validated against GM/T 0002/0003/0004 KATs in CI (offline #3); PQ deferred. Pure-software caps at GM/T 0028 安全二级; SKF/SDF build variant for 等保三级. See [ARCH-015](../docs/adr/ARCH-015-platform-crypto-sm4-key-custody.md).
- **Explicitly NOT the deleted mail-core** — mail-core carried a Rust sync engine + a JMAP client. offline-core has none of that; the sync engines are TS. See `docs/adr/ARCH-012-offline-core-app-agnostic-store.md`. *(Spec: `retired-docs:superpowers/specs/2026-06-23-offline-mail-program-index.md`; the crate is created in offline #1a — workspace member + UniFFI bindings land then.)*

#### `mail-core` — REMOVED (C2)

The native JMAP client crate (`clients/rust/mail-core/`) was **deleted** under client unification: the WebView hosts the responsive webmail, which speaks JMAP/sync directly over HTTP, so a parallel native JMAP/sync/send implementation is redundant. Its former responsibilities (JMAP session discovery + multi-call, mailbox/email/calendar/contacts/tasks sync and CRUD, send, free/busy, `.well-known/setjoin` capability negotiation, the RFC 8887 push stub, the local SQLite cache) now live in the webmail web app, not in a native crate. No source under `clients/` depends on it; the desktop crate's dependency and the workspace member were removed with it.
