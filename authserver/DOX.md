# authserver — DOX child AGENTS.md

Parent: `../AGENTS.md` (root). Project-wide rules live there; this file owns only the auth server area.

## 1. Purpose

Standalone authentication server (`setjoin.com/authserver`). Issues and rotates JWTs; handles every pre-auth MFA method (TOTP, passkeys, push, backup codes); provides OAuth2 token introspection, SAML 2.0 SP, OIDC RP and OIDC OP (IdP mode), Kerberos/SPNEGO stub, AD/LDAP connector, the 8-step threat pipeline, conditional access, and device trust. The mailserver gateway proxies all `/auth/*` routes to this process.

## 2. Ownership

**This doc owns:** `authserver/cmd/authserverd/`, `authserver/internal/`, `authserver/sql/`, `authserver/config.yaml`, `authserver/go.mod`.

**Stays with parent/shared:**
- The 8-step threat pipeline engine lives in `shared/threat/` — authserver consumes it, does not define it.
- JWT claims type (`jwtutil.Claims`) and token type constants live in `shared/jwtutil/`.
- `shared/pwhash`, `shared/cryptokey`, `shared/httputil`, `shared/toggle`, `shared/pgnotify`, `shared/pgxutil`, `shared/middleware` (CSRF, RequestID), `shared/dbscope` (GUC tenant-scope seam), `shared/reducererr` (BZ decode/classify — promoted here by arch #A8; `terms.go`/`auth.go` were the two hand-rolled hold-outs before the move) — consumed here, not owned here.
- Conditional access policy evaluation logic is in `shared/threat.PolicyEngine`; authserver wires its SQL-backed `threat.PolicyStore` via the shared `threat.NewPolicyStore` (the pgx adapter is owned by `shared/threat`, not duplicated per module).

## 3. Local Contracts

### Shared PostgreSQL cluster

- Auth server and mailserver share one PG cluster. Auth tables are in the same database (`mailserver`). **Post-collapse (ARCH-007):** the auth tables now live in the single combined `mailserver/sql/migrations/V001__baseline.sql` (the FK graph is one connected component — `users` is co-owned); the pre-collapse `authserver/sql/{schema,migrations}` are archived non-executed under `authserver/sql/_archive/` for provenance.
- Migration version is checked at startup (`SELECT COALESCE(MAX(version),0) FROM schema_migrations`); the required version is derived from the shared embedded `mailserver/sql/dbschema/V<NNN>__*.sql` set via `dbschema.ExpectedVersion()`, so authserver, mailserver, and mailctl fail closed on the same schema head without a manually synchronized constant.
- Auth server uses the `oauth_tokens`, `users`, `guest_accounts`, `guest_invites`, `passkey_credentials`, `push_devices`, `push_mfa_challenges`, `saml_sp_registrations`, `conditional_access_policies`, `used_saml_assertions`, `login_events`, `password_history`, `used_password_reset_tokens`, `devices`, `device_policy`, `device_events`, `oidc_auth_requests`, `signing_keys` tables.

### Three DB connections

- PgBouncer pool (`DB_DSN`) for all normal queries.
- Worker pool (`DB_WORKER_DSN`) for the cross-tenant, FORCE-RLS-denied guest-invite accept flow. It is carried as the compile-time-distinct `pgxutil.WorkerPool`; when unset it aliases `DB_DSN`, and authserver opens a separate pool only when the DSNs differ.
- Dedicated direct PG connections (`DB_DIRECT_DSN`) for asynchronous listeners. Feature toggles, SAML reload, OIDC reload, and Conditional Access each own an independent reconnecting `shared/pgnotify.Listener`, so one external federation reload cannot stall another cache or a security boundary. All fall back to `DB_DSN` if `DB_DIRECT_DSN` is empty.

### Startup order (mandatory)

`cmd/authserverd/main.go` steps, in order:
1. Load config + start SIGHUP hot-reload goroutine. Immediately after, resolve the auth listen address (D-AUTHSERVER-CMD-AUTHSERVERD-005): explicit `LISTEN_ADDR` > explicit YAML `listen.addr` (presence-tracked by `Config.ListenAddrExplicit` — an explicit `":8443"` equal to the compiled default still wins, AUTHSERVERD-005 finding 1) > `AUTHSERVER_URL` host:port (install.sh parity, stock port 8443) > compiled `:8443`. The resolved address + source (`listen_source`) are logged; boot REFUSES — schema-mismatch precedent — when the effective bind is wildcard/non-loopback while `AUTHSERVER_URL` is absent or not a usable http(s) URL (remediation: loopback bind via `authserver.listen.addr`/`LISTEN_ADDR`, or a valid `AUTHSERVER_URL`). A valid-but-non-loopback URL-derived bind WARNs instead (split-host is supported). Boot-time only; reloads never re-arm it.
2. Open PgBouncer pool plus the `DB_WORKER_DSN` pool (aliasing the first pool when the DSNs match); derive the schema head from the shared embedded mailserver migrations and refuse startup when `schema_migrations` is behind it.
3. Initialize feature toggles; the independently connected listener is bound through `shared/toggle.BindNotifications`. Durable `config_changed` registration and the authoritative post-LISTEN `FeatureFlags.Reload` are boot-critical, closing the registration snapshot gap; cancellation unregisters both notification and reconnect callbacks.
4. Initialize GeoIP reader; build `threat.ThreatConfig`; call `threat.New()`; start `threat.RefreshFeeds()` goroutine.
5. Create the policy store via `threat.NewPolicyStore(pool, logger)`; build `threat.PolicyEngine`; wire `SetPolicyEngine`; start its independent durable `LISTEN conditional_access` listener. Every notification and reconnect invalidates both policy caches and reloads break-glass state; a reload failure clears stale break-glass exclusions and keeps reconnecting.
6. Start `token.CleanupRotatedTokens` ticker (every minute).
7. Build `token.JWTProvider` (HS256 or SM2 depending on `CryptoProfile`), then `token.Load` the ES256 signing keystore (`signing_keys`) and attach it via `JWTProvider.WithKeySet(ks, ParseSigningAlg(JWT_SIGNING_ALG))` (fails closed on keystore load error).
8. Derive cookie key (`cryptokey.DeriveCookieKey`).
9. Initialize SAML SP registry (`federation.NewSAMLSPRegistry`) if `SAML_ENABLED` + cert/key files are present.
10. Initialize OIDC RP provider (`federation.NewOIDCRPProvider`) if `OIDC_ENABLED`.
11. Start independent durable federation live-reload listeners for SAML and OIDC. Each subscribes before its initial authoritative reload and repeats that order after reconnect. Invalid provider rows are omitted from the atomically replaced healthy snapshot; a global query/scan failure installs an empty snapshot. The listener keeps retrying while configuration remains broken, and the two registries never share a concurrent `pgx.Conn`. V170 emits canonical SAML and bounded `oidc_provider_*_config` notifications for insert, update, and delete.
12. Initialize OIDC OP (`op.Provider` via `zitadel/oidc`) if `OIDC_PROVIDER_ENABLED`.
13. Initialize `authn.PasskeyProvider` (WebAuthn).
14. Initialize `authn.NumberMatchPushProvider` (VAPID push MFA) if `VAPID_PRIVATE_KEY` set; wire APNs / FCM / HMS dispatchers. The transports now live in **`shared/push`** (extracted so the mailserver mail-push worker shares them) — `push.Build(push.LoadConfig())` constructs every configured provider from the env and logs each configured/absent/**INVALID** (loud). The three native dispatchers satisfy `push.Dispatcher` and live in a `map[push.ProviderKind]push.Dispatcher`; `SetNativeDispatchers` **merges** non-nil providers. authn keeps its ECIES/MFA payload building (`EncryptECIES` in `push_native.go`) and its inline webpush MFA send; it only delegates transport to `push.Dispatcher.Send`. (FCM now takes a service-account JSON that self-refreshes its OAuth token — the old static `FCM_ACCESS_TOKEN` / raw-SA-as-bearer wiring, which never refreshed, is gone.)
15. Build `handlers.AuthHandler`; register routes; start HTTP/2 server.

### Token signing

- **Issuance algorithm** is selected by `JWT_SIGNING_ALG` (default `HS256`) + the crypto profile. The signing seam is `JWTProvider.sign()`; verification is `JWTProvider.Validate()` — both dispatch on the header `alg`+`kid` and **dual-verify** (HS256 + SM2 + ES256) so a migration never has a window where a freshly-issued token can't be verified.
  - **HS256** (default, `kid: authserver-hmac-1`): HMAC-SHA256 under `JWT_SECRET` (≥ 32 chars).
  - **SM2** (Xinchuang profile, `kid: authserver-sm2-1`): SM2-signed, `SM2_PRIVATE_KEY_FILE`. Hybrid profile: SM2 primary, HS256 accepted for validation.
  - **ES256** (asymmetric, ADR-005): ECDSA P-256 under the **DB-backed encrypted keystore** (`signing_keys`, authserver V009). Opted in via `JWT_SIGNING_ALG=ES256` (requires a loaded active key; otherwise sign() falls back to HS256). The token's `kid` is the active key's kid; resource servers verify offline against the published first-party JWKS — no shared secret. Each `kid` binds to exactly one `alg`; Validate REJECTS a token whose header `alg` ≠ the kid's registered `alg` (RFC 8725 alg-confusion closure). `jku`/`x5u`/embedded-key header fields are never read.
- **The KeySet seam** (`internal/token/keyset.go`) owns generate/load, the active signer, the kid→public-key verifier map (active + retiring keys only — `retired` keys drop out and no longer verify), and JWKS marshaling. `token.Load(ctx, pool, encKey, profile)` load-or-generates on boot: if no `active` key exists it mints a P-256 keypair, encrypts the PKCS#8-DER private key via `cryptokey.EncryptColumn` (AES-256-GCM column envelope, key = `DeriveDBEncryptionKey(JWTSecret, profile)`), and INSERTs it `active`. Generation is race-safe via the partial-unique-active index (a losing concurrent INSERT is a no-op; the loser re-SELECTs the winner). The KeySet is loaded even on the HS256 default so the JWKS publishes the public key before issuance flips. The single ES256 verification primitive is `shared/jwtutil.ParseES256` (ES256-only `WithValidMethods`, kid required, key resolved solely via the caller's key set), shared with the gateway.
- Audience claim is always `"mailserver-gateway"`. Issuer is `JWT_ISSUER` (default `"mailserver"`); the gateway must match.
- OIDC IdP tokens: RS256, key at the configured `OIDC_PROVIDER_PRIVATE_KEY_FILE` (default `/opt/setjoin/oidc_key.pem`), managed by `federation.OIDCKeyManager` — a **separate** key/endpoint (the OIDC OP `/keys`), untouched by ADR-005.

## 4. Features / Capabilities

### Password authentication

- **Password login** (`POST /auth/login`): stored-prefix-aware bcrypt/SM3 verify against `users.password_hash`; checks `enabled = TRUE`. Implementation: `loginHandler.Login` → `verifyPassword` → `pwhash.VerifyPasswordHash` in `internal/handlers/auth.go` (reached via the embedded `AuthHandler`, so the route stays `authH.Login`). Issues an **HttpOnly** session cookie — this is the ONLINE session token (not a key); the offline mail store key is provisioned by guard-core's `provision_store_key(appKey)` entirely in the native process and never passes through this endpoint.
- **Session cookie `Secure` behind a proxy (wave-7)**: every cookie authserver sets (`setAccessCookie`/`setAccessCookiePersist`, OIDC `oidc_state`/`oidc_nonce`/`oidc_provider`, WebAuthn `wa_reg_sess`/`wa_login_sess`/`wa_login_uid`, `clearAuthCookie`) computes `Secure` as `cookieSecure || r.TLS != nil || forwardedHTTPS(r)` — `cookieSecure` fires when authserver terminates TLS itself (`TLS_CERT` set); `r.TLS != nil` when this process is the direct TLS listener; `forwardedHTTPS` (auth.go) is the new leg: it honors `X-Forwarded-Proto: https` so the standard single-node deploy (the mailserver gateway terminates TLS at `:443` and proxies to authserver over `127.0.0.1` plain HTTP — authserver's own `r.TLS` is nil on that hop) still ships a Secure cookie. `forwardedHTTPS` only trusts the header when `(*deps).isTrustedProxyPeer(r)` accepts the immediate peer/`RemoteAddr` — since AUTHSERVERD-005 finding 3 that means **loopback always, plus only the networks the operator allowlisted via `AUTH_TRUSTED_PROXY_CIDRS`** (default empty = loopback-only: a private-range peer is NOT implicitly trusted, because every RFC 1918/4193 neighbor could otherwise forge the header) — OR the operator sets the blanket `AUTH_TRUST_PROXY` (trusts any peer, e.g. a separate proxy host no allowlist expresses) — never for an arbitrary peer (header-spoofing closure). `NewAuthHandler` parses the allowlist to `[]*net.IPNet` and fail-closes the whole list to loopback-only on any unparseable entry (defense-in-depth behind config validation). The gateway already sets the header correctly via stdlib `httputil.ProxyRequest.SetXForwarded()` (`mailserver/internal/authproxy/proxy.go`), keyed off the GATEWAY's own `r.TLS` (the real client-facing listener) — no gateway change was needed. Proxy peers must also be **last-hop** truthful (rightmost XFF semantics: `docs/guides/TRUSTED_PROXY_DEPLOYMENT.md`). Tests: `authserver/internal/handlers/auth_cookie_test.go`.
- **Password policy endpoint** (`GET /auth/password-policy`): returns configurable min-length and character class requirements from `system_config` plus the shared `maxBytes=72` cross-profile credential-writer ceiling. No auth required (client reads before submitting). The limit is UTF-8 bytes, not code points; SQL and Go reject above-bound inputs as 400-class validation failures before hashing or state writes. `internal/handlers/auth.go:PasswordPolicy`.
- **Password complexity validation**: calls PL/pgSQL `validate_password($1, $2)` during login, password change, and forgot-password reset.
- **Common password check**: `shared/pwhash.CheckCommonPassword` blocks bcrypt-common passwords before accepting new passwords.
- **Password must not contain email**: `passwordContainsEmail` helper prevents local-part/domain embedding.
- **Password history** (`password_history` table): depth configurable via `system_config.password_history_depth` (default 5); enforced on password change with bcrypt comparison.
- **`must_change_password` flag**: login issues a `TypeForcePasswordChange` JWT instead of an access token when set; client must call `PUT /auth/password` first.
- **MFA enrollment enforcement**: `mfa_status($1)` can return only `exempt`, `enrolled`, `enrollment_required`, or `optional`. For password-first admission, only challengeable TOTP or Push counts as `enrolled`; normalized passkeys remain visible as inventory but are their own passwordless entry point, and the retired `users.webauthn_credentials` JSON never satisfies the gate. Password login fails closed with a retryable 503 on query, decode, missing-row, or unknown-status failures; it never treats an unreadable policy as MFA-exempt. `enrollment_required` issues a five-minute `TypeMFAPending` proof, not an access or force-password-change token. `POST /auth/totp/enroll/setup` accepts only that pending token and stores a latest-wins pending secret while the user is enabled, unenrolled, and still policy-required. `POST /auth/totp/enroll/confirm` locks the user row, rechecks live policy, enforces the shared five-failure/15-minute TOTP lockout and replay window, enables TOTP exactly once, writes the audit event in the same transaction, and mints the `pwd+otp` session through the normal DPoP/Conditional-Access completion path. Self-service first enrollment is intentionally trust-on-first-use after the password proof; deployments needing administrator-vouched enrollment must use a different bootstrap policy.
- **Password change** (`PUT /auth/password`): acquires `identity_auth_local_mint_fence` before the user-row mutation lock; old-password and history verification use stored-prefix dispatch under `FOR UPDATE`; complexity + history + email-similarity checks; profile-aware re-hash; and complete first-party revocation in the same transaction (`oauth_tokens`, all-session denylist, pending identity elevations, `sessions`, and `ws_subscriptions`). Forgot-password reset uses the same lock order, hash seam, and complete revocation. This prevents a concurrent password/MFA completion from publishing a refresh-family anchor after the credential was changed. Best-effort AD password write-back uses the **injected `ConnectorManager`** (`h.connectors.CachedGet("ad").ChangePassword`), not a connector package global. `internal/handlers/auth.go:ChangePassword`, `internal/handlers/forgot_password.go`.

### JWT lifecycle

- **Access token issue** (`TypeAccess`): HMAC-SHA256 or SM2 signed; audience `mailserver-gateway`; carries `user_id`, `email`, `is_admin`, optional `device`, `mam`, `risk` (CA-3b: populated from the `user_risk` row via `threat.RiskFromRow` at login (`riskClaimFor`) AND on every refresh rotation (`readRisk`, so it survives `issueAndStore`), gated `feature.user_risk`; both reads run through `dbscope.RunUserScoped` because `user_risk` is FORCE-RLS and a bare `setjoin_app` pool sees zero rows; nil/omitted when the user is clean, the toggle is off, or the scoped read fails under the established fail-open scoring policy), `domain_scope`, `acr`, `amr`, and (Guest Accounts G0, P13) `acct` claims.
- **`acct`/`AccountType` claim (Guest Accounts G0)**: `""` = member, `jwtutil.AccountTypeGuest` = guest — derived ONCE per mint from `is_guest_account($1)`, never trusted from a caller-supplied value. Minted at **all four** access-token paths, each fail-CLOSED on a lookup error (deny the token rather than mint a guest a member claim, or vice versa): (1) the `Login` seam — `h.pool.QueryRow(... is_guest_account ...)` immediately before building `token.IssueInput{AccountType: ...}`, threaded through `TokenService.Issue` → `IssueAccessCA(..., accountType string)` (the trailing param every `IssueAccessCA` call site now carries — `IssueAccessCA` with a nil `cnf`/`sif` stays byte-compatible with the pre-G0 `IssueAccessFull` shape); (2) the refresh re-mint chain (`refresh.go`'s `issueAndStore` re-derives `accountType` from the satellite on every rotation — a guest's status can change between logins, so the claim is re-checked, not carried forward blindly — and re-mints via the SAME `IssueAccessCA`); (3) `IssueImpersonation(targetUserID, targetEmail, adminActorID, accountType string)` — a NEW trailing param; impersonating a guest yields a guest-claimed token (the gateway's `chain.AuthenticateRequest` satellite belt would force it anyway, so this is honesty at mint time, not the sole enforcement); (4) the Drive-native token, minted gateway-side (`internal/drive`, outside this server) copying the same claim forward. Guarded by `internal/token/account_type_mint_test.go`'s mint-site inventory (fails if a new mint path is added without setting `AccountType`) + `internal/token/guest_refresh_test.go` (the refresh re-derivation). The gateway's `chain.applyGuestBelt` (`mailserver/internal/auth/chain.go`) is the UNCONDITIONAL backstop — it does not trust this claim either, re-deriving it from the satellite on every request; see `mailserver/internal/AGENTS.md`'s `auth` package row. **The `admin_role` (`role`) claim was REMOVED by the RBAC cut-over** (`V017` dropped `users.admin_role`) — authorization flows from the resolved `Permissions` set, not an enum. TTL default 1 h. `internal/token/jwt.go:IssueAccessWithDevice` / `IssueAccessFull` (the acr/amr-aware variant). Every access token now carries a **unique `jti`** (16-byte random hex, CA-3 per-session denylist substrate; inert until CA-3a ships — no revocation checks performed). Every impersonation token also carries a `jti`. `Claims.JTI` (`shared/jwtutil/types.go`).
- **`is_admin` is DERIVED at mint time, NOT read from `users.is_admin`** (RBAC cut-over): every mint-path user lookup (`verifyPassword`, `lookupUser`, `lookupUserByOIDC`/`BySAML`, `resolveUserByAddress`, JIT `RETURNING`, and `token.RefreshTokens`) computes `is_admin` as `EXISTS(unexpired admin_role_assignments)` (constant `handlers.isAdminExprSQL`, `users.id`-qualified to avoid binding the subquery's own `admin_role_assignments.id`) — byte-aligned with `session.go` (Me) and `shared/permissions.Resolve`. The vestigial `users.is_admin` column is retained but **no longer authoritative**: neither `AssignMember` nor SSO sets it, so reading it minted `IsAdmin=false` for a freshly-granted admin, and the gateway (`chain.go`, which skips `permissions.Resolve` when `!IsAdmin`) then 403'd every admin route. After the derivation, `claims.IsAdmin` is true iff the user holds a governed assignment, so the `chain.go` gate is correct unchanged.
- **Authentication-context claims (`acr`/`amr`)**: the access token signals the MFA/AAL actually performed so it's enforceable downstream (conditional-access step-up). `amr` per RFC 8176 — `pwd` (password), `otp` (TOTP / backup code), `hwk` (WebAuthn passkey), `swk`+`user` (number-match push: software-key proof-of-possession + human presence), and `mfa` once ≥2 distinct factors complete. `acr` per NIST AAL — `aal1` single-factor, `aal2` once `mfa` is derived. The derivation lives in the pure `shared/jwtutil.DeriveAuthContext` / `AuthContextFromFactors` (with `ACRSatisfies` for the AAL ladder). Each MFA-verify handler threads its factor set into `AuthHandler.issueTokensWithFactors`; the first factor is carried in the MFA-pending token (`IssueMFAPending` = `[pwd]`, `IssueMFAPendingWithAMR` for passkey-first = `[hwk]`) and combined via `factorsFromMFAPending` with the second factor. Both claims are `omitempty` — legacy `IssueAccess` emits neither, so existing tokens are byte-for-byte unchanged.
- **MFA-pending token** (`TypeMFAPending`): 5-min short-lived JWT issued when MFA verification or mandatory first enrollment is required; exchanged via `/auth/totp/verify`, `/auth/backup-codes/verify`, or the paired `/auth/totp/enroll/{setup,confirm}` endpoints. A normalized SSO step-up includes `IdentityFenceClaim` with the exact source/link IDs and generations; every completion restores it through `issueTokensFromMFAPending` and rechecks `identity_auth_mint_fence` transactionally before publishing a session. A local password-first challenge includes `CredentialFence`, a signed SHA-256 digest of the bcrypt hash that was actually verified; completion acquires `identity_auth_local_mint_fence`, compares the current hash version in constant time, and refuses stale proof after password change/reset. The claim is opaque and is not a password verifier. First-enrollment setup applies the same exact fence before persisting a pending TOTP secret; accepted confirmation commits TOTP activation, its audit event, and the token-family anchor in one transaction, and buffers all token cookies/body until that commit succeeds. (Number-match push does **not** complete in-band — `/auth/push/verify` rejects the answer; the device approves out-of-band via `/auth/mfa/approve` and the browser/webpush flow completes by polling `/auth/push/status`. See "Push MFA" / C10.) `IssueMFAPendingWithFences`.

- **Force-password-change token** (`TypeForcePasswordChange`): 5-min JWT; client must change password before proceeding. `IssueForcePasswordChange`.
- **Password-reset token** (`TypePasswordReset`): 5-min JWT with random `jti`; single-use (tracked in `used_password_reset_tokens`). `IssuePasswordReset`.
- **Refresh token issue** (`TypeRefresh`): default 30 d TTL; stored as SHA-256 hash in `oauth_tokens`. `IssueRefreshWithFamilySession` carries the immutable refresh-family controls: `family_id`, DPoP `cnf`, the login-derived device claim, sign-in-frequency policy, and the original `auth_time`. New logins generate the family and, when SIF applies, one authentication timestamp; both access and refresh tokens receive that same timestamp. Every normal and grace-window rotation re-embeds these controls into the next access and refresh token, so refresh cannot silently drop quarantine/wipe state, unbind DPoP, or reset the SIF clock by assigning a fresh `iat`. The database anchor keeps the family id; the remaining controls are taken only from the validated presented refresh JWT.
- **Refresh token rotation** (`POST /auth/refresh`): acquires `identity_auth_person_fence` before any `oauth_tokens` row lock and holds it through successor commit; validates the signed `user_id` equals the stored anchor owner; then uses `FOR UPDATE` serialization, marks the old row `rotated_at`, and inserts the successor with `previous_token_hash`. The same order applies to the 30 s grace path. A concurrent complete revocation therefore cannot commit while leaving an active successor. On suspicious reuse (old token presented after grace): `RevokeAllTokens`. **Both branches check `users.enabled`** — a disabled/suspended user's refresh is refused with the SAME error shape as an invalid/expired token (no oracle) and all anchors are revoked via `RevokeAllTokens`. The admin-console suspend path (`mailserver/internal/admin/admin_users.go`) additionally fires a best-effort immediate revocation via `scim.RevokeAuthSessions` right after its commit. `internal/token/refresh.go`; deterministic DB race regressions: `refresh_revocation_fence_test.go`.
- **Impersonation token** (`POST /auth/admin/users/{id}/impersonate`): 15-min `TypeAccess` token with `AdminActorID` set (RFC 8693 act claim); requires re-validated admin; logged to `audit_log`. `IssueImpersonation`.
- **Domain-scoped admin tokens**: `issueTokensWithFactors` resolves the narrowest domain scope from `admin_role_assignments` + `admin_role_groups` via `shared/permissions.MintDomainScope(ctx, h.pool, user.ID)` (`MIN(COALESCE(ra.domain_override, rg.domain_scope))` over live assignments only — the query carries `AND (ra.expires_at IS NULL OR ra.expires_at > now())`, so an expired narrowing override never wins the MIN); **fail-closed on error** (HTTP 500 — the error is never swallowed to a nil/global scope). The mailserver gateway **re-derives the same scope by the same rule** at request time (`shared/permissions.Resolve(userID)` in `chain.go:resolvePermissions`). These are now **single-sourced**, not a hand-copied twin: `MintDomainScope` is the inverse-projection sibling of `Resolve` over the same rows (both in `shared/permissions/resolver.go`), so the ENFORCED scope agrees with the MINTED one **by sharing code** — there is no `auth.go` SQL literal to keep in lockstep, and the old `mintedScope` test twin is retired (it now delegates to `MintDomainScope`). Pinned by `shared/permissions/resolver_test.go`: the scope-agreement test plus `TestMintDomainScope_HonorsExpiry`, which pins the mint rule directly — deleting the `expires_at` clause inside `MintDomainScope` turns BOTH tests red. (Phase 1; Phase 2 — ARCH-005 — would embed the resolved scope in the JWT and drop the re-derivation behind the same seam.)
- **Token lifecycle seam** (`token.TokenService`, `internal/token/service.go`): the cohesive owner of issue/validate/introspect/refresh/revoke for first-party tokens, composing `JWTProvider` (signing core, ADR-005 ES256 dual-verify intact) with the `oauth_tokens` store. It is the **one place a first-party token is revoked** — the RFC 7009 `/auth/revoke` handler, refresh-token reuse-detection, logout, password-change, forgot-password reset, and SCIM disable all funnel through `TokenService.RevokeByToken` / `RevokeAllForUser` / `RevokeAllForUserTx`, which delegate to the single SQL primitives in `refresh.go`. No handler re-implements the revoke SQL. (Separately, OIDC-OP `oidc_tokens` revocation has its own single owner — `oidcTokenStore.revoke`.)
- **Token revocation** (`POST /auth/logout`): `TokenService.RevokeAllForUser` calls the reducer-owned complete boundary `revoke_user_sessions(...,'all',...)`. Under one person fence and transaction, the reducer revokes `oauth_tokens`, invalidates pending identity-link elevations, deletes `ws_subscriptions` and `sessions`, records the all-session denylist/audit event, and notifies runtime consumers. No Go caller may reproduce a partial subset. The shared lock order makes a concurrent mint either precede revocation and be revoked or follow it only after the relevant lifecycle/credential fence is rechecked. Logout fails closed with 503 if that transaction fails.
- **Rotated token cleanup**: background ticker calls `token.CleanupRotatedTokens` every minute; removes rows with `rotated_at < now() - 60s`.
- **JWT validation**: `JWTProvider.Validate` — checks signature, issuer, audience; does not check revocation (access tokens are short-lived). `internal/token/jwt.go`.
- **Web session row (web-session-revoke Tier 1)**: `issueTokensWithFactors` INSERTs a `sessions` row (mailserver-owned table, shared cluster) on every web login — `id` = the just-minted access token's own jti (read back via `h.jwt.Validate(res.AccessToken)`), `token_hash` = `sha256(access)`, plus UA/IP/`auth_method`/expiry. Best-effort (a write failure logs+drops, mirrors `RecordSignIn`) — never blocks issuance. ### OAuth2 token introspection (RFC 7662)

- `POST /auth/introspect`: accepts **two** caller classes — the internal gateway presenting `INTERNAL_API_KEY` as a Bearer token (the historical IMAP/SMTP path, JSON `{"token":...}` body), **and** a registered OAuth client authenticating with `client_id`+`client_secret` via HTTP Basic or POST body (RFC 7662 §2.1, form-encoded `token` parameter). Client credentials are verified against `oidc_clients` (bcrypt; constant-failure timing for unknown clients) via the shared `handlers.authenticateClient`. The endpoint is registered unconditionally (no longer behind the `INTERNAL_API_KEY != ""` gate). Looks up the SHA-256 hash of the submitted token in `oauth_tokens`; the response carries the full RFC 7662 §2.2 field set: `active`, `token_type` (always `"Bearer"` — the token *type*, not the `oauth_tokens` access/refresh/app_password discriminator), `scope`, `client_id`, `username`/`email`, `sub`, `aud` (gateway audience), `iss` (`JWT_ISSUER`), `iat`, `nbf` (= issuance), `exp`. An authenticated caller submitting an unknown/expired/revoked/disabled-user token gets the uniform bare `{"active":false}` — never an error oracle; an unauthenticated caller gets `401`. `internal/handlers/introspect_handler.go`, `internal/token/introspect.go`.

### OAuth2 token revocation (RFC 7009)

- `POST /auth/revoke`: revokes authserver-issued OAuth tokens (access + refresh) in `oauth_tokens` by SHA-256 hash via `token.RevokeByToken`. Same client-authentication contract as introspection (`INTERNAL_API_KEY` Bearer OR `client_id`+`client_secret` Basic/POST). **Idempotent**: an authenticated request always returns `200` whether or not the token existed (the SQL filters `revoked_at IS NULL`, so re-revoking / unknown tokens are no-ops); `token_type_hint` is intentionally ignored (the hash lookup is type-agnostic). Missing `token` → `400`; unauthenticated → `401`. **Distinct from the OIDC OP `/revoke` and `/oauth/introspect`** (which operate on `oidc_tokens` issued to OIDC clients). `internal/handlers/revoke_handler.go`.

### OAuth2 Authorization Server Metadata (RFC 8414)

- `GET /.well-known/oauth-authorization-server`: public metadata document for OAuth-only clients that don't speak OIDC discovery. Issuer is fixed to `https://<HOSTNAME>` (matches the OIDC OP `StaticIssuer`, so the two discovery documents agree); every advertised endpoint belongs to the same OP/`oidc_tokens`/RS256 universe: `/authorize`, `/oauth/token`, `/oauth/introspect`, `/revoke`, `/keys`, and `/userinfo`. It advertises `response_types_supported=[code]`, `grant_types_supported=[authorization_code,refresh_token]` (no implicit/ROPC/device grant), `token_endpoint_auth_methods_supported=[client_secret_basic,client_secret_post,none]`, `code_challenge_methods_supported=[S256]` (no `plain`), the AAL ladder, scopes, and claims. The first-party ES256 `/.well-known/jwks.json`, `/auth/introspect`, and `/auth/revoke` endpoints are intentionally absent because mixing those two token universes makes verification and revocation metadata false. `internal/handlers/oauth_metadata.go`.

### XOAUTH2 / app passwords (IMAP/SMTP SASL)

XOAUTH2 SASL decode/validate and app-password generate/list/revoke for IMAP/SMTP clients are implemented **in the mailserver gateway**, against the shared `oauth_tokens` table (`mail-ap-{hex}` prefixed tokens, SHA-256 hash, `token_type = 'app_password'`, max 10 per user; XOAUTH2 `base64("user={email}\x01auth=Bearer {token}\x01\x01")` parse → hash lookup → `last_used_at`/`last_used_protocol` bump): `mailserver/internal/imap/imap.go`, `mailserver/internal/smtp/submission.go`, `mailserver/internal/user/app_passwords.go`, `mailserver/internal/admin/admin_app_passwords.go`. The auth server's HTTP layer is not on this path; there is no authserver-side copy (an unreachable duplicate previously lived in `internal/token/` and was removed — the gateway is the single owner).

### TOTP (RFC 6238)

- **Setup** (`GET /auth/totp/setup`): generates 32-byte TOTP secret via `pquerna/otp`; stores AES-encrypted (`pgp_sym_encrypt`) in `users.totp_secret_enc`; returns provisioning URI for QR display. If TOTP already enabled, requires `current_totp_code` to replace. Logged to `admin_audit_log`. `internal/authn/totp.go:GenerateTOTPSecret`, `internal/handlers/totp.go:TOTPSetup`.
- **Confirm** (`POST /auth/totp/confirm`): verifies the first code against the **pending** secret (`authn.ConfirmTOTP` → `verifyPendingTOTP`, which fetches the secret regardless of `totp_enabled`, since enrollment confirm runs while `totp_enabled` is still `FALSE`), then sets `totp_enabled = TRUE`. Logged to `admin_audit_log`.
- **Verify** (`POST /auth/totp/verify`): unauthenticated; accepts `{mfa_token, code}`; validates MFA-pending JWT type. Verification + lockout go through the single `authn.VerifyTOTPWithLockout` seam (load → check-locked → verify → record-failure / reset), shared with the forgot-password TOTP path so the "5 consecutive failures → 15-min lock" (`totp_locked_until`) cannot be bypassed at one site. RFC 6238 replay protection is enforced atomically: the success path is a single conditional `UPDATE ... WHERE last_totp_used_at` (30 s window) `RETURNING` that doubles as the replay claim, so two concurrent requests with the same code yield exactly one success (no SELECT-then-UPDATE TOCTOU). On success: issues access + refresh tokens. `internal/handlers/totp.go:TOTPVerify`, `internal/authn/totp.go`.
- **Disable**: `authn.DisableTOTP` (called from settings flow, not a direct HTTP route here — handled in gateway's user API).

### WebAuthn / passkeys (FIDO2)

- **Registration begin** (`GET /auth/webauthn/register/begin`): requires access token; calls `go-webauthn`; session data stored AES-encrypted in cookie `wa_reg_sess` (5-min TTL, Secure, HttpOnly, SameSiteStrict). `internal/handlers/webauthn.go:WebAuthnRegisterBegin`.
- **Registration finish** (`POST /auth/webauthn/register/finish`): decrypts session cookie; calls `go-webauthn.FinishRegistration`; persists credential to `passkey_credentials` table (id, public_key, attestation_type, sign_count, device_name). `WebAuthnRegisterFinish`. **Cross-user collision is rejected (passkey-takeover closure):** `passkey_credentials` PK is `(id)` alone and the credential id is authenticator-chosen, so `persistCredential`'s `ON CONFLICT (id) DO UPDATE` is scoped `WHERE passkey_credentials.user_id = EXCLUDED.user_id` — a conflict on an id owned by another user updates 0 rows (never clobbers the victim's public_key) and surfaces an error instead of silently no-oping. Regression: `TestPersistCredential_CrossUserCollision` (DB-gated).
- **Login begin** (`GET /auth/webauthn/login/begin`): unauthenticated; looks up user by email; generates assertion options; stores session in encrypted cookie `wa_login_sess`; user ID in `wa_login_uid`. `WebAuthnLoginBegin`. `PasskeyProvider.BeginLogin` **canonicalizes the email at the provider boundary** (`identity.CanonicalizeAddress`) before both the DB lookup and the decoy HMAC — the handler feeds raw `r.URL.Query().Get("email")`, so a mixed-case passkey user (`Alice@Corp.com`) previously match-missed the `lower(email)`-unique row and fell into the decoy path (couldn't start a real assertion). See "Bug fix — auth-path email-lookup case-fold" below.
- **Login finish** (`POST /auth/webauthn/login/finish`): verifies assertion; updates sign count + `last_used_at`; if user has TOTP/push enabled, routes through MFA pending instead of issuing tokens directly. `WebAuthnLoginFinish`.
- **Rename credential** (`PUT /auth/webauthn/credential/{id}/name`): sets `device_name`. `WebAuthnNameCredential`.
- **Revoke credential** (`DELETE /auth/webauthn/credential/{id}`): sets `revoked_at`. `WebAuthnRevokeCredential`.
- **List credentials** (`GET /auth/webauthn/credentials`): requires bearer token; returns `{credentials: [{id, device_name, created_at}]}` for the authenticated user. `WebAuthnListCredentials`.
- WebAuthn user handle stored in `users.webauthn_user_handle`; generated randomly on first use.

### Push MFA (number matching)

- **Challenge generation** (`authn.NumberMatchPushProvider.GenerateChallenge`): rate-limited to 3 challenges per user per 5 minutes; generates a 2-digit code + 32-byte nonce; stores in `push_mfa_challenges` (120 s TTL). Dispatches in goroutine to all registered push devices. `internal/authn/push.go`.
- **WebPush dispatch**: decrypts VAPID push subscriptions from `push_devices`; sends JSON payload `{type, options, nonce, timestamp}` via `webpush-go`. Options include the correct number + 2 decoy numbers shuffled (Fisher-Yates).
- **Native push dispatch** (APNs / FCM / HMS): ECIES-encrypts the challenge code with the device's P-256 public key (`push_native.go`); dispatches via the `shared/push.Dispatcher` map (`SetNativeDispatchers`, §3 step 14 above) — the per-transport dispatchers themselves are not owned by this package. Device public key stored in `push_devices.device_public_key`.
- **OUT-OF-BAND answer (C10)**: the correct number-match code is **never** returned to the login client — not in the login response, the WebAuthn-login response, or `/auth/mfa/push/send`. It rides only the ECIES native device channel. Browser users use WebAuthn; a WebPush subscription is not treated as an authentication credential. `ChallengeResponse` carries no answer field by design.
- **Push MFA send** (`POST /auth/mfa/push/send`): accepts MFA-pending JWT; per-IP cap via `AllowIP` (`pushIPLimit`/`pushIPWindow`) before challenge generation; generates challenge; returns `{challenge_id, mfa_method, nonce, ttl_seconds}` (**no** `challenge_number`). `internal/handlers/push_mfa.go`.
- **Push MFA verify** (`POST /auth/push/verify`): in-band answer submission is **rejected** (returns `410 Gone` after validating the MFA-pending token). It never feeds a client-submitted answer into `VerifyChallenge` and never issues tokens — closing the C10 bypass. `internal/handlers/push.go:PushMFAVerify`.
- **Push MFA status poll** (`POST /auth/push/status`): the OUT-OF-BAND completion path for the browser/webpush login flow (C10). Body `{mfa_token, nonce}`. **Bound to the login session by the MFA-pending token** (proves the password factor + identifies the user; a bad/expired one → 401 before any DB work) and the challenge is looked up **by nonce scoped to that user** (no cross-user poll). Returns `{approved:false}` until approval, then issues the session to the poller. Tokens are issued **only when `push_mfa_challenges.approved_at IS NOT NULL`** — `approved_at` is a column DISTINCT from `verified_at` (V069) precisely because `VerifyChallenge`'s 3-strike lockout also stamps `verified_at`, so reading `verified_at` would let a lockout masquerade as an approval and hand out a session. **NOT wrapped in the threat interceptor** (a benign token-gated poll; the per-IP auth rate limiter would otherwise trip a 2 s polling cadence). `internal/handlers/push.go:PushMFAStatus`; SPA poller is `webmail/src/lib/stores/auth.ts:verifyPush`.
- **`VerifyChallenge`** (`internal/authn/push.go`) is the shared verification primitive: it delegates to `verifyChallengeTx`, which locks the challenge row with `FOR UPDATE` **scoped by `user_id`** (a nonce belonging to another user is treated as not-found, never compared/locked); compares the answer with `crypto/subtle.ConstantTimeCompare`; allows up to 3 failed attempts before invalidating the challenge; marks `verified_at` on success (single-use). Every failure path returns the single uniform `authn.ErrChallengeInvalid` (no nonce-miss vs wrong-answer oracle).
- **Per-account recovery lockout** (`internal/authn/push_lockout.go`): `VerifyChallengeWithLockout` is the SINGLE entry point for the forgot-password in-band push answer, mirroring `VerifyTOTPWithLockout`. Storage is the shared `auth_lockouts` table (key `push_user:{user_id}` — cross-replica by construction, replacing the round-1 in-process map); check, purpose probe, verification, and outcome recording run in ONE transaction that holds the account row from `INSERT .. ON CONFLICT DO UPDATE`, so concurrent attempts serialize and nothing verifies once the 5th failure commits. Threshold/window are compile-time aliases of the TOTP constants. Lock-state or purpose-probe read errors FAIL CLOSED (uniform invalid + logged error); a definitive purpose mismatch (login-stamped or stale nonce) is refused unrecorded. Pinned by `push_lockout_test.go` (concurrency exact-count, cross-replica shared budget, purpose fail-closed, TOTP parity — DB_DSN-backed).
- **Native MFA approve** (`POST /auth/mfa/approve`): a closed `setjoin.push-approval.v1` assertion binds nonce, displayed code, registered device/user IDs, initiating session, approve decision and a ≤120-second time window. The native vault signs RFC-8785-compatible canonical JSON with its persisted P-256 key; the handler locks the challenge, verifies the active device and signature, applies the 3-strike number-match rule, and atomically stamps `verified_at` + `approved_at`. Code/nonce alone is rejected. The approval call returns 204 and **never mints tokens**; only `/auth/push/status` can issue to the initiating MFA-token holder. Physical secure-keystore evidence remains a release gate. `internal/authn/push_assertion.go`, `internal/handlers/device.go:MFAApprove`, `clients/rust/guard-core`.
- **Security alerts**: `NumberMatchPushProvider.SendSecurityAlert` dispatches localized push notifications (en/zh/de) to all user push devices without creating a challenge record. `internal/authn/push_templates.go` provides `PushTitle`, `PushBody` per `PushTemplateKey`.
- **Device registration** (`POST /auth/device/register`): registers a push device — either native (APNs/FCM/HMS) with hex-encoded P-256 public key, or (QoL #9) `provider:"webpush"` with `push_token` = the browser's JSON-stringified `PushSubscription` and no `device_public_key` (ECIES envelope encryption is native-only; webpush's own VAPID+p256dh/auth channel covers it). Stores the token AES-encrypted in `push_devices`. `internal/handlers/device.go:DeviceRegister`.
- **VAPID public key** (`GET /auth/push/vapid-key`, unauthenticated — not a secret): serves the base64url public half of `VAPID_PRIVATE_KEY`, derived once at startup (`authn.DeriveVAPIDPublicKey`) so only one env var need be configured. 404 when push isn't configured. Consumed by the webmail's `pushManager.subscribe()` before the `POST /auth/device/register` webpush call above. `internal/handlers/push.go:VAPIDKey`.

### MFA first-factor possession gate (possession scheme v7; supersedes nightly-16 step-up)

EVERY factor-set mutation requires a fresh possession proof grant (owner
decision (a)); bearer identity alone never extends a factor set. The grant is
one row in `mfa_reauth_step_ups` (V271 transport, V272 tuple: `operation`,
`target_ref`, `proof_method password|totp|webauthn_uv`, `proving_factor_id`,
`bound_factor_generation`, `token_scope`, `refresh_family_id`), issued only by
`POST /auth/mfa/reauth` (password, C2/C3), `POST /auth/mfa/possession/totp`
(C1, session scope) and `POST /auth/mfa/possession/webauthn/begin|finish`
(C1 UV assertion, session or `mfa_pending` scope; begin/finish resolve their
dual token admission in-handler — bearer/cookie → session, else presented
`mfa_token` → `mfa_pending`, which may only request `bootstrap.totp.enroll`).
All four issuance endpoints require `Content-Type: application/json` (415 at
the mount). Impersonated bearers are refused at issuance AND every gated arm,
including the V250 removal. Consumption re-validates the FULL tuple under the
§2.2 fences (`identity_auth_person_fence` → users row → artifacts) inside the
mutation's transaction, plus the durable revocation-recheck watermark
(mirrors `shared/threat` `IsRevoked`); a tuple mismatch deletes the dead grant.
TOTP setup stages a pending enrollment (`totp_pending_enrollments`, UUID +
`staged_by_jti`, 15-min TTL) with one-time grant binding — the ACTIVE factor is
touched only at confirm, which promotes + bumps `users.factor_generation` +
consumes the grant atomically. `bootstrap.totp.enroll` grants are minted
atomically with the login's `mfa_token` (C2/C3); C1 passkey holders bootstrap
through the UV ceremony instead. Storage: `internal/authn/possession.go`;
endpoints: `internal/handlers/mfa_possession.go`. Contract:
retired-docs:verification/2026-09-23-possession-scheme-v7.md. The bootstrap TOTP-cycle
(`VerifyTOTPWithLockoutTx`) runs load→check→verify→record/reset in ONE
transaction for every shared TOTP caller (login, forgot-password, removal
begin).

### Forgot password (self-service reset via MFA)

### OIDC Relying Party (RP)

- **Multi-provider**: `federation.OIDCRPProvider` loads `system_config` rows with keys matching `oidc_provider_*_config` (JSON). `internal/federation/oidc_rp.go`.
- **SSRF-guarded discovery**: before `rp.NewRelyingPartyOIDC` fetches `{issuer}/.well-known/openid-configuration` + JWKS, `loadProviders` enforces https on the admin-set issuer (`validateOIDCIssuerScheme`, mirroring saml_sp.go's scheme check) and passes `rp.WithHTTPClient(safeOIDCDiscoveryClient())` — the `shared/ssrf` dial-time guard (DNS-rebinding defense), matching the SAML metadata fetch / mailserver JWKS / MTA-STS paths. The guard applies on both the initial `NewOIDCRPProvider` load and the `ListenForChanges` hot-reload (both funnel through `loadProviders`).
- **Login** (`GET /auth/oidc/login?provider=<name>`): generates cryptographically random `state` + `nonce`; stores in encrypted HttpOnly cookies (`oidc_state`, `oidc_nonce`, `oidc_provider`) with 10-min TTL; PKCE (FEDERATION-003, `internal/federation/pkce`): `AuthCodeURL` mints the RFC 7636 `code_verifier` and the redirect URL carries its S256 `code_challenge`; the verifier rides the same flow-cookie set (`oidc_verifier`, HttpOnly SameSite=Strict, 10-min TTL); redirects to IdP authorization URL. `AuthHandler.OIDCLogin`.
- **Callback** (`GET /auth/oidc/callback`): validates state cookie; rejects a missing/malformed `oidc_verifier` fail-closed ("missing/invalid code verifier") before provider resolution; clears the `oidc_state` + `oidc_verifier` flow cookies immediately — the verifier is single-use, deleted on exchange before the token call, and a replayed callback is rejected by the IdP's one-time-code check; exchanges code for ID token presenting the verifier (a well-formed verifier that does not derive the redirect's challenge is rejected by the IdP's RFC 7636 §4.6 check); validates nonce (OIDC Core §3.1.2.1, §15.5.2); validates `email_verified`; validates `redirect_uri` if present; extracts `sub`+`iss` stable identity and groups; calls `lookupOrJITUser`. The zitadel RP verifier's default empty-nonce callback is explicitly disabled because Setjoin sends a random nonce and performs the request-bound comparison itself against its HttpOnly `oidc_nonce` cookie immediately after cryptographic token verification; leaving both enabled rejects every correct non-empty nonce before Setjoin can compare it. `AuthHandler.OIDCCallback`.
- **JIT**: per-provider `jit_enabled` or global `JIT_ENABLED`; user created in `users` with `sync_source = 'sso'`, `oidc_subject`, `oidc_issuer` fields.
- **Group mappings**: decoded from `oidcProviderConfig.groupMappings`; applied on every SSO login (same `applyGroupMappings` as SAML).
- **Live reload**: `OIDCRPProvider.ListenForChanges` on `config_changed` with `key = "auth_methods"` or `"oidc_rp"`.

### OIDC Identity Provider (OP / IdP mode)

Enabled via `OIDC_PROVIDER_ENABLED = true`. Implemented using `zitadel/oidc` v3 (OpenID Foundation certified library).

- **Discovery** (`GET /.well-known/openid-configuration`): standard OIDC discovery metadata, augmented via `federation.OPDiscoveryWrapper`. The wrapper guarantees the conformance fields `acr_values_supported` (`["aal1","aal2"]`), `code_challenge_methods_supported` (`["S256"]`), `scopes_supported`, and `claims_supported` are present. It also narrows zitadel's provider-wide defaults to the capabilities Setjoin actually implements: `response_types_supported=["code"]`, `grant_types_supported=["authorization_code","refresh_token"]`, and no `device_authorization_endpoint`. Advertising implicit, device, or another unmounted flow is a protocol-contract failure even when the upstream library has generic support for it. It post-processes discovery only and passes every other path through untouched.
- **id_token acr/amr**: `storedAuthRequest.GetACR()`/`GetAMR()` return the session's authentication context (floor `aal1`/`[pwd]` — the OP authorize flow proceeds only on a password-authenticated session; `withAuthContext` records stronger factors when the login UI captures them, never up-claiming an AAL the session did not reach). `internal/federation/oidc_op.go`.
- **JWKS** (`GET /keys`): public key set (RS256 from OIDCKeyManager).
- **Authorization endpoint** (`GET /authorize`): wrapped in threat interceptor. A valid request is stored incomplete and redirected through `storedClient.LoginURL` to `GET /auth/oidc/op/complete?id=…`. That completion route accepts an existing Setjoin access session or redirects an anonymous browser to the same-origin login page with the exact completion URL in a bounded `continue` parameter. The web client accepts only `/auth/oidc/op/complete` with one bounded `id`, performs a full browser navigation after any password/passkey/MFA completion, and rejects external/unrelated/duplicate-parameter continuations. The resumed route binds only the authenticated `user_id` plus its exact `auth_time`/`acr`/`amr`, then returns to zitadel at `/authorize/callback?id=…`. An uncompleted or expired request cannot mint a code; completion is one-shot even for the same user so a replay cannot overwrite the original authentication context, and a different user cannot take over an already-bound request.
- **Token endpoint** (`POST /oauth/token`): authorization code exchange + refresh.
- **Introspection endpoint** (`POST /oauth/introspect`): client-authenticated introspection of OP-issued `oidc_tokens`, distinct from first-party `/auth/introspect`.
- **UserInfo endpoint** (`GET /userinfo`): returns claims for bearer token.
- **End session** (`POST /end_session`), **Token revocation** (`POST /revoke`): standard endpoints.
- **PKCE**: S256 enforced (`CodeMethodS256: true`).
- **Refresh grant**: enabled (`GrantTypeRefreshToken: true`).
- **Auth request storage**: V176 adds explicit `done`, `auth_time`, `acr`, and `amr` state to the short-lived `oidc_auth_requests` table. `CreateAuthRequest` never trusts the optional `id_token_hint` subject as a logged-in user and writes `user_id=NULL`; `CompleteAuthRequest` performs a one-shot authenticated bind requiring `done=FALSE AND user_id IS NULL`, so neither same-user replay nor cross-user takeover can replace the original authentication context. V177 binds the distinct authorization code generated by the OP library to that completed request as a unique SHA-256 `code_hash`: request IDs are not bearer codes, raw codes are not recoverable from the database, binding is write-once, and `AuthRequestByCode` accepts only a matching completed row before atomically consuming it with `FOR UPDATE + DELETE`. The stored client returns callable pass-through scope-restriction functions because zitadel invokes those callbacks unconditionally while creating access and ID tokens; a nil callback panics after consuming the code. Email/profile claims are read for the exact numeric subject through `dbscope.RunUserScoped`, so the constrained FORCE-RLS role returns the authenticated user's claims instead of silently emitting an empty email. `IDTokenUserinfoClaimsAssertion` is true so zitadel retains those approved-scope claims in code-flow ID tokens even when it also issued an access token; false strips `email`/`email_verified` before the RP can enforce them. The table remains UNLOGGED by baseline design: a database crash may invalidate an in-flight ten-minute authorization request, which safely requires the user to restart login rather than issuing from incomplete state. `internal/federation/oidc_op.go`.
- **OPStorage structure** (zitadel `op.Storage`): a thin coordinator over three single-concern collaborators — `oidcClientStore` (`oidc_clients` reads + client auth), `oidcTokenStore` (every `oidc_tokens` read/mutation incl. the lone OIDC-token revoke seam), `oidcSigningAdapter` (RS256 key material). OPStorage keeps only the `oidc_auth_requests` coordination + the zitadel adapter types (`storedClient`/`storedAuthRequest`) and delegates the rest, so the interface is satisfied identically. The OP's `RevokeToken` is the third revocation path, funneled through `oidcTokenStore.revoke` (client-scoped, by refresh-hash OR access-id).
- **Key management**: `federation.LoadOrGenerateKey` loads or generates the RS256 key at the configurable `OIDC_PROVIDER_PRIVATE_KEY_FILE` / `OIDC_PROVIDER_PUBLIC_KEY_FILE` paths (defaults under the writable `/opt/setjoin/` install root). `internal/federation/oidc_keys.go`.
- **Crypto key**: derived via `cryptokey.DeriveOIDCCryptoKey(JWTSecret)`, passed as 32-byte array.

### Identity resolution — resolve_identity seam (ADR-004 Half A)

A person is **one identity with a full address set**: `users.email` ∪ `aliases.email` (joined to the owner via `mailboxes.user_id`) ∪ `users.ad_upn`. A single SQL rule — `connector.ResolveIdentitySQL` (case-insensitive UNION) — is the matching key everywhere, so no path re-derives "which person is this address?" and they cannot drift apart:

**Co-evolving twin + the documented cross-module DB dependency (shared/identity plan 2026-06-18 → Concern B).** `connector.ResolveIdentitySQL` is the authserver twin of the mailserver reducer `mailserver/sql/reducers/resolve_identity.sql`. The two **share the matching predicate** (the union WHERE: email ∪ alias ∪ UPN, case-folded, enabled-only) but **differ in projection** — this Go fragment is FROM/WHERE-only (each caller appends its own SELECT for the full `Identity`/`userRow`), the reducer returns `(user_id, primary_mailbox, domain_id)`. The predicate MUST stay structurally identical: if it drifts you get **split-brain identity** (auth logs you in, mailserver can't find your mailbox — silent lockout / duplicate JIT). A definition guard — `scripts/check-identity-predicate.sh` (extracts + normalizes away the cosmetic `$1`⇄`p_address`, `mb`⇄`m` alias, whitespace, and the reducer-only `IS NOT NULL` null-guard, then diffs both WHERE clauses; self-test `check-identity-predicate-selftest.sh`; wired into `scripts/test.sh`) — fails CI the instant they diverge. Both sites carry a `co-evolving twin` source comment. A guard firing on an *intended* rule change (a NameID/`sub` normalization landing) is the trigger to merge the union into a single `resolvable_identity` view. **Cross-module DB note:** the `resolve_identity` *reducer* is owned under `mailserver/sql/`; authserver is allowed to depend on it (and on the shared `users`/`aliases` schema) because both servers share one PostgreSQL database under ARCH-002. authserver itself does not call the reducer today (it runs its own twin SQL via the connectors), but the predicate is co-owned and guarded as above.

**Input canonicalizer — one match-key/provision-key seam (normalization wave, 2026-06-18).** The matching predicate above takes its `$1` from `shared/identity.CanonicalizeAddress` at **every** consumer, and the provisioning sites take their value from `shared/identity.NormalizeAndValidate` — and `NormalizeAndValidate` is `CanonicalizeAddress + validate.ValidateEmail`, so on success its output is **byte-identical** to `CanonicalizeAddress`. That equality makes the **duplicate-JIT-on-normalization** bug structurally un-writable: an SP assertion subject carrying surrounding whitespace or an RFC-5322 display-name form (`"Alice" <a@x>`) now canonicalizes to the same value the provision path would write, so step-3 match and step-4 provision can no longer disagree. The canonicalizer is **trim + ASCII-fold lower + display-name strip ONLY** (NOT unicode `ToLower` — avoids the Turkish-I / ß hazards; pinned by a live test) and it **never rejects** — a bare UPN / Kerberos principal passes through (trim+lower) so it still resolves against `ad_upn`/aliases. The matching *predicate* and its twins guard are **unchanged** — only the input feeding the predicate is normalized. IDN/Unicode-NFC is **deferred** to a future writer-first migration (`shared/identity.CanonicalizeAddress` is the documented seam it will extend). See `shared/identity/addr.go`.

- **Connector seam** — `Connector.LookupByAddress(ctx, address)` (replaces the old primary-only `LookupByEmail`) on the local + AD connectors, both consuming `ResolveIdentitySQL` with `identity.CanonicalizeAddress(address)` bound to `$1` (the AD no-pool echo fallback echoes the canonical form). Returns the **canonical** identity (`users.email`) regardless of which address matched. The local connector's **single-table** lookups — `VerifyPassword`, `ChangePassword` (SELECT **and** UPDATE), keyed on `users.email = $1` — now also bind `identity.CanonicalizeAddress(extID).String()`, so the seam holds at every consumer (not just the union lookup). `ChangePassword` additionally asserts the UPDATE touched **exactly one row** (`RowsAffected() == 1`), failing loudly on the zero/multi-row class (a folded SELECT with an un-folded UPDATE would otherwise silently write zero rows). See "Bug fix — auth-path email-lookup case-fold" below.
- **Federated auth, SP mode** — `lookupOrJITUser` (step 3) matches the inbound assertion subject (NameID / `email` / UPN / `preferred_username`) against the full set via `AuthHandler.resolveUserByAddress`, which routes the subject through `identity.CanonicalizeAddress` before the same `ResolveIdentitySQL` rule (returning a `userRow` with admin fields) **before** JIT-provisioning. So a UPN-or-alias assertion from an external IdP (Azure AD/ADFS/Okta — UPN commonly differs from primary SMTP), in any whitespace/display-name/case form, resolves to the EXISTING person; a duplicate is never JIT-provisioned. JIT runs only when no address matches. (The raw NameID/`sub` — the IdP's **stable id** — is passed verbatim to `linkSAMLIdentity`/`createJITUser`; only the *address* is canonicalized.)
- **P17 SSO fail-closed guest exclusion (Guest Accounts G0):** a guest row never participates in SSO resolution, stable-id linking, or JIT — SSO-federated guest identity is an explicit v1 anti-scope. Checked at the first point `h.identityResolver.ResolveExisting(ctx, keys)` returns a non-nil `user`, BEFORE any of the per-source side effects (SSO-email refresh, stable-id link, group-mapping settle, token mint): an `is_guest_account($1)` hit **fails closed** — a query error 500s ("account type resolution failed"), and a genuine guest hit 401s ("sso: identity resolves to a guest account") — no link, no mint, no email refresh, no JIT. `internal/handlers/auth.go` (guarded by `internal/handlers/guest_sso_test.go`). The mailserver-side SCIM surface carries the identity-plane's other P17 exclusion (PATCH/DELETE refuse a guest target; every list query omits guest rows) — see `mailserver/internal/AGENTS.md`'s SCIM 2.0 section; both close the same principle (a guest is provisioned/managed via the guest console, never IdP sync) from their own server.
- **Federated auth, IdP mode** (`oidc_op.go`) — asserts the **canonical** person: the OIDC subject is `users.id`, and `email`/`profile` claims are read from that row. No primary-only matching bug exists here. (Exposing a non-primary address via a configurable claim is an optional future enhancement, not required for the bug fix.)
- **Multi-forest** — a person synced from two AD forests with addresses on different domains resolves to ONE identity, because all of their addresses (proxyAddresses → `aliases`, userPrincipalName → `ad_upn`) union under their single `users` row.

the committed family anchor. `deferred_token_response_test.go` proves both the
normalized-SSO and fenced-TOTP caller-owned transaction shapes publish no cookie
or body and persist no anchor when commit fails; source-text scans are not the
primary contract proof.

Password-originated TOTP enrollment setup and confirm must apply the signed
`CredentialFence` before writing a pending secret or activating the credential.
When either an identity or credential fence is present, setup uses the Tx variant;
the transaction first calls the shared `applyAuthenticationMintFence` selector
(normalized exact source/link fence, otherwise local person fence), then verifies
the credential version, so a password update cannot interleave between proof and
write. Confirm keeps fence checks, TOTP activation, and refresh-family anchor in the same
caller-owned transaction and publishes tokens only after commit. A password change
between first factor and enrollment therefore returns 401 with no TOTP or token
state committed. Legacy MFA-pending tokens with neither fence keep their existing
compatibility path. Tests cover identity-only, credential-only, and combined
identity-plus-stale-credential inputs. An injected deferred commit failure proves
confirm publishes no cookie/body or family anchor and rolls activation back to the
exact pre-confirm pending-secret state.

Every local first-party completion path (password, TOTP, backup code, push,
WebAuthn, and device approval) opens a transaction and calls
`identity_auth_local_mint_fence` before persistence. `TokenService.IssueTx`
stores the access/refresh family through that same transaction, so a concurrent
detach, disable, or transition cannot pass a check and mint afterward.
Normalized identity resolver and mint-fence query errors are terminal; neither
falls back to legacy email matching or an unscoped token.

**Normalized SSO settlement fence.** With `feature.identity_model_v2` enabled,
an asserted email/UPN is discovery evidence only: it may locate a candidate but
never creates or claims a durable link, and an unlinked address match returns
409 before any entitlement or token write. A successful normalized callback
commits its bounded profile and provider-scoped entitlement reconciliation
first, then re-derives the authorization/email view and evaluates conditional
access. Immediately before mint it opens `identity_auth_mint_fence`, rechecks
and locks the enabled user plus exact source/link generations, and stores the
refresh-family anchor through that same transaction with
`TokenService.IssueTx`. Cookie and JSON token output remain buffered until
commit succeeds. This ordering prevents a second mapping transaction from
self-blocking on the fence's user-row lock, while a concurrent detach/disable
that wins before the final fence rejects the mint and one that loses waits for
the committed anchor before revocation. If conditional access returns step-up,
the signed MFA-pending token carries those exact source/link generations; the
shared TOTP enrollment/verify, backup-code, and push completion seam restores
them and runs `identity_auth_mint_fence` in the same transaction as
`TokenService.IssueTx`. A federated first factor therefore cannot silently
degrade to the local mint fence after source pause/retire, link detach, purpose
removal, or a generation change.

Authenticated link initiation is state-changing and therefore POST-only:
`POST /auth/oidc/link` and `POST /auth/saml/{idp}/link` run behind the shared
Origin/Referer CSRF middleware. Do not restore a GET initiator.

### JIT (Just-In-Time) user provisioning

- `lookupOrJITUser` (shared by SAML and OIDC paths): priority lookup — OIDC stable ID → SAML stable ID → **any address (resolve_identity seam, above)** → JIT create. On any SSO login, links stable IDs to existing users, then **settles group mappings AND clears conditional access BEFORE issuing the session token** via `settleSSOMappingsThenIssue` (commit mappings → re-derive identity/authority → `evaluateSSOConditionalAccess` → final normalized mint fence → persist/commit family anchor → publish tokens), so a first-login grant/revoke lands in the same-login token, a CA block/step-up denies/steps-up the federated login, and a commit failure emits no token material. `internal/handlers/auth.go`.
- JIT user creation: inserts into `users` with `sync_source = 'sso'`; creates primary `Inbox` mailbox for distribution group membership.
- **Email is untrusted**: the JIT email comes from the SAML NameID / OIDC sub. Both write sites route through the single `normalizeAndValidateSSOEmail` seam — now a thin wrapper over `shared/identity.NormalizeAndValidate` (the provision half of the one canonicalizer): it trim + ASCII-fold-lowers + display-name-strips, then validates via `shared/validate.ValidateEmail` (well-formed, ≤254 chars, no control chars / header-injection, domain has a dot) **before** any DB write: `createJITUser` validates before the INSERT (invalid → no user provisioned), and `updateSSOEmail` (the returning-user path that refreshes `users.email` on every SSO login) validates before the UPDATE (invalid → no write, error logged). Keeping one chokepoint means the validation cannot be missed at one site again — and because it shares `CanonicalizeAddress` with the match path, the provisioned value equals the value the matcher would have resolved.

### 8-step pre-auth threat pipeline

Implemented in `shared/threat/interceptor.go`; consumed here as `threat.New(pool, featureToggles, geoipReader, threatCfg, logger, nil)`. Each step is feature-toggled independently:

1. **Threat feed** (`FeatureThreatFeed`): blocks IPs on Spamhaus DROP/EDROP and operator-defined IP blocklists; feeds refreshed every 30 min via `threat.RefreshFeeds` goroutine.
2. **IP rules** (`FeatureThreatFeed`): per-IP operator rules (allow/block) from `threat_ip_rules` table.
3. **Geo-block** (`FeatureGeoBlock`): blocks IPs from configured country codes (`GEO_BLOCK_COUNTRIES`) using MaxMind GeoLite2 DB.
4. **Lockout** (always active): per-IP lockout after repeated failures.
5. **Spray detection** (`FeatureSprayDetect`): counts distinct usernames per IP in `THREAT_SPRAY_WINDOW_SECS`; lockout for `THREAT_SPRAY_LOCKOUT_MINS` when `THREAT_SPRAY_MAX_USERS` exceeded. PL/pgSQL: `detect_spray.sql`, `lockout_escalate.sql`.
6. **CAPTCHA** (`FeatureCaptcha`): requires CAPTCHA token after `THREAT_CAPTCHA_THRESHOLD` failures in `THREAT_CAPTCHA_WINDOW_MINS`; validated using HMAC on `CAPTCHA_SECRET` (defaults to `JWT_SECRET`).
7. **Tarpit** (`FeatureTarpit`): progressive delay for suspicious IPs; triggered after `THREAT_TARPIT_THRESHOLD` failures in `THREAT_TARPIT_WINDOW_MINS`.
8. **Rate limit**: max `THREAT_RATE_LIMIT_PER_MIN` requests per IP per minute; returns `429`.

The threat interceptor is applied as middleware on `POST /auth/login`, `POST /auth/refresh`, TOTP verify, push verify, backup code verify, forgot-password, and OIDC OP endpoints. Skipped entirely on login when all five threat feature toggles are disabled.

### Conditional access

- `threat.PolicyEngine` wraps the shared `threat.pgxPolicyStore` (built via `threat.NewPolicyStore`).
- `LoadPolicies` queries `conditional_access_policies` filtered by `global`, `user`, `group`, or `role` scope (V142 widened the `scope_type` CHECK to add `role` — `scopeMatches` in `shared/threat/policy.go` already implemented it); ordered by priority ASC. `domain` is not a valid scope — it was briefly offered in the webmail CA editor with no engine/CHECK support anywhere and was removed from the UI rather than implemented.
- `ResolveGeoTier` looks up country risk tier from `geo_country_tiers`.
- Evaluated after password verification in `Login`; result can be `Allow`, `Block`, or `StepUp` (force MFA regardless of user's TOTP setting). `internal/handlers/auth.go`, `shared/threat/store.go`.
- **Federated logins (SAML SP / OIDC RP) are also gated.** `settleSSOMappingsThenIssue` runs `evaluateSSOConditionalAccess` (which calls the same `evaluateAndRespond` block/step-up seam as `Login`, with `AuthMethod` = `"saml"`/`"oidc"` and the user's resolved groups) AFTER the SSO group mappings settle and BEFORE the session is minted. `Block` denies the login; `StepUp` yields an MFA-pending body, not a full session. Previously SAML ACS + OIDC callback issued tokens with no `Evaluate` call, so the primary enterprise login path bypassed every CA control (block/step-up/geo/device). `evaluateAndRespond`'s receiver is `*deps` (not `*loginHandler`) so both the password and SSO seams share it.
- **acr/amr requirement (step-up)**: a policy may carry the `require_acr` action (`{"action":"require_acr","acr":"aal2"}`, default `aal2`) to demand a minimum Authentication Context Class for a context. The engine compares it against `PolicyEvalContext.CurrentACR`: at login (`CurrentACR=""`) an unmet requirement yields `StepUp` (the MFA-pending → second-factor path mints a token carrying the satisfied `acr`/`amr`); downstream, `PolicyEngine.EvaluateTokenACR` re-checks an already-issued token's `acr` and returns `StepUp` (caller must reject) for an `aal1` token against an `aal2` requirement. `PolicyResult.RequiredACR` reports the demanded class. `shared/threat/policy.go`.
- **Guest-scoped Conditional Access (Guest G5):** password login, SSO settlement, and factor-completion evaluation all populate `PolicyEvalContext.IsGuest` through the injected production resolver `SELECT is_guest_account($1)`. A resolver error returns 503 before evaluation or token mint; tests may intentionally leave the resolver nil as the explicit hermetic member-context seam. This makes targetless `scope_type='guests'` policies depend on the authoritative satellite rather than email/domain heuristics or a caller-supplied claim.
- Policy cache invalidated on `LISTEN conditional_access` NOTIFY (the single CA channel; `ca_notify_policy_change()` reducer calls `app_notify('conditional_access', …)`; `InvalidateCache()` flushes both the 30 s policy-set cache and the F8 ≤5 s per-principal decision cache).
- `CONDITIONAL_ACCESS_FAIL_CLOSED=true` denies login if policy evaluation errors (maps to `failMode="closed"` in `PolicyEngine`).
### Device trust

- **Device HMAC secrets are sealed at rest** (V247 + shared/device SecretCodec, med-auth-baseline-secrets-001 SHIP): registrations persist only the AES-256-GCM EK01 `_enc` envelope + `hmac_secret_key_id` (plaintext returned once, never stored); legacy plaintext rows verify unchanged and are lazily re-sealed ciphertext-only on first verification (TOCTOU-safe R3-shaped UPDATE); unknown key-id fails closed. Rotation/rollback semantics for already-issued keys remain an open owner decision.
- **Single auth seam** (`internal/device/auth.go`): every device endpoint is wired through `device.RegisterRoutes(mux, pool, jwt, logger, csrf)` (called from `main.go`), which attaches the correct guard so no device route can be exposed unauthenticated by omission. Two guards:
  - `RequireUserAuth` (+ CSRF) for the registration *bootstrap* only — it validates a Bearer **access** token (rejecting other token types) and stamps the user ID into the request context. Registration can't be HMAC-authenticated (it's what mints the secret), so it binds to the authenticated user instead.
  - `RequireDeviceHMAC` for every post-registration endpoint (checkin, policy read), which extracts `device_id` (from body or query), then calls the shared `VerifyDeviceRequest` before the handler runs. Both endpoints route through this one guard.
- **Device identity** (`internal/device/identity.go`): `RegisterDevice` upserts into `devices` table (keyed by `user_id + fingerprint`); generates per-device HMAC secret; returns device ID. The `Handler.Register` handler binds the device to the user from `UserIDFromContext` and **fails closed (401)** if the context is unauthenticated — it never trusts a user ID from the body and never defaults to 0. `VerifyDeviceRequest` authenticates inbound device requests by checking the `X-Device-HMAC` header (over `challengeFor(device_id, X-Device-Timestamp)`) against the stored per-device secret via constant-time `ValidateHMAC`, **and** bounds the `X-Device-Timestamp` to `MaxClockSkew` (±5 min) via `checkTimestampFresh` so a captured HMAC cannot be replayed indefinitely.
- **Device registration** (`POST /device/register`): user-access-token authenticated (`RequireUserAuth` + CSRF); binds the new device to the authenticated user; returns the per-device HMAC secret once. `internal/device/identity.go:Handler.Register`. (Distinct from `POST /auth/device/register`, which registers an APNs/FCM/HMS *push* device in `push_devices`.)
- **Device check-in** (`POST /device/checkin`): **per-device HMAC authenticated** via `RequireDeviceHMAC` → `VerifyDeviceRequest` (HMAC + timestamp-freshness) — the request must carry `X-Device-HMAC` (hex HMAC-SHA256 of the canonical challenge `"{device_id}:{X-Device-Timestamp}"`, keyed by the per-device secret issued once at registration) and a fresh `X-Device-Timestamp`; a missing/unknown/mismatched/stale proof is rejected with 401 before any policy read or state mutation (prevents `device_id` spoofing and HMAC replay). On success: resolves merged device policy (global → per-device); reports device events to `device_events`; returns wipe flag and policy ETag. `internal/device/checkin.go`, `internal/device/identity.go`.
- **Device policy** (`GET /device/policy`): same per-device HMAC guard as check-in (the SIBLING site — both call the single `VerifyDeviceRequest` seam); ETag-cached (304 if policy version unchanged). `HandleGetDevicePolicy`.
- **Policy layers**: global (`device_policy WHERE device_id IS NULL`) overridden by per-device rows; version computed as sum of key+value rune values.
- **Wipe**: `devices.wipe_requested` triggers `{wipe_requested: true, wipe_reason: "..."}` in check-in response.
- **MAM policy defaults**: copy_paste=allow, screen_capture=allow, encryption=required, watermark=false, notification_profile=push, max_offline_days=30.
- JWT `device` and `mam` claims: optionally embedded in access tokens via `IssueAccessWithDevice`; not yet wired from check-in into the login flow (device ID path deferred).

### Admin impersonation

- `POST /auth/admin/users/{id}/impersonate`: re-validates admin status against live DB (defense-in-depth against stale JWT) — actor + target admin status are DERIVED from `admin_role_assignments` (`isAdminExprSQL`), NOT the vestigial `users.is_admin` column (the RBAC cut-over leaves that column false, so reading it 403'd every governed/SSO admin); issues 15-min impersonation token with `AdminActorID` claim; logs to `audit_log`; sets the **`access_token`** HttpOnly cookie (900 s) — the name the gateway auth chain + authserver session read (the old `auth_token` name was read by nothing, so the impersonation session was never picked up). `internal/handlers/impersonation.go:impersonationHandler.AdminImpersonate`.
- **Privilege-escalation guard (safe default — refuse cross-or-upward admin impersonation)**: the handler derives each party's privilege tier from its **governed `admin_role_assignments`** (the `users.admin_role` enum was dropped — `resolveImpersonationTier` returns `hasGoverned` + `isSuperAdminGroup`), then refuses (`403`, audited as `admin_impersonate_denied`) when the target's tier is **>=** the actor's. Tiers (via `impersonationRank(isAdmin, hasGoverned, isSuperAdminGroup)`): non-admin 0 < legacy bare `is_admin` (no governed row) 1 < governed non-super admin 3 < governed **Super Admin** group (id 1) 4. All governed non-super admins share rank 3, so a governed admin can never impersonate a peer or a super-admin. An admin may impersonate only strictly-less-privileged accounts.
- **Scope-constrained token**: the impersonation token carries the RFC 8693 `act` claim for audit but never grants admin authority (`IsAdmin=false`; the token also carries no `role` claim — that field was removed). `AdminImpersonate` re-validates these invariants on the freshly issued token before handing it out and refuses (`500`) if the constraint does not hold.
- **Guest Accounts G0**: `IssueImpersonation` gained a trailing `accountType string` param — the handler derives it the same `is_guest_account(target)` way every other mint site does before calling it, so impersonating a guest yields a guest-claimed token honestly rather than a silently-member-claimed one (the gateway's `chain.applyGuestBelt` would force the correction anyway; this closes the gap between the minted claim and the enforced reality).

- SIGHUP listener (`sharedcfg.NotifyReloadOnSIGHUP`) reloads config and stores in atomic pointer.
- `POST /admin/reload`: API-key gated HTTP endpoint for Windows (no SIGHUP) and cross-platform automation.
- SAML and OIDC registrations reload live through separate durable `shared/pgnotify` listeners on `config_changed`; reconnect performs a full authoritative reload before notification delivery resumes.
